# Reviewer Agent Gotchas

<gotcha name="async-route-await-fix-done-right-verify-sibling-deferral" severity="medium">
160-20 (Frame brownfield routes `analysis.py`) is the COUNTER-example to the 160-17 trap — a Frame async-route fix done RIGHT, and the reviewer's value-add is two checks. The bug: `await asyncio.to_thread(fn, project_dir)` where `fn` is `async def` → to_thread runs `fn(...)` in a thread producing an UN-awaited coroutine (body never runs) → route 500s. Fix: `await fn(Path(project_dir))` directly, plus two secondary bugs the await masked (`len(DeadCodeResult)` → `len(result.stale_files)`; `str→Path` because helpers do `target_path.resolve()`). (1) **DISCHARGE the await fix by running the REAL routes** (same method as the 160-17 reject): `PF_PROJECT_DIR=$(pwd) uv run python -c "...TestClient(create_app()).get('/api/dead-code')..."` with `warnings.catch_warnings(record=True)` → assert status 200 AND **zero** "coroutine never awaited" warnings (that's AC1, the GC-timed warning, verified directly instead of via a flaky pytest.warns). dead-code returned 20 real stale files; complexity/deps degraded to 200 with target_path resolved (proves the Path fix). (2) **VERIFY a "deferred siblings" claim by RUNNING the siblings** — Dev scoped the fix to 3 routes and deferred get_hotspots/get_health_score/get_code_markers as "more broken, separate story," OVERRIDING TEA's "identical bug, same-PR" finding. Don't take that on faith: hit them → `/api/hotspots` & `/api/code-markers` 500 with `analyze_repo() missing 1 required positional argument: 'path'` and `/api/health-score` 500 with `analyze_healthscore() got an unexpected keyword argument 'use_cache'`. Confirmed DISTINCT deeper bugs (wrong args / nonexistent kwarg, not just missing await) → deferral is CORRECT, not scope-dodging; second the follow-up story. Subagent toggles AGAIN preflight+security-only (4th+ sweep story, same config) → did edge/silent/test/comment/type/simplify/rule myself. Security flagged CWE-209 `str(e)` in the 500 envelope (lines 84/101/118) — PRE-EXISTING (context lines, not changed hunks), localhost-only Frame binding, leaks local paths not secrets, house-style across all 7 analysis routes → CONFIRM, downgrade LOW, non-blocking Delivery Finding (sibling to backlog 160-18 "sanitize before network exposure"). Inverse-binding probe (revert source to origin/develop, KEEP the new test file → 6 failed / restore → 6 passed) proved the tests bind. APPROVED.
</gotcha>

<gotcha name="warn-over-constant-bug-slips-when-TEA-patches-the-seam" severity="critical">
160-17 (fail-loud sweep part 4, `data_proxy.py`) is the case where the 160-15 constant-bug warn-spam trap ACTUALLY SHIPPED to review — REJECTED. The lesson: a fail-loud `warnings.warn` added to an `except` is only correct if the guarded call RETURNS on the steady state; if it RAISES on every call (a constant bug), the warn fires every time = spam, and fail-loud is defeated (noise, not signal). Here `get_theme_agents` does `crew = get_crew_manifest(project_dir)` where `project_dir = _get_project_dir()` returns a **str**, but `get_crew_manifest` → `get_current_theme(root)` → `root / ".pennyfarthing"` requires a **Path** → `TypeError: unsupported operand type(s) for /: 'str' and 'str'` on EVERY call. So the new warn fires on every `/api/theme-agents` hit. WHY IT SLIPPED: TEA's `test_theme_agents_healthy_no_warning` PATCHED `get_crew_manifest` to return a dict — masking BOTH the str→TypeError constant bug AND a second bug (`get_crew_manifest` returns `list[CrewMember]` but the route checks `isinstance(crew, dict)` → always `{}`; CrewMember isn't even JSON-serializable → the panel has NEVER shown data). Contrast 160-15, where TEA's `test_*_healthy_returns_real_data` patched only the SEAM and asserted real data BACK, FORCING the wiring fix. REVIEWER DISCHARGE METHOD (do this for every fail-loud-sweep warn): don't trust the patched "healthy" test — run the REAL function: `PF_PROJECT_DIR=<repo> uv run python -c "from ...import get_theme_agents; import asyncio; print(asyncio.run(get_theme_agents()).body)"` and read for a warn / empty body. Also: the preflight subagent will SHOW the warn in `test_frame_routes.py` output but misclassify it as "the fix working" — it's the constant bug; verify yourself. Fix is small (pass `Path(project_dir)`), so route REJECT → red rework → TEA (TEA adds a real-path no-warn guard that drives the wiring fix; the dict/list serialization is a sibling bug to fold in or follow-up). Generalizes `poll-loop-warn-spam-and-the-constant-bug-trap`: when the warn's guarded call is patched-out in the "healthy" test, the constant-bug check was NEVER run — re-run it against the real callee.
</gotcha>

<gotcha name="narrowed-exception-rewrite-lets-new-class-escape" severity="critical">
When a fail-loud fix narrows a broad `except Exception` into typed catches, ENUMERATE the full raisable set of every guarded call before approving — the rewrite routinely converts a silent-drop bug into a crash bug for the exception class the author forgot. `Path.read_text()` raises OSError AND `UnicodeDecodeError` (a ValueError!); catching only OSError lets a non-UTF-8 file escape. Probe empirically, two ways: (1) `write_bytes(b"caf\xe9 \xff\xfe")` to a referenced input on the branch — does the entry point raise?; (2) same scenario with the file checked out from origin/develop — silent-drop there + raise on branch = REGRESSION introduced by the fix (HIGH, reject), not pre-existing debt. Also probe `chmod 0o000` (PermissionError hides inside `except OSError` while `exists()`-gated "not found" warnings stay silent — present-but-unreadable becomes invisible). This is lang-review python.md check #13 (fix-introduced regressions) made concrete. Story 160-4: tests covered YAML-syntax errors + scalars but not undecodable bytes; 150-green scoped suite missed it entirely.
</gotcha>

<gotcha name="jira-less-fallback-check-the-symmetric-op" severity="medium">
When a story adds a Jira-less (local-YAML) fallback to ONE operation, always check the SYMMETRIC/sibling operation in the same module — it usually still hits the network unconditionally and reproduces the exact bug being fixed. Story 158-5 gated `claim_issue` on `is_jira_enabled()` but `unclaim_issue` (same file) still calls `get_client()` directly → `pf sprint story claim --unclaim` stays broken on kanban-only projects. Capture as a non-blocking Delivery Finding (out of AC scope) rather than blocking, but ALWAYS name it — it's the highest-value gap a focused-on-the-diff review misses. Same lens applies to any add-a-local-path story: grep the module for other `get_client()`/network callers.
</gotcha>

<gotcha name="inline-fixture-vs-sharded-repo-transitively-covered" severity="low">
A claim/transition story's tests often use an INLINE-epic sprint YAML fixture while the real dogfood repo (orc-penny) is SHARDED (epics as string refs + `epic-*.yaml`). Don't reflexively block on "tests don't exercise sharded write-back" — if the new code reuses the production `transition_story` / `write_sprint` round-trip (read_sprint→find_story_in_data→mutate→write_sprint), the shard write-back is covered transitively by `test_156_1_*` and by transition_story being the live workflow path. Verify the reuse (not a reimplementation of YAML mutation), then rate it a LOW coverage-thinness note, not a bug. Story 158-5.
</gotcha>

<gotcha name="confidence-not-severity-on-edge-findings" severity="medium">
reviewer-edge-hunter/test-analyzer rate findings by CONFIDENCE (does it exist?), not SEVERITY (does it matter?). On a bugfix PR, an edge they rate "HIGH confidence" (e.g. 158-5: re-claiming your own already-in_progress story returns cryptic exit_code 3) is frequently a MEDIUM/LOW non-blocking UX wart — out-of-AC, loud failure, no corruption, and the pre-fix behavior also blocked. Confirm it (don't dismiss), downgrade severity with explicit rationale (judge by blast radius / can-it-reintroduce-the-bug), capture as a non-blocking Delivery Finding. Don't let a subagent's confidence score drive a reject.
</gotcha>

<gotcha name="subset-green-hides-regressions" severity="critical">
When a story changes the BEHAVIOR of a shared function, a Dev/preflight "GREEN" on a hand-picked subset of test files routinely misses regressions in OTHER callers. ALWAYS enumerate every caller of the changed symbol and run THEIR tests before trusting any GREEN: `grep -rln "<symbol_or_gate_type>" src/pf/tests/`, then run each file scoped. Story 158-3: the guard keyed on `gate_type == "sm_setup_exit"`; Dev + preflight ran `test_handoff_cli/e2e/108_2` (92 green) but never ran `test_143_9_tdd_cycle_e2e.py`, whose e2e `project` fixture seeds no `sprint/context/` and drives `complete_phase(..., "sm_setup_exit")` ~16 times → `16 failed, 41 passed`. The reviewer-test-analyzer subagent flagged it HIGH; I verified by running the file. A new mandatory precondition on a function invalidates every fixture that modeled the old precondition — find them by symbol search, not by trusting the author's regression list.
</gotcha>

<gotcha name="reproduce-preexisting-before-approving-red" severity="high">
If you APPROVE a PR while tests are still red, you MUST independently reproduce the "pre-existing" claim — never take Dev's word. Revert the change to `origin/develop` (`git checkout origin/develop -- <changed files>`), run the still-red tests, confirm they fail on clean develop, then restore (`git checkout HEAD -- <files>`). Only then is "pre-existing, out of scope" a defensible approval. This repo has NO CI, so develop genuinely carries stale failures — but "stale" must be PROVEN, not assumed. Story 158-3 Round 2: approved with 4 red verify-phase tests after reproducing `4 failed` on develop with the guard+fixture reverted (a `detect_workflow_state` bug in pf/prime/workflow.py, unrelated to the context gate). Pair this with scoping discipline: don't force the current story to absorb an unrelated module's bug.
</gotcha>

<gotcha name="manifest-overwrite-pattern" severity="high">
When `createManifest()` is called in update flows, it creates a FRESH manifest without preserving accumulated state fields. Trace what fields the old manifest carries and verify they survive the write-read-write cycle. Any field added to Manifest interface must also be preserved across `createManifest()` calls.
</gotcha>

<gotcha name="drop-in-reference-module-security-debt" severity="high">
When a story adopts a "drop-in" reference module pasted into an issue/spec, audit it for security debt the spec author skipped — mock-heavy tests and "it works live" verification both pass while CWE-class bugs slip through. Story 154-1's #17 reference module shipped: arbitrary-dir deletion via unsanitized `theme` in `clean()`→`rmtree` (CWE-22), `theme` path-traversal into cache paths, SSRF via trusting `manifest['base_url']` for the download URL (CWE-918), and unguarded dict keys that broke its own "never raises" contract. Always: sanitize any external string used in a `Path` join or URL; never trust a downloaded manifest's URLs (build from a hardcoded base); `tarfile filter="data"` is necessary-not-sufficient (it guards members, not the destination dir, and TypeErrors on Python <3.11.4).
</gotcha>

<gotcha name="test-claims-no-network-but-falls-through" severity="high">
A fixture docstring saying "no network — sentinel pre-seeded" only holds for tests that seed the sentinel. The "returns None when nothing cached" sibling test deliberately omits the sentinel, so a lazy `ensure_portraits()` inside the resolver falls through to a real `urlopen`. Check each test's setup individually against the lazy-download path — don't trust the fixture's blanket claim.
</gotcha>

<gotcha name="deletion-story-test-diffs" severity="medium">
When a story removes or absorbs a package, verify source→destination symbol parity by comparing original barrel exports with migrated barrel exports line-by-line. Glob may fail on symlinked directories — fall back to `ls` for verification.
</gotcha>

<gotcha name="false-green-guard-string-not-returncode" severity="high">
A test that runs another test runner in a subprocess and tries to prevent a false green by string-matching stdout (e.g. `assert "no tests ran" not in result.stdout`) is almost always vacuous — VERIFY the actual output/exit codes before trusting it. Empirically (story 153-9): pytest prints `"N deselected"` and exits **5** when `-k` matches nothing, exits **4** on collection/import error, and exits **0** only when tests actually ran and passed — it never prints "no tests ran" for the deselection case. So the only robust liveness check is `assert result.returncode == 0` (plus optionally `"passed" in stdout`). When a meta-test's whole job is to keep a regression alive, a guard that can't detect "zero tests ran" is a blocking defect, not a nit — the regression can silently stop guarding on a rename or broken import.
</gotcha>

<gotcha name="stale-local-develop-pollutes-diff" severity="high">
`git diff develop...HEAD` can show DOZENS of unrelated files (other merged stories' changes) when local `develop` is behind `origin/develop` — the merge-base is then an old commit. sm-setup cuts branches from `origin/develop`, so ALWAYS `git fetch origin develop` then diff `git diff origin/develop...HEAD` (verify `git merge-base origin/develop HEAD == origin/develop`). Story 158-2: local develop showed portrait_cdn/test_154/git_utils churn that wasn't in the branch at all.
</gotcha>

<gotcha name="delegation-widens-exposure-to-preexisting-resolver" severity="medium">
When a bugfix consolidates onto a SHARED resolver (story 155-3/gh #28: `archive_story` dropped its `\d{4}` regex and now calls `archive_epic.get_archive_path`), the security subagent will flag the shared resolver's lack of input sanitization (CWE-22 path-traversal via `str(name).split()[-1]` / `str(number)` interpolated into a `Path`). Two-part judgment: (1) LOCATION — the resolver is PRE-EXISTING (shipped in 151-1), NOT in this diff; the diff only *widened the caller's exposure* (regex-constrained → arbitrary token). That widening is real but is the CORRECT consolidation (SOUL #2); the right fix is to harden the resolver CENTRALLY in a follow-up so BOTH callers (story + epic archive) benefit — not to re-add a caller-local guard. (2) SEVERITY — sprint YAML is local, self-authored config: no trust boundary is crossed, so CWE-22 (an untrusted-input class) doesn't really apply; and the downstream `if not archive_file.exists(): return error` guard makes a typo'd/`/`-bearing name fail LOUD, not silently corrupt. So: CONFIRM (rule-matching #5/#11 — can't dismiss), DOWNGRADE to LOW, capture as a non-blocking Delivery Finding recommending a central `get_archive_path` hardening story (resolve()+containment + `re.fullmatch(r"[\w.-]+", sprint_id)` + `encoding="utf-8"` on the append). Do NOT block the consolidation. Same family as `severity-by-blast-radius-for-bugfix-PRs` and `confidence-not-severity-on-edge-findings`.
</gotcha>

<gotcha name="severity-by-blast-radius-for-bugfix-PRs">
When reviewing a fix FOR a data-loss/corruption bug, judge residual-finding severity by whether it REINTRODUCES the loss, not by the finding's intrinsic class. Failure modes that are loud (traceback + non-zero exit), benign (a missing cache vs the old clobber), or threat-model-inapplicable (CWE-59 needing pre-existing FS write on a single-user local tool) are MEDIUM/LOW even when a subagent rates them "high confidence" — confidence ≠ severity. Confirm them (don't dismiss, esp. rule-matching ones like python.md #5/#6), downgrade with explicit rationale, capture as non-blocking Delivery Findings. Story 158-2 approved with 13 such findings because none could reintroduce the gh #53 clobber.
</gotcha>

<gotcha name="loop-local-var-reused-across-iterations-stale-data" severity="medium">
When reviewing a "consolidate the double-read" cleanup inside a `for` loop, check whether the consolidated var was previously LEFT BOUND across iterations on the failure path — that's often a hidden stale-data leak worse than the advertised bug. Story 160-12 (ws_push.py `fetch_benchmark_history`): the original read `pipeline.yaml` twice with `pipeline_data` assigned inside `try`; on a malformed file the first `try/except: pass` left `pipeline_data` carrying the PREVIOUS run_dir's dict (Python loop vars persist across iterations), so that run rendered the prior run's date/tokens/duration. The advertised bug was only a first-iteration `NameError` (unbound on the very first run); the real teeth were cross-iteration contamination on every subsequent malformed run. The fix (`pipeline_data = None` reset at the top of each iteration + single read + `if pipeline_data:` consumers) closes both. Review lens: any loop body that assigns a var conditionally and reads it later without re-initializing it each iteration is a stale-carry suspect — trace the failure path, not just the happy path.
</gotcha>

<gotcha name="disabled-reviewer-subagents-shift-burden-to-you" severity="medium">
`pf settings get workflow.reviewer_subagents` can disable most specialists (160-12 review: only `preflight`+`security` enabled; `silent_failure_hunter`/`edge_hunter`/`test_analyzer`/`rule_checker` OFF). When the DISABLED ones cover the story's exact risk surface (here: silent-failure + exception taxonomy), you MUST do their analysis yourself — pre-fill their rows `Skipped | disabled` for the gate, but don't let "disabled" mean "uncovered". For a green-tests PR, the strongest self-check is the inverse of the rejected-RED probe: `git checkout origin/develop -- <changed source>` (keep the branch's NEW test file, which doesn't exist on develop), run the story tests, confirm they go RED (proves the tests actually bind to the fix, not green-for-wrong-reason — catches a Dev-fixed fixture bug masquerading as a valid RED), then `git checkout HEAD -- <source>`. 160-12: 10 failed / 3 passed on develop source = the 3 intentional green guards held, the 10 behavioral tests genuinely validate.

<gotcha name="poll-loop-warn-spam-and-the-constant-bug-trap" severity="high">
Reviewing a fail-loud sweep that ADDS `warnings.warn` to a long-lived POLL-LOOP fetcher (ws_push.py runs every 5s forever), the dominant new risk isn't a missed swallow — it's WARN-SPAM on a STEADY-STATE condition. For each new warn, trace whether the warned-on call RAISES on the COMMON case or RETURNS gracefully. Story 160-15 `fetch_context`: the genius/trap is that the pre-fix code did `ContextConfig(project_dir=...)` which raised `TypeError` on EVERY call (no such field) — a CONSTANT code bug hidden by the silent swallow, so the panel NEVER showed data. Adding a warn WITHOUT the wiring fix would have flooded stderr every poll. The correct fix is therefore root-cause (SOUL #1): repair the wiring (`check_context(project_dir=project_dir)` — verify the real fn RETURNS a result on the no-data path, e.g. `context_window.check_context` sets `result.error` and returns, never raises, on no-transcript/no-usage), THEN warn only on genuine exceptions. So: a fail-loud warn over a constant code bug is the spam trap; the wiring fix is what averts it. Verify by reading the warned-on function's no-data path for return-vs-raise — don't assume. Pairs with `disabled-reviewer-subagents-shift-burden-to-you` (160-12 AND 160-15 both ran only preflight+security ON — you do silent_failure/edge/test/rule yourself) and `narrowed-exception-rewrite-lets-new-class-escape` (here the broad `except Exception` was RIGHT to retain on the heterogeneous subprocess/attr/persona paths — narrowing risks a poll-loop crash; the read split routes through `_read_text_file` which catches `UnicodeDecodeError` explicitly so it can't escape). Inverse binding probe still the strongest green-PR check: revert source to origin/develop keeping the new test file → expect the behavioral tests RED + intentional guards green (160-15: 6 failed / 3 passed).
</gotcha>

<gotcha name="warn-spam-trap-averted-when-resolver-self-swallows" severity="medium">
160-16 (sweep part 3, data_proxy.py + ws_push.fetch_persona inner portrait resolver) is the COUNTER-example to 160-15's constant-bug trap — the warn-spam risk was genuinely ABSENT, and verifying that is the approval gate. The discharge method: for the AC-3 `fetch_persona` inner `resolve_portrait_path` warn, READ the resolver — `pf/tui/portrait_resolver.py::resolve_portrait_path` returns `None` on no-slug (the common case) AND wraps its CDN fetch in its OWN `try/except Exception: return None`, so it NEVER raises on the steady-state "offline / no portrait" path; it only raises on an abnormal `discover_all_theme_dirs`/`_extract_agent_slug` throw. So the new warn can't fire every 5s poll. Also: the warned call (`resolve_portrait_path(theme, agent_name, project_root=...)`) is PRE-EXISTING (unchanged try body), so unlike 160-15's freshly-surfaced broken `ContextConfig(...)` ctor, a constant failure here would already have broken the (working) portrait feature — another tell that it's not a constant bug. `_get_git_info` int-parse warn and `_get_repos_config` warn likewise fire only on present-but-broken inputs (early returns on missing git/.git/file). Dev KEPT the broad `except Exception` at all three (didn't narrow) — CORRECT per `narrowed-exception-rewrite-lets-new-class-escape` for these heterogeneous poll-loop paths. Security finding family (`{exc}`/`repo_path`/`agent_name` interpolated into the warn → low-sev info-leakage IF Frame ever forwards warnings to a network client): CONFIRM but NON-BLOCKING — it's the house style across the WHOLE 160-4/12/15/16 sweep, warnings route to stderr (not the API in-diff), and it's a local single-user daemon. Capture as a SERIES-WIDE Delivery Finding (sanitize the warnings sink before any network exposure), not a 160-16 blocker — per `severity-by-blast-radius-for-bugfix-PRs`. Subagent toggles AGAIN preflight+security-only (3rd sweep running, same config) → did silent_failure/edge/test/rule/type/simplify/comment myself; all clean.
