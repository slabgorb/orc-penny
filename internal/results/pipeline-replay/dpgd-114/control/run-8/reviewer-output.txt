### Devil's Advocate

What if a malicious plugin author submits a manifest with `PluginId::new("", "")` directly? The empty namespace and name would create a plugin that collides with the `":"` identity, potentially hijacking another plugin's registration slot. The `builtin("")` call is equally dangerous — it creates `builtin:` which could match any builtin plugin in a prefix-based lookup. Since `PluginId::new()` is `pub`, any code depending on `axiathon-plugin-sdk-core` can create these invalid IDs.

What if a plugin mutates its own manifest after registration? Since `PluginManifest.permissions` is `pub`, a plugin that receives `&mut` access to its manifest could add `"admin:all"` to its permissions vec, escalating privileges. Similarly, `manifest.signature = None` could clear the signature after verification, defeating the verification chain. This is only exploitable if the runtime passes `&mut PluginManifest` to plugins, which the current trait design doesn't — `manifest()` returns `&PluginManifest`. But any code holding the manifest by value (e.g., during registration) could mutate it.

What if `jsonschema::validate` is called with a crafted recursive JSON Schema? The `jsonschema` crate handles this via internal depth limits, but the error is mapped to `PluginError::ConfigInvalid` which is appropriate. The risk is denial-of-service, but this is bounded by the crate's implementation.

The lack of `#![forbid(unsafe_code)]` inheritance means a future contributor could add `unsafe` blocks to any SDK crate without compiler rejection. For a plugin SDK that will eventually load WASM code and manage sandboxing, this is a meaningful gap.
