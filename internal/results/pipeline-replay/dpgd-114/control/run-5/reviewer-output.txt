### Devil's Advocate

**Arguing this code is broken:**

The most concerning finding is the SSRF vector. Right now, `validate_config()` is the only code path that accepts attacker-influenced JSON (a plugin manifest's `config_schema` field). That JSON passes through `jsonschema::validate()` which by default uses `reqwest::blocking::get()` to resolve any `$ref` URI. A malicious plugin author — or anyone who can modify a manifest before it reaches `validate_config` — can trigger outbound HTTP requests to arbitrary hosts from the Axiathon server.

Scenario: An operator loads a community plugin with `config_schema: {"$ref": "http://169.254.169.254/latest/meta-data/iam/security-credentials/"}`. The `validate_config` call fetches AWS instance metadata credentials. The response gets embedded in the jsonschema error if validation fails, which flows into `PluginError::ConfigInvalid(e.to_string())` and potentially into logs or API responses. This is a complete SSRF-to-credential-theft chain that works today with zero exploitation difficulty.

The missing `#[non_exhaustive]` on `PluginKind`, `PluginHealth`, and `PluginError` means any downstream crate that exhaustively matches these enums will break when we add variants in Stories 23.2+. This is explicitly required by `.claude/rules/rust.md`: "*`#[non_exhaustive]` on enums that will grow*". All three enums will grow — `PluginKind` when new plugin types are added, `PluginHealth` may gain states like `Starting`/`Stopping`, and `PluginError` will gain variants for WASM/registry errors.

The `PluginId::new("", "")` inconsistency creates an invariant violation: `FromStr` rejects empty parts, but `new()` accepts them. Any code that round-trips through Display+FromStr will break: `PluginId::new("", "x").to_string().parse::<PluginId>()` yields `Err("invalid plugin id ':x': expected 'namespace:name'")`. This means the type's own serialization is not self-consistent.

The `validate_config` error mapping conflates two distinct failure modes: (1) the schema itself is malformed (developer error, should be `ManifestInvalid`) and (2) the config doesn't match the schema (user error, should be `ConfigInvalid`). Using `jsonschema::validate()` as a one-liner merges both into `ConfigInvalid`, which means an operator debugging a broken manifest gets told their config is wrong when the schema is wrong.
