### Devil's Advocate

Let me argue this code is broken.

**The PluginId invariant hole is real and exploitable by plugin authors.** `PluginId::new("", "")` creates a plugin ID that displays as `:` — the exact format `FromStr` rejects. If the plugin runtime (Story 23.2) uses PluginId as a HashMap key, `PluginId::new("", "test")` and `PluginId::new("builtin", "test")` would be different keys despite both being "valid" in different contexts. A malicious or confused plugin author could register a plugin with namespace="" and name matching a builtin plugin's name, creating a shadow registration that bypasses namespace-based policy checks. The `builtin()` and `community()` helpers are safe, but `new()` is public and unchecked.

However — this is MEDIUM severity, not HIGH. The plugin runtime (Story 23.2) will manage registration and can validate IDs at the registry boundary. The SDK is an internal API; plugin authors use `builtin()`/`community()` helpers or parse from string. Direct `new()` calls happen in test code and internal wiring. The fix is simple (validate in `new()` or make fields private), but it doesn't block this PR.

**The `RawEvent.tenant_id` field is publicly mutable.** An enricher receives `&mut AxiathonEvent` and could theoretically swap out the `tenant_id` field, causing cross-tenant data leakage. But the AxiathonEvent type is a placeholder (Story 1.21), and enrichers work on events that have already been assigned to a tenant by the connector → parser pipeline. The real fix is private fields with getters on AxiathonEvent when it becomes the proto-backed type in Story 2.16.

**The `as_str()` method on RawEvent returns an owned String, not a borrowed &str.** The naming convention per Rust API guidelines is that `as_*` methods should be cheap borrowing operations, while `to_*` methods indicate allocation. This allocates via `to_string()`. It should be `to_str()` or `to_string_lossy()`.

**What if config_schema contains a `$ref` to an external URL?** The jsonschema crate's default configuration may fetch external schemas, which could be a SSRF vector if a plugin manifest is loaded from an untrusted source. However, the SDK doesn't load manifests from untrusted sources — manifests are compiled into plugin binaries. The risk is deferred to Story 23.6 (Plugin Packaging) when manifests come from .axpkg files.

None of these issues are Critical or High severity blockers.
