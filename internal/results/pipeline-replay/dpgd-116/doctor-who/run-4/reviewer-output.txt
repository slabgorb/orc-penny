# Adversarial Code Review: Story 6.1 — CLI Framework & Structure

## Findings

### `[CRITICAL]` Timestamp format is NOT ISO 8601/RFC 3339 — `output.rs:119-124`

The `chrono_now()` function produces `"1741564800Z"` — raw epoch seconds with a Z suffix. This is **not** a valid RFC 3339 timestamp. AC-4 specifies `ResponseMetadata` with a `timestamp` field, and any consuming system expecting `"2026-03-09T12:00:00Z"` will choke on this. The comment on line 118 even says "Returns an ISO 8601 timestamp string" — the comment is a lie.

The test at `output_formatting.rs:133-138` only checks `!meta.timestamp.is_empty()` — a vacuous assertion that passes for any non-empty string, including `"potato"`.

**Fix:** Use `chrono::Utc::now().to_rfc3339()` (chrono is already a workspace dependency) or format `SystemTime` properly.

---

### `[CRITICAL]` Workspace lint safety override — `Cargo.toml:37-44` vs root `Cargo.toml:81-82`

The workspace root sets `unsafe_code = "forbid"` (line 82). The `axiathon-client` crate **overrides this** to `unsafe_code = "warn"` (line 44) and does NOT use `lints.workspace = true`. The comment on line 34 explains this is to allow `unsafe { std::env::set_var }` in tests.

This is a **security architecture violation**. The `forbid` at workspace level exists as a hard safety guarantee. Downgrading it to `warn` in the crate's `[lints.rust]` means production code in this crate can now use `unsafe` and only get a warning. The `#![forbid(unsafe_code)]` in `lib.rs` and `main.rs` provides protection for production code, but the crate-level lint override weakens the safety net unnecessarily.

**Fix:** Use `lints.workspace = true` and annotate only the specific test functions with `#[allow(unsafe_code)]` using `#[cfg(test)]` scoping, or move the env var tests into a separate test binary that has its own lint config.

---

### `[HIGH]` Tests accept both pass AND fail — false-pass risk — `cli_framework.rs:280-297, 299-317`

Two security tests use the pattern `if let Ok(cli) = result { ... }` without asserting whether the result SHOULD be `Ok` or `Err`. This means:

- `server_url_rejects_newlines` (line 280): If clap accepts `"https://example.com\r\nX-Injected: true"` and the validator doesn't fire, the test **silently passes** because the `if let Ok` branch does the assertion, but if clap rejects it, the test also passes with no assertion at all. The test proves nothing definitively.

- `tenant_flag_rejects_non_uuid` (line 299): Same pattern — `if let Ok(cli) = result { assert UUID valid }`. If clap rejects the XSS payload, the test passes without verifying WHY it was rejected.

**Fix:** These tests must assert a specific outcome:
```rust
assert!(result.is_err(), "clap must reject CRLF in --server");
```

---

### `[HIGH]` `siem_client_rejects_token_with_crlf` test is vacuous — `siem_client.rs:254-277`

The CRLF header injection test has:
```rust
match result {
    Err(_) => {} // good, rejected
    Ok(_) => {
        // If it succeeded, verify no injection occurred
        // (wiremock would not match the injected header)
    }
}
```

Both arms are no-ops. This test literally cannot fail. A `match { _ => {} }` is not an assertion. The wiremock mock on line 258-262 responds 200 to any GET, so even if the CRLF token passes through, the response succeeds and the `Ok` arm does nothing.

**Fix:** Assert `result.is_err()` — reqwest's `HeaderValue::from_str` rejects CRLF, so this should always error. Or if you want to verify it defensively, at minimum assert something in the `Ok` arm.

---

### `[HIGH]` CWE-209: `ServerError(String)` passes arbitrary server text to user — `error.rs:8-9`

The `Display` impl for `ServerError` is `#[error("server error: {0}")]` — it forwards whatever string is inside directly to the user. In `client.rs:73`, reqwest error `.to_string()` is passed in, which can include internal URLs, DNS resolution details, connection specifics. At `client.rs:83`, raw JSON parse failure details are forwarded. The SECURITY comment on line 3-4 says "Do not expose internal server details" but the implementation does exactly that.

**Fix:** Sanitize the error message before storing in `ServerError`, or at minimum don't forward raw reqwest error strings. Map to generic user-facing messages.

### `[MEDIUM]` `_format` field stored but never read — `output.rs:63`

**Fix:** This is explicitly called out in the technical guardrails as a requirement for this story. Add TTY detection logic.
