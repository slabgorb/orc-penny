# Story 6.1 Code Review — Miss Marple's Report

*Well now, I've seen every type of poorly-structured CLI in St. Mary Mead, and this one is... rather more competent than most. But competence is where the truly interesting problems hide, isn't it? Let me share what my village network has uncovered.*

## Review Findings

### [HIGH] Missing `main.rs` binary entry point — no executable binary produced

There is no `main.rs` in `crates/axiathon-client/src/`. The story requires producing an `axiathon` binary. Without a binary entry point with `fn main()`, there is no CLI binary, no exit-code dispatch, no tracing initialization, and no `std::process::exit()` call. This is the most fundamental deliverable of Story 6.1.

**Impact:** The entire AC-3 exit code flow (errors → stderr, `std::process::exit()`) is untestable in integration. The crate compiles only as a library, not a binary.

---

### [HIGH] `CliError::ServerError` Display leaks internal details (CWE-209)

At `error.rs:7`, `ServerError(String)` uses `#[error("server error occurred")]` — which is correct and does NOT display the inner string. However, the inner `String` is still accessible via `Debug`. The test at `error_exit_codes.rs:121` passes only because `Display` is tested, but the `Debug` format `ServerError("database connection pool exhausted at 10.0.0.5:5432")` WILL leak if any error handler logs with `{:?}` format (which is standard practice with `tracing::error!("{err:?}")`). The `/// **SECURITY:**` comment on the error type acknowledges this concern but the inner string is still stored unredacted in the variant.

More critically: `SiemClient::get()` at `client.rs:57` creates `ServerError("request failed".into())` — this is fine. But when the `get` method maps deserialization errors at line `client.rs:65`, it uses a generic `"invalid response"` string, losing the actual error context that developers need for debugging while also not leaking. This is a design tension worth noting.

---

### [MEDIUM] Workspace `Cargo.toml` missing Story 6.1 dependencies

The story specifies adding `reqwest`, `comfy-table`, `keyring`, `clap_complete`, `dirs`, `csv`, and `toml` to `[workspace.dependencies]`. The current workspace `Cargo.toml` has **none** of these — they are declared only as direct dependencies in the crate's `Cargo.toml`. This violates the workspace dependency management pattern established by the project (all other deps like `tokio`, `serde`, `clap` use workspace-level declarations). The `toml` version in the crate is `0.8` but the story specifies `0.9`.

---

### [MEDIUM] `OutputFormatter` is a concrete struct, not a trait as specified

AC-4 and the story context specify an `OutputFormatter` **trait** with Table/Json/Csv implementations. The actual code at `output.rs:24` implements `OutputFormatter` as a concrete struct with a format enum field. This means future command modules cannot provide custom formatting behavior — they must go through the single struct. The story explicitly says "OutputFormatter trait with Table (comfy-table), JSON (serde_json + metadata), CSV (csv crate) implementations."

---

### [MEDIUM] No TTY auto-detection for output format

AC-4 states: "Table default for TTY, JSON for piped output." The implementation uses `std::io::IsTerminal` nowhere in the codebase. The default is always `Table` regardless of whether stdout is a TTY or piped. This means scripting use cases (`axiathon status | jq .`) will get table output instead of JSON, breaking scriptability.

---

### [MEDIUM] `config.rs` silently ignores unparseable `AXIATHON_TIMEOUT` values

At `config.rs:39-42`, if `AXIATHON_TIMEOUT` is set to a non-numeric value (e.g., `"thirty"`), the code silently falls back to the file/default value with no warning. An operator debugging timeout issues would have no indication their env var is being ignored. This is a silent failure pattern.

---

### [MEDIUM] `CompletionArgs.shell` is `Option<String>` instead of `clap_complete::Shell`

At `cli.rs:179`, the shell argument is an `Option<String>`. This means clap won't validate shell names at parse time — an invalid shell like `axiathon completion nushell` would parse successfully, deferring the error to runtime. Using `Shell` as the type would give free validation and help text from clap.

---

## Verdict: **CHANGES_REQUESTED**

The two HIGH findings block approval:

1. **No `main.rs`** — the story's primary deliverable is a binary. Without it, there is no CLI.
2. **`ServerError` inner string leakage risk** — the `Debug` impl exposes internal details stored in the variant. Either redact the inner string in `Debug` or don't store raw internal details in it.

The MEDIUM findings (missing workspace deps, no trait for OutputFormatter, no TTY detection, silent env var failures, nightly fmt) should also be addressed but are not individually blocking. The nightly fmt failure in particular is flagged per the reviewer gotchas — it must pass before merge.
