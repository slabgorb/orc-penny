## Findings

### `[HIGH]` Nightly `rustfmt` fails — import ordering violations at `cli.rs:3-4`, `client.rs:3`

Per the gotchas sidecar: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not."* The nightly formatter shows diffs in `cli.rs` (crate imports before std) and `client.rs` (crate imports before external). This blocks approval per project rules.

### `[HIGH]` AC-4 violated: No TTY auto-detection for default output format

AC-4 requires *"Table default for TTY, JSON for piped output. Use `std::io::IsTerminal`."* The `Cli.format` is `Option<OutputFormat>` but there is **zero code** that defaults to `Table` for TTY vs `Json` for piped output. `std::io::IsTerminal` is never imported or used anywhere in the crate. The `OutputFormatter` struct exists but has no auto-detection. No test covers this behavior.

### `[HIGH]` AC-5 violated: `--server` flag missing `AXIATHON_SERVER` env var support

AC-5 states *"`--server` supports `AXIATHON_SERVER` env var."* The `--server` arg in `cli.rs:28` has no `env = "AXIATHON_SERVER"` attribute. While `config.rs` supports `AXIATHON_API_URL`, the AC explicitly calls out `AXIATHON_SERVER` for the `--server` CLI flag. These are different integration points.

### `[MEDIUM]` AC-2 gap: No `after_help` usage examples on any command group

AC-2 requires *"include `after_help` usage examples for each command group."* None of the `Commands` enum variants or subcommand enums have `#[command(after_help = "...")]` attributes. Help renders without panic (tested), but the required example sections are missing.

### `[MEDIUM]` AC-9 gap: Shell completion sends no installation instructions to stderr

AC-9 states *"Script to stdout, installation instructions to stderr."* `completion.rs` generates the script but prints nothing to stderr. In `main.rs:30`, the script is `print!`-ed to stdout but no `eprintln!` with install instructions exists.

### `[MEDIUM]` AC-4 gap: `OutputFormatter` is a struct, not a trait

The story spec and AC-4 explicitly call for an *"`OutputFormatter` trait with Table/JSON/CSV implementations."* The implementation uses a concrete struct with methods. This prevents downstream command handlers from abstracting over output formatting or providing custom formatters.

### `[MEDIUM]` `SiemClient` timeout config never wired to HTTP client at `client.rs:21`

`ClientConfig.timeout_secs()` exists and is tested, but `reqwest::Client::new()` at `client.rs:21` has no timeout configured. The AC-7 mapping says *"timeout -> ConnectionTimeout"*, and the error variant exists, but without a timeout set on the client, the `is_timeout()` branch at `client.rs:71` can never trigger in practice (reqwest's default is no timeout).

### `[MEDIUM]` Header injection test is vacuous at `security_integration.rs:59-78`

`siem_client_rejects_newline_in_token` accepts `CliError::Config`, `CliError::ServerUnavailable`, **and** a catch-all `Err(other)` arm. This means the test passes for *any* error, making it impossible to fail. A proper assertion would require specifically `CliError::Config` to verify the injection check at `client.rs:50-51` actually triggered.

### `[MEDIUM]` `toml` dependency version mismatch — workspace declares `0.8`, story spec requires `0.9`

`Cargo.toml:54` specifies `toml = "0.8"`. The story technical guardrails specify `toml` 0.9. This may cause issues if 0.9 features are needed later.

### `[LOW]` `SiemClient::get` URL path joining is fragile at `client.rs:60`

`format!("{}{path}", self.base_url)` relies on `path` starting with `/`. If it doesn't, the URL is malformed (`http://example.comapi/v1/status`). No validation exists. Tests always pass paths with leading `/`, masking this.

### `[LOW]` Stub story references are vague — `rules.rs:4` says `"6"`, `tenant.rs:4` says `"6"`

AC-10 says stubs print *"not yet implemented (Story X.Y)"*. `rules.rs` and `tenant.rs` use `"6"` instead of specific story numbers. The test `assert_stub_not_implemented(&err, "6")` passes because `"6"` contains `"6"`, but this would also match `"6.2"`, `"6.3"`, etc. — the assertion is too permissive.

### `[VERIFIED]` `#![forbid(unsafe_code)]` on both `main.rs:1` and `lib.rs:2` — production code protected

The crate-level `[lints.rust] unsafe_code = "allow"` is necessary for test `set_var`/`remove_var` in Rust 2024 edition, and the file-level `forbid` in production modules compensates correctly.

### `[VERIFIED]` `#[serde(deny_unknown_fields)]` on `ConfigFile` at `config.rs:12` — rejects token/password fields in TOML

### `[VERIFIED]` `CliError` is `#[non_exhaustive]` at `error.rs:11` — future-proof per Rust rules

### `[VERIFIED]` Header injection validation present at `client.rs:49-57` — checks `\r` and `\n` before sending request
