## Findings

### [HIGH] F1 — Workspace `unsafe_code` downgraded from `forbid` to `deny` at `Cargo.toml:65-67`

The root workspace lint was `unsafe_code = "forbid"` and this PR changes it to `"deny"` to allow test files to `#![allow(unsafe_code)]` for env var manipulation. This weakens the safety guarantee for **every crate in the workspace**, not just `axiathon-client`. Any crate can now `#[allow(unsafe_code)]` in production code. The correct fix is to keep `forbid` at the workspace level and use `#[cfg(test)]` blocks with `unsafe` only where needed, or use a test helper crate that's allowed unsafe. Alternatively, avoid `set_var`/`remove_var` entirely by using `temp_env` or similar test utilities that don't require unsafe.

### [HIGH] F2 — Missing `main.rs` binary entry point

The story explicitly requires "the `axiathon-client` crate producing the `axiathon` binary" with `main.rs` handling tracing init, dispatch, exit codes via `std::process::exit()`. No `main.rs` exists. The crate is library-only. AC-3 exit code behavior is untestable end-to-end without it.

### [HIGH] F3 — Missing `logout` and `tui` commands per AC-1

AC-1 states: `axiathon --help` must show `login`/`logout`, `tui`, `completion`, `init`. The `Commands` enum has no `Logout` or `Tui` variant. The top-level help test (`top_level_help_lists_all_command_groups`) does not assert for `logout` or `tui`, masking the gap.

### [HIGH] F4 — `init` command is an empty struct, not functional

AC says `init` and `completion` should be functional, not stubs. `completion` is properly implemented with `generate_completion()`. But `InitArgs` at `commands/init.rs:3` is just an empty struct with no handler — there's no `handle_init()` function, no first-time setup logic, no config directory creation.

### [HIGH] F5 — Nightly fmt check fails

Per `gotchas.md`: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval." It fails with diffs in `client.rs` and `output.rs`. This blocks approval.

### [MEDIUM] F6 — `--server` flag missing `env = "AXIATHON_SERVER"` per AC-5

AC-5 says: "`--server` supports `AXIATHON_SERVER` env var." The clap arg at `cli.rs:25` has no `env = "AXIATHON_SERVER"` attribute. Operators setting this env var will be ignored.

### [MEDIUM] F7 — `AXIATHON_TIMEOUT` env var parse failure is silent at `config.rs:67-68`

```rust
let timeout = std::env::var("AXIATHON_TIMEOUT")
    .ok()
    .and_then(|v| v.parse::<u64>().ok())  // silently drops "30s", "-1", "abc"
```

If an operator sets `AXIATHON_TIMEOUT=30s`, the parse fails silently and falls through to file/default value. This should at minimum log a warning, or return a `ConfigError`.

### [MEDIUM] F8 — `ServerError` display leaks up to 200 chars of server response body (CWE-209)

At `client.rs:104-110`, server 5xx responses have their body truncated to 200 chars and stored in `CliError::ServerError`. The Display impl at `error.rs:24` prints this directly: `server error ({0}): {1}`. Server error bodies may contain internal paths, DB schemas, or stack traces. The SECURITY comment on the error type says "avoid leaking internal implementation details" but the code does exactly that.

### [MEDIUM] F9 — Missing workspace-level dependency declarations

Story spec says to add `reqwest`, `comfy-table`, `keyring`, `clap_complete`, `dirs`, `csv`, `toml` to `[workspace.dependencies]`. Instead, `clap_complete`, `comfy-table`, `csv`, `dirs`, `reqwest`, and `toml` are declared directly in `crates/axiathon-client/Cargo.toml` with pinned versions, bypassing workspace dependency management. This creates version drift risk as more crates adopt these deps.

### [MEDIUM] F10 — `keyring` dependency completely absent

AC-7/AC-8 specify OS keychain via `keyring` crate for credential storage. It's not in `Cargo.toml` at all. `SiemClient::from_env()` only reads `AXIATHON_API_TOKEN` env var — there's no keychain integration path.

### [MEDIUM] F11 — Missing `after_help` usage examples per AC-2

AC-2 requires "include `after_help` usage examples for each command group." None of the command structs have `#[command(after_help = "...")]` attributes.

### [MEDIUM] F12 — `RawConfig` silently ignores unknown fields at `config.rs:16`

`#[serde(default)]` without `#[serde(deny_unknown_fields)]` means typos like `sever_url` or `timeot` are silently ignored. The security test at `security.rs:146-154` passes `api_token` and `token` fields — both silently dropped. While token-ignoring is correct, the lack of any unknown-field handling means operators won't discover config typos.

### [LOW] F13 — `ResponseMetadata` uses UUID v4 instead of v7

Project convention in `rust.md` says "UUID v7 for time-ordered IDs." `ResponseMetadata::new()` at `output.rs:21` uses `Uuid::new_v4()`. Request IDs should be time-sortable for log correlation.

### [LOW] F14 — `ClientConfig::has_token()` always returns `false`

At `config.rs:87-89`, `has_token()` unconditionally returns `false`. While the intent is correct (config doesn't store tokens), the method name is misleading — it reads like "does the system have a token" but only answers "did the config file contain a token." Consider removing this method or renaming to clarify scope.

### [VERIFIED] V1 — Header injection prevention is correctly implemented

`sanitize_header_value()` at `client.rs:16-18` strips `\r` and `\n` from header values. Applied to both token and tenant in `with_token()` and `with_tenant()`. Tests at `security.rs:72-98` verify this. Good.

All `CliError` variants map to valid exit codes {1, 3, 4}. Tests cover every variant. `#[non_exhaustive]` on the enum ensures future variants require wildcard arms.

`RawConfig` has no token field. Tests verify tokens in TOML files are silently ignored. Correct — tokens belong in keychain or env var.
