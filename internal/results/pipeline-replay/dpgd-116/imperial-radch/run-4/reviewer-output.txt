# Story 6.1 — Adversarial Code Review

## Observations

### [HIGH] Missing `logout` and `tui` command groups — AC-1 violation at `cli.rs:49-90`

AC-1 explicitly requires: *"`axiathon --help` must show all command groups: `query`, `rules`, `alerts`, `ingest`, `config`, `status`, `tenant`, `login`/`logout`, `tui`, `completion`, `init`."* The `Commands` enum has no `Logout` variant and no `Tui` variant. This is a direct AC violation. Even as stubs, they must exist. The test `cli_help_lists_all_command_groups` at `cli_framework.rs:96-108` also does **not** assert `logout` or `tui`, making the test complicit in the gap.

### [HIGH] `ServerError` Display silently swallows diagnostic context — CWE-209 overcorrection at `error.rs:15-16`

`#[error("server error")]` discards the `String` payload entirely. When an operator sees "Error: server error" on stderr, they have zero diagnostic information — no hint about whether it was a 500, 502, or 503, no request ID, nothing actionable. The SECURITY comment says "do not relay raw internal error strings," but the current implementation goes too far: it gives **no** information. The `ServerError(String)` payload is dead data that exists but is never shown. At minimum, the status code class (e.g., "server error (5xx)") should be surfaced without the body. Alternatively, log the detail at `-vv` and show the generic message at default verbosity.

### [MEDIUM] `NotFound` Display leaks HTTP response body to operator — CWE-209 at `error.rs:18-19`

`#[error("not found: {0}")]` formats the raw body string from `map_status_error(404, body)`. The HTTP response body from the server could contain internal paths, stack traces, or server software versions. This contradicts the SECURITY doc comment on the same file. If `ServerError` suppresses, `NotFound` should too — or both should apply consistent sanitization.

### [HIGH] `RawConfig` silently ignores unknown TOML fields — config safety at `config.rs:11-18`

`RawConfig` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. A typo like `api_rul = "..."` or `timeotu = 60` is silently ignored and the operator gets defaults without any warning. For a security tool's config file, silent config misapplication is dangerous — an operator thinks they've set a timeout of 120s but a typo means they got the 30s default. This should either deny unknown fields or warn on stderr.

### [MEDIUM] `nightly fmt` check fails — formatting violation at `tests/siem_client.rs:27-29,131-132`

`cargo +nightly fmt --all --check` reports diffs in `siem_client.rs`. Per `gotchas.md`, nightly fmt must pass before approval. This is a pre-merge gate failure.

### [MEDIUM] `toml` version mismatch — workspace declares `0.8`, story spec says `0.9` at `Cargo.toml:50`

The story's Technical Guardrails section specifies `toml 0.9`. The workspace declares `toml = "0.8"`. This may be intentional if 0.9 isn't released yet, but it should be documented or the story spec updated.

### [MEDIUM] `handle_init` is silent on success — UX gap at `commands/init.rs:6-20`

`handle_init()` creates the config directory and writes the default file but prints **nothing** on success. An operator running `axiathon init` sees zero output and no confirmation. The story says this should be "functional, not stub." A functional init command should tell the operator what it did (e.g., "Created ~/.config/axiathon/cli.toml").

### [MEDIUM] TOCTOU race in `handle_init` — `init.rs:12-18`

`config_path.exists()` check followed by `fs::write()` is a classic TOCTOU race. In practice, for a single-user CLI init command, the blast radius is low (overwriting a just-created config), but the pattern is wrong. Should use `OpenOptions::new().create_new(true)` or at minimum document the limitation.

### [LOW] `output.rs` uses `expect()` in four places — production code at `output.rs:64,69,73,74`

The rust rules say "No `unwrap()` in production code — use `?` or `expect()` with actionable message." These `expect()` calls have messages, so they technically comply, but `format_as_csv` and `format_as_json` could return `Result` instead. If CSV writing fails on, say, a broken pipe, these will panic instead of returning a clean error. For a CLI that may have stdout piped, this matters.

### [LOW] `OutputFormatter` is a struct, not a trait — AC-4 mismatch at `output.rs:15`

AC-4 specifies "the `OutputFormatter` trait provides consistent formatting." The implementation uses a concrete struct, not a trait. This works but doesn't match the architectural intent. Future command implementations that need custom formatting would need to depend on this concrete struct rather than a trait object.

### [LOW] `main.rs` never loads config, never constructs `SiemClient`, never reads keychain at `main.rs:9-29`

The `run()` function parses CLI args and dispatches to stubs, but never wires up the `ClientConfig` or `SiemClient`. Global flags like `--server`, `--tenant`, `--config` are parsed but never used. This is acceptable for stubs, but the wiring gap means **none** of the config→client→command data flow is actually tested end-to-end. The `SiemClient` and `ClientConfig` are tested in isolation but never together.

### [VERIFIED] CWE-113 header injection prevention — `client.rs:25-42`

CRLF injection in `with_token()` and `with_tenant()` is correctly rejected. Tests verify this at `siem_client.rs:117-138`.

### [VERIFIED] `#[non_exhaustive]` on `CliError` — `error.rs:13`

Present and tested at `exit_codes.rs:98-116`.

### [VERIFIED] `#![forbid(unsafe_code)]` — `lib.rs:2`, `main.rs:2`

Both lib and binary entry points forbid unsafe code.

### [VERIFIED] Plural command names (`rules`, `alerts`) — `cli.rs:57,59`

Correctly uses plural nouns per architecture doc. Negative tests at `cli_framework.rs:76-85` confirm singular forms are rejected.

### [VERIFIED] Exit code mapping — `error.rs:47-53`

All exit codes map correctly: 3 for auth, 4 for authz, 1 for everything else. Comprehensive tests in `exit_codes.rs`.

### [VERIFIED] Token excluded from config — `config.rs:103-105`

`token()` always returns `None`. Test at `config_loading.rs:183-195` verifies tokens in TOML are ignored.

### [VERIFIED] Shell completion generation — `completion.rs:12-15`

Functional (not stub) as required. All four shells tested.
