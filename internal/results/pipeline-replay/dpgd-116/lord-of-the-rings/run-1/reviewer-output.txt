## Findings

### [CRITICAL] Missing `main.rs` binary entry point — `config.rs:1`, `cli.rs:1`

AC-1 through AC-10 require a functional `axiathon` binary. The story spec explicitly calls for `main.rs` with tracing init, dispatch, and exit code handling via `std::process::exit()`. No `main.rs` exists. No `[[bin]]` section in `Cargo.toml`. This crate produces **no binary** — only a library. The entire story deliverable (an operator-facing CLI binary) is unachievable without this file. Every AC that says "axiathon --help must..." or "exit with code X" is structurally untestable in production form.

### [CRITICAL] `with_token()` and `with_tenant()` bypass header injection validation — `client.rs:47-50`, `client.rs:68-71`

`SiemClient` provides both `with_token()`/`with_tenant()` (no validation) and `try_with_token()`/`try_with_tenant()` (validates for `\n`/`\r`). The non-validating methods are `pub` and accept arbitrary strings including newline characters. There is **nothing** preventing production code from calling `with_token("evil\r\nX-Injected: true")` and succeeding. The safe API is opt-in, the unsafe API is the easier path. This is CWE-113 (HTTP header injection) waiting to happen. Either remove the non-validating methods or make them `pub(crate)` at minimum.

### [HIGH] Missing `logout` and `tui` command groups per AC-1 — `cli.rs:49-71`

AC-1 explicitly requires: "query, rules, alerts, ingest, config, status, tenant, **login/logout**, **tui**, completion, init". The `Commands` enum has no `Logout` or `Tui` variant. The help text test at `cli_structure_test.rs:83-94` conveniently omits both from the `required_groups` array, masking the gap. The story scope says "TUI mode implementation" is out of scope, but the **command group stub** (which would print "not yet implemented") is in scope per AC-1 and AC-10.

### [HIGH] `toml` version mismatch: workspace has `0.8`, story spec requires `0.9` — `Cargo.toml:49`

The story technical guardrails specify `toml 0.9`. The workspace declares `toml = "0.8"`. While functionally acceptable today, this is a direct deviation from the architectural specification.

### [HIGH] Nightly `rustfmt` check fails — `cli.rs:5-8`, `client.rs:41`, multiple command files

Per the reviewer gotchas (`gotchas.md`): "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval." The check fails with import reordering diffs in `cli.rs`, formatting diffs in `client.rs`, and long attribute lines in multiple command files. This is a blocking finding per project policy.

### [HIGH] `ConfigFile` silently accepts unknown fields — `config.rs:10-24`

The `ConfigFile` and `ServerConfig` structs use `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. A config file with typos like `[servr]` or `timout = 30` will be silently ignored, falling through to defaults. Operators will believe their config is applied when it's not. This is a classic misconfiguration trap. The token field silently being ignored (line 22-23) compounds this — an operator who puts `token = "..."` in their config gets no warning that it's ignored.

### [HIGH] `--server` flag missing `env = "AXIATHON_SERVER"` attribute — `cli.rs:29-30`

AC-5 states: "`--server` supports `AXIATHON_SERVER` env var." The clap attribute on the `server` field has no `env = "AXIATHON_SERVER"` annotation. The env var fallback exists only for `AXIATHON_API_URL` in `config.rs`, which is a different var name and a different layer of the precedence chain.

### [MEDIUM] `format_as_json` uses `expect()` in production code — `output.rs:90`

`serde_json::to_string_pretty(&output).expect("JSON serialization should not fail")` — the Rust coding rules state: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect` message is explanatory but not actionable. More importantly, `format_table` returns `String` not `Result`, so error propagation is impossible. The CSV formatter at lines 95-100 has four `expect()` calls with the same issue.

### [MEDIUM] `generate_completions` silently returns empty string for invalid shells — `completion.rs:44`

An invalid shell name returns `String::new()` silently. The clap enum `ShellType` prevents this at the CLI level, but the `generate_completions` function takes a raw `&str`, so it's possible to call with an invalid shell from tests or other code. This should return a `Result<String, CliError>`.

### [MEDIUM] Config env var override for `AXIATHON_API_URL` skips URL validation — `config.rs:99-101`

The file-loaded URL is validated against `http://`/`https://` prefix at line 92-96. But when `AXIATHON_API_URL` overrides at line 99-101, the override value replaces `server_url` **after** validation, so an env var like `AXIATHON_API_URL=ftp://evil` bypasses the URL scheme check.

### [MEDIUM] `keyring` crate missing from workspace dependencies — `Cargo.toml`

While the actual keyring integration is for Story 9.1, the `SiemClient` token loading architecture (AC-7, AC-8) is designed around keyring being available.

### [MEDIUM] `init` command has no implementation — `init.rs:1-7`

The `init.rs` file contains only the `InitArgs` struct with no handler function at all — not even a stub. Completion is functional; init is neither functional nor stubbed.

### [LOW] Config permission check uses 0o044 mask which catches group-readable too — `config.rs:59`
