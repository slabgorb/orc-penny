## Findings

### [HIGH] Nightly rustfmt check fails — `stub_handlers.rs:111-125`

`cargo +nightly fmt --all --check` reports a formatting diff in `crates/axiathon-client/tests/stub_handlers.rs`. Per gotchas.md, nightly fmt must pass before approval. This is a blocking finding.

### [HIGH] Missing `logout` and `tui` command groups — `cli.rs:44-119`

AC-1 explicitly requires `axiathon --help` to show `login`/`logout` and `tui` command groups. The `Commands` enum has `Login` but is missing `Logout` and `Tui` variants entirely. The help output will not satisfy AC-1.

### [HIGH] Config silently accepts unknown fields — `config.rs:15-22`

`RawConfig` uses `#[serde(default)]` without `#[serde(deny_unknown_fields)]`. A user who types `server_ur = "..."` (typo) or `api_token = "secret"` will get no warning. The comment says "token/password fields are intentionally ignored" but this is a security risk — a user may believe their token is being used from the config file when it silently is not. At minimum, unknown fields with names like `token`, `password`, `secret`, `api_key` should produce a warning or error.

### [MEDIUM] `toml` workspace dep version mismatch with story spec — `Cargo.toml:74`

Story spec says `toml = "0.9"` but workspace declares `toml = "0.8"`. This likely reflects that 0.9 doesn't exist yet, so 0.8 is correct in practice, but it's a documentation-vs-reality gap worth noting.

### [MEDIUM] `ServerError` variant hides its payload in Display — `error.rs:13-14`

`#[error("server error: the server encountered an internal error")]` hardcodes the message and ignores the `String` payload entirely. This means different server errors (e.g., "server returned status 500" vs "server returned status 502") are indistinguishable to the user. While the CWE-209 caution is appreciated, the variant's own constructed message (which is already sanitized at construction time in `client.rs`) should be visible for debugging. The current implementation swallows useful diagnostic information.

### [MEDIUM] `config_flag_accepted` test is vacuous — `cli_structure.rs:320-326`

The test uses `--config /tmp/test-config.toml` which doesn't exist. Since `main.rs:16-19` validates config file existence when `--config` is provided, this test will actually fail with exit code 1, not 2. But the assertion is only `code(predicate::ne(2))` — so exit code 1 passes. The test proves the flag is parsed (not exit 2) but does NOT test that config loading actually works with the flag. The test name is misleading.

### [MEDIUM] `error_output_does_not_expose_absolute_paths` test has weak assertion — `security.rs:19-29`

The predicate uses `.not().or(...)` which means: "either `/etc/shadow` is NOT in stderr, OR one of the acceptable messages IS in stderr." This means if the error message contains BOTH `/etc/shadow` AND "not found", the test still passes — it doesn't actually verify path suppression. The test should verify that the path is NOT exposed period (or at least that it's part of a well-formed error message rather than a raw filesystem path leak).

### [MEDIUM] `#[non_exhaustive]` missing on `CliError` — `error.rs:12`

Per rust.md: "enums that will grow" should use `#[non_exhaustive]`. `CliError` will certainly grow as more stories add error variants. Without it, downstream match arms won't need a wildcard, making additions breaking.

### [LOW] No `IsTerminal` auto-detection for output format — `cli.rs:13`, `output.rs`

AC-4 says "Table default for TTY, JSON for piped output." The current implementation always defaults to `table` regardless of whether stdout is a terminal. `std::io::IsTerminal` (as spec requires) is never used. This means piped output defaults to table format rather than JSON, breaking scripting ergonomics.

### [LOW] `expect()` in output formatters — `output.rs:91,109-116`

Multiple `.expect()` calls in `JsonFormatter::format()` and `CsvFormatter::format()`. While these are unlikely to fail in practice, the rust.md rule says "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The messages here are descriptive so they meet the letter of the rule, but writing to a `Vec<u8>` is infallible — the `expect` could be replaced with `unwrap_or_else` to be more precise, though this is not blocking.

### [LOW] `from_file_with_env` silently ignores unparseable `AXIATHON_TIMEOUT` — `config.rs:64-68`

If `AXIATHON_TIMEOUT=abc`, the env var is silently ignored and the file value is kept. This is defensible behavior, but the user gets zero feedback that their env var was malformed.

### [VERIFIED] Header injection prevention — `client.rs:12-19`

`validate_header_value` checks for `\n` and `\r` before constructing `HeaderValue`. Additionally, `HeaderValue::from_str` provides a second layer of defense against non-visible ASCII. Both token and tenant paths are protected. Tests verify rejection in `siem_client.rs:307-342`.

### [VERIFIED] Exit code mapping covers all variants — `error.rs:41-55`, `error_exit_codes.rs:71-91`

All `CliError` variants have explicit match arms. Test `all_cli_error_exit_codes_are_valid` enumerates all variants and asserts valid exit codes.

### [VERIFIED] `#![forbid(unsafe_code)]` present — `main.rs:2`, `lib.rs:2`

Both binary and library crate root forbid unsafe code.

### [VERIFIED] Tokens not loaded from config files — `config.rs:101-103`, `config_loading.rs:183-208`

`ClientConfig::token()` always returns `None`. `RawConfig` does not have a token field. Test confirms token field in TOML file is ignored.

### [VERIFIED] Dependency rule respected — `Cargo.toml`

`axiathon-client` depends only on `axiathon-core`. No server-side crate imports (storage, detection, ingestion, query).
