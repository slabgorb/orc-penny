# Story 6.1 Review: CLI Framework & Structure

*The Librarian has examined the ancient tablets of this submission, cross-referencing every glyph against the architectural scrolls...*

## Review Findings

### [CRITICAL] Nightly rustfmt violations — import ordering and line wrapping

`cargo +nightly fmt --all --check` fails across 4+ files: `cli.rs`, `completion.rs`, `config.rs`, `client.rs`. Nightly enforces import group ordering (std → external → crate-local) and line wrapping on long attributes.

Per the Reviewer Gotchas sidecar: *"Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval."*

**Files affected:** `cli.rs:1-5`, `completion.rs:3-5`, `config.rs:3-5`, `config.rs:80-84`, `config.rs:95-99`

### [CRITICAL] Binary entry point (`main.rs`) is a non-functional stub

`main.rs` contains only `eprintln!("not yet implemented"); std::process::exit(1);`. There is no:
- `Cli::parse()` invocation
- Tokio runtime initialization
- Config loading
- Command dispatch
- Error-to-exit-code handling

**AC-1 requires** `axiathon --help` to show all command groups. Currently it prints "not yet implemented" and exits 1. The entire purpose of Story 6.1 is to deliver a functional CLI framework — the wiring is the story.

### [HIGH] No tokio runtime — async SiemClient cannot be called

`SiemClient::get()` is `async fn` requiring `.await`. `main.rs` has no `#[tokio::main]` or manual runtime construction. Any command dispatching to `SiemClient` would panic at runtime. The story's technical guardrails specify loading keyring tokens "in sync context BEFORE entering Tokio runtime" — neither the sync nor async phases exist.

### [HIGH] Token loading completely absent

`ClientConfig::token()` always returns `None` (line 118-120). No code calls the `keyring` crate despite it being listed as a dependency. No code reads `AXIATHON_API_TOKEN` env var. AC-8 requires tokens from the OS keychain with env var fallback. The `keyring` dependency is declared but never used — dead dependency.

### [HIGH] Stub handlers have no dispatch wiring — tests are vacuous

Tests in `stub_handlers.rs` manually construct `CliError::NotImplemented("status".into(), "6.2".into())` and assert the message contains "6.2". This tests the `Display` impl on an error variant, **not** that `axiathon status` actually produces that error. There is no dispatch code that would create these errors. The tests pass vacuously — they prove string formatting works, not that stub commands are wired up.

### [HIGH] Test-to-binary gap — all tests bypass `main.rs`

All 111 tests call `Cli::parse_from()` or construct types directly. Zero tests exercise the actual binary via `assert_cmd` (which is declared as a dev-dependency but never used). The tests create a false confidence signal: the library modules work, but the binary that AC-1 through AC-5 describe does not.

### [MEDIUM] `toml` version mismatch — Cargo.toml says "0.8", story spec says "0.9"

`crates/axiathon-client/Cargo.toml:21` declares `toml = "0.8"`. The story technical guardrails specify `toml 0.9`. This is a minor version discrepancy that may cause issues if 0.9-specific features are needed later.

### [MEDIUM] `clap_complete`, `comfy-table`, `csv`, `dirs`, `keyring`, `reqwest`, `toml` not declared at workspace level

The story guardrails say: *"Add to `[workspace.dependencies]`"*. But `clap_complete`, `comfy-table`, `csv`, `dirs`, `keyring`, `reqwest`, and `toml` are declared directly in `crates/axiathon-client/Cargo.toml` with inline version specs, not via `workspace = true`. Only `clap`, `serde`, `serde_json`, `thiserror`, `tokio`, `tracing`, `chrono`, `uuid` use workspace declarations. This violates the workspace dependency management pattern.

### [MEDIUM] `OutputFormatter` methods don't use `self.format` — design inconsistency

`OutputFormatter` stores a `format: OutputFormat` field but exposes three separate methods: `format_table()`, `format_json()`, `format_csv()`. The caller must choose which to call. A more consistent API would have a single `format()` method that dispatches based on `self.format`. The `format()` accessor only returns the enum value. This means every call site must implement its own match — violating the pattern the trait was meant to centralize.

### [MEDIUM] `sanitize_message()` false positives on forward-slash words

At `error.rs:54`, any word starting with `/` and containing another `/` with length > 1 is redacted. This would redact legitimate error content like `/api/v1/status` in "not found: /api/v1/status", turning it into "not found: [redacted]". The `NotFound` variant at line 68 passes through unsanitized (`write!(f, "not found: {resource}")`), so this specific case is bypassed, but `ServerError` messages containing API paths would be redacted.

### [MEDIUM] Security tests for CRLF injection are weak — `Ok` branch is a no-op

In `security.rs:58-63`, if `SiemClient::new()` returns `Ok` (doesn't reject CRLF), the test just does `let _ = client;` — it does NOT assert failure. The test is structured as "if it rejects, good; if it doesn't, also fine." This means if the CRLF validation were removed, these tests would still pass. Only `siem_client_rejects_base_url_with_newline` at line 92 actually asserts `is_err()`.

### [LOW] `expect()` calls in production code (`output.rs`)

Lines 43, 49, 51, 53, 54 of `output.rs` use `expect()`. The project rules say *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* These `expect()` calls have messages, so they comply with the letter of the rule, but some are fragile — `CSV row write` could fail with pathological input (e.g., data containing the csv crate's internal terminator). Low risk for typical CLI usage.

### [LOW] Missing `#[non_exhaustive]` on `CliError` and `Commands` enums

Per the Rust rules: *"`#[non_exhaustive]` on enums that will grow."* Both `CliError` and `Commands` will grow as new stories add variants. Without `#[non_exhaustive]`, downstream code (tests, future crates) can exhaustively match without a `_` arm, causing breakage when variants are added.

### [VERIFIED] Security — CWE-113 header injection prevention is sound

`validate_no_crlf()` at `client.rs:14-21` correctly rejects `\r` and `\n` in base URL, token, and tenant ID at construction time. This is the right layer for this check.

### [VERIFIED] Security — CWE-209 error sanitization implemented

`sanitize_message()` strips absolute paths from `ServerError` display output. Auth errors are generic ("authentication expired") without leaking user existence.

### [VERIFIED] CLI structure — all command groups present per AC-1

`Commands` enum includes: `Query`, `Rules`, `Alerts`, `Ingest`, `Config`, `Status`, `Tenant`, `Login`, `Logout`, `Completion`, `Init`, `Tui`. Plural nouns (`Rules`, `Alerts`) match architecture doc.

### [VERIFIED] Global flags — all present with `global = true` per AC-5

`--format`, `--verbose` (repeatable with `Count`), `--quiet`, `--tenant`, `--server` (with `env = "AXIATHON_SERVER"`), `--config`, `--no-color` — all present and correctly annotated.

### [VERIFIED] Clippy clean — no warnings with `-D warnings`

### [VERIFIED] `#![forbid(unsafe_code)]` present in both `lib.rs` and `main.rs`
