## Findings

### `[HIGH]` CWE-209: ServerError leaks raw response body in Display — `error.rs:18`

The `ServerError` variant's `#[error]` format is `"Server error ({0}). Please try again later."` which includes the status code `{0}` but **not** the body `{1}` — good. However, the `ServerError(u16, String)` stores the raw body, and **anyone calling `format!("{:?}", err)` gets the full body** via the `Debug` derive. The test `server_error_display_sanitizes_internal_details` at `security.rs:12` correctly verifies `Display` doesn't leak, but: the `body` field is stored and accessible via pattern matching. If any future code logs at debug level (e.g. `tracing::debug!("{err:?}")`), the raw server body — potentially containing DB errors, credentials, stack traces — goes to logs. This is a **latent CWE-209 risk**. The body should be sanitized or omitted from the struct entirely, or the `Debug` impl should be manually implemented to redact it.

**Verdict: HIGH — stores raw server error body that Debug can expose.**

### `[HIGH]` Nightly `cargo fmt` check fails — `cli.rs`

Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not."* Running `cargo +nightly fmt --all --check` produces **366 lines of diff**. This is a blocking formatting violation per project conventions.

**Verdict: HIGH — nightly fmt check fails with significant formatting deltas.**

### `[MEDIUM]` `RawConfig` silently accepts unknown fields — `config.rs:7-12`

`RawConfig` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. This means a TOML file with `tken = "secret"` (a typo of "token") is silently accepted. The test at `config_loading.rs:79` (`client_config_ignores_token_field_in_toml`) verifies the token field is ignored, but serde actually ignores **all** unknown fields. This silently swallows typos, which can lead to operators thinking they've configured something when they haven't.

**Verdict: MEDIUM — silent acceptance of unknown config fields hides typos.**

### `[MEDIUM]` No TTY auto-detection for output format — missing from implementation

AC-4 requires: *"Table default for TTY, JSON for piped output. Use `std::io::IsTerminal`."* There is zero usage of `IsTerminal` or any TTY detection in the codebase. The `--format` flag defaults to `None` and the code never auto-selects JSON when piped. This is a missing AC requirement.

**Verdict: MEDIUM — AC-4 TTY auto-detection not implemented.**

AC-5 states: *"`--server` supports `AXIATHON_SERVER` env var."* The `--server` flag in `cli.rs:28` has no `env = "AXIATHON_SERVER"` attribute, and there is no code anywhere to read this env var. The config module supports `AXIATHON_API_URL` and `AXIATHON_TIMEOUT` but `AXIATHON_SERVER` for the `--server` flag is unimplemented.

**Verdict: MEDIUM — AC-5 env var for --server not wired.**

### `[MEDIUM]` `output.rs` uses `expect()` in production code — `output.rs:74-87`

The Rust coding rules at `.claude/rules/rust.md` explicitly state: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` calls have messages, so they technically comply. However, 6 `expect()` calls in `render_json` and `render_csv` mean a malformed input could panic the binary rather than returning a proper error. The `format_table` method returns `String` — it should return `Result<String, CliError>` to propagate errors. Writing to a `Vec<u8>` is infallible in practice, but the `serde_json::to_string_pretty` could theoretically fail with recursive structures.

**Verdict: MEDIUM — expect() in production code creates panic risk (though low probability).**

### `[MEDIUM]` `SiemClient` silently drops CRLF-injected tokens — `client.rs:27-34`

When `with_token()` receives a CRLF-injected value, it silently sets `self.token = None`. This is a silent failure — the caller has no way to know the token was rejected. A malicious env var or config value could silently strip authentication, causing confusing "auth expired" errors. This should either return `Result` or log a warning.

**Verdict: MEDIUM — silent rejection of CRLF-tainted tokens can mask real issues.**

### `[MEDIUM]` Credential stripping logic is fragile — `config.rs:37-44`

The `SCHEME_SEP` replacement hack to strip userinfo from URLs is brittle. Consider `https://user@host:port@path` — the `find('@')` finds the first `@`, but the logic's index arithmetic with `scheme_end` and `at_pos` is hard to verify. The comment says "strip userinfo" but there's no test for edge cases like `http://user@host:8080/path` with a port. The `url` crate would handle this correctly.

**Verdict: MEDIUM — hand-rolled URL parsing for credential stripping is fragile.**

**Verdict: LOW — invalid shell name silently produces empty output instead of error.**
