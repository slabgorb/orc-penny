# Story 6.1 Code Review — CLI Framework & Structure

**Reviewer:** Linus Torvalds mode

## Findings

### [CRITICAL] No `main.rs` binary entry point — AC-3, AC-10 cannot be fulfilled at runtime
The story requires an `axiathon` binary (`main.rs`) that dispatches commands, catches errors, writes errors to stderr, and calls `std::process::exit()` with exit codes. **There is no `main.rs`.** The `Cargo.toml` has no `[[bin]]` section. This means:
- No binary is produced — `cargo build -p axiathon-client` produces only a library
- Exit code mapping (AC-3) is tested in unit tests but never wired to `std::process::exit()`
- Stub handlers (AC-10) are defined as error types but no dispatch code calls them
- Errors-to-stderr routing (AC-3) has no implementation

This is the single most important deliverable of Story 6.1 and it's missing entirely.

### [HIGH] CWE-209: `ServerError` Display leaks internal details at `error.rs:5`
`ServerError(String)` uses `#[error("server error")]` for Display, which seems safe. BUT the `map_status_code` at `client.rs:90` stores `"server returned HTTP {status}"` inside it. The Display impl ignores the inner string and prints generic "server error". This means the inner string is only accessible via `Debug` — which is fine for logging. However, note that the `Display` for `ServerError` *discards* the specific HTTP status code, so operators get "server error" with no diagnostic info. This is arguably too aggressive — the HTTP status code itself is not sensitive. **Medium concern** — reclassifying.

### [HIGH] `with_token` and `with_tenant` bypass header injection validation at `client.rs:50-58`
The `SiemClient` provides safe `try_with_token`/`try_with_tenant` methods that validate against CWE-113, but also provides `with_token`/`with_tenant` that accept arbitrary strings with NO validation. The doc comments say "No validation" but this creates a dangerous API surface. Any code path using the non-`try` variants is vulnerable to header injection. The `try_*` variants also create a *new* `reqwest::Client` on every call, which is wasteful and semantically wrong (they clone everything, including reconstructing the HTTP client).

### [HIGH] `RawConfig` silently ignores unknown fields — no `#[serde(deny_unknown_fields)]` at `config.rs:14`
The comment at line 21 says "Unknown fields are silently ignored by serde's default behavior" and there's a test (`config_ignores_unknown_fields`) verifying this. The story says forward compatibility, so this is intentional. However, a typo like `api_url = ...` vs `api-url = ...` or `timeoutt = 30` would be silently ignored, returning defaults instead. This is a **silent failure** pattern. No warning is emitted. Operators will think their config is applied when it isn't. Reclassifying to **Medium** since the test explicitly encodes this as desired behavior.

### [MEDIUM] `uuid_v4_placeholder` is not a UUID at all — misleading name at `output.rs:123`
The function `uuid_v4_placeholder` generates a zero-padded nanosecond timestamp formatted as hex. It's called `uuid_v4_placeholder` but produces something like `00000000000000001a2b3c4d5e6f7890` — not a UUID v4 (no hyphens, no version/variant bits). The `request_id` in JSON metadata will be a hex timestamp, not a UUID. This violates AC-4's requirement for `ResponseMetadata` with a proper `request_id`.

### [MEDIUM] `timestamp_now` returns Unix epoch seconds, not ISO 8601 at `output.rs:133`
The comment says "ISO 8601 approximation" but it returns raw seconds like `"1709913600"`. This is not ISO 8601 by any stretch. AC-4 specifies `ResponseMetadata` with a `timestamp` — consumers would expect `2024-03-08T12:00:00Z`, not a raw integer string.

### [MEDIUM] `toml` dependency version mismatch — story spec says 0.9, Cargo.toml has 0.8 at `Cargo.toml:20`
The Technical Guardrails specify `toml 0.9`. The Cargo.toml uses `toml = "0.8"`. This may be intentional (0.9 may not exist yet), but it contradicts the spec.

### [MEDIUM] Workspace dependencies not declared for several crates at `Cargo.toml:11-20`
Story spec says to add `reqwest`, `comfy-table`, `keyring`, `clap_complete`, `dirs`, `csv`, `toml` to `[workspace.dependencies]` in the root `Cargo.toml`. Currently `clap_complete`, `comfy-table`, `csv`, `dirs`, `reqwest`, and `toml` are declared inline in the crate's Cargo.toml, not via workspace. This violates the workspace dependency management pattern.

### [MEDIUM] `keyring` dependency is missing entirely
The story spec lists `keyring 3` for OS keychain credential storage. It's not in the Cargo.toml at all. While the actual login implementation is Story 9.1, the `SiemClient` is supposed to load tokens from the keychain at startup (per AC-8: "Tokens in OS keychain").

### [MEDIUM] Test env var manipulation is not thread-safe at `config_loading.rs:63`, `global_flags.rs:89`
`std::env::set_var` / `remove_var` are not thread-safe and can cause UB in Rust 2024 edition. Tests using these will race when run in parallel. The `#[allow(deprecated)]` attribute isn't present either, so these may warn or fail on edition 2024.

### [MEDIUM] `config_ignores_token_field_in_toml` test is vacuous at `config_loading.rs:111`
The test verifies that `config.token()` returns `None` after parsing TOML with a `token` field. But `ClientConfig::token()` is hardcoded to always return `None` (line 43-45 of config.rs). The TOML `token` field is just silently ignored by serde (since `RawConfig` has no `token` field). The test doesn't actually verify the token was *rejected* — it verifies a hardcoded `None`. A more meaningful test would verify the token value isn't accessible anywhere on the struct.

### [MEDIUM] `no_arguments_does_not_panic` test has no assertion at `cli_structure.rs:258-262`
```rust
fn no_arguments_does_not_panic() {
    let result = Cli::try_parse_from(["axiathon"]);
    let _ = result;  // <-- discards result, asserts nothing
}
```
This test "passes" by not panicking, but it doesn't verify the *expected behavior* (should produce a help/error message). It's a vacuous test.

### [LOW] `ServerError` Display discards diagnostic information at `error.rs:5`
`#[error("server error")]` ignores the inner `String`. An operator seeing "server error" gets zero diagnostic value. The `{0}` should at minimum include the HTTP status code (which is not sensitive).

### [LOW] Nightly `rustfmt` check fails
`cargo +nightly fmt --all --check` shows formatting differences in `stub_handlers.rs`. Per the gotchas doc, nightly fmt must pass before approval.

## Summary

The library code is reasonably well-structured, the type design is clean, and the test coverage for what exists is thorough. But the elephant in the room is **there's no binary**. Story 6.1 is supposed to deliver an `axiathon` binary that operators can run. Without `main.rs`, there's no command dispatch, no exit code wiring, no stderr routing, and no actual CLI. The tests verify library behavior in isolation, but the integration point — the binary itself — doesn't exist.

The unsafe `with_token`/`with_tenant` methods alongside the safe `try_*` variants is a footgun waiting to happen. The timestamp and UUID helpers are misleadingly named and produce wrong formats. Several workspace dependency management rules are violated.

## Verdict

**CHANGES_REQUESTED**

### Blocking issues (must fix):
1. **No `main.rs`** — create the binary entry point with command dispatch, error-to-stderr, and exit code mapping
2. **Nightly fmt failure** — run `cargo +nightly fmt --all` 
3. **Unsafe `with_token`/`with_tenant`** — either remove these or add validation (don't offer two APIs where one is silently unsafe)

### Should fix (strongly recommended):
4. Declare shared dependencies in `[workspace.dependencies]` per project conventions
5. Fix `uuid_v4_placeholder` and `timestamp_now` to produce correct formats
6. Address thread-safety of `set_var`/`remove_var` in tests (edition 2024 concern)
7. Add assertion to `no_arguments_does_not_panic` test
