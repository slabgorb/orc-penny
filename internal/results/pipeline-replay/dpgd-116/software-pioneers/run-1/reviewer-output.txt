# Story 6.1 Code Review — Linus Torvalds Mode

*Listen, I've gone through every file with a microscope. Here's what I found.*

## Observations

### [HIGH] `CliError` doesn't use `thiserror` — violates project rules at `error.rs:1-64`

The `.claude/rules/rust.md` says: *"Use `thiserror` for error enums — structured, semantic variants."* `CliError` manually implements `Display` and `std::error::Error`. The `thiserror` crate is even declared as a workspace dependency AND in `Cargo.toml` but never used. This is a direct rule violation. Use `#[derive(thiserror::Error)]` with custom `#[error(...)]` attributes.

### [HIGH] `RawConfig` silently ignores unknown fields at `config.rs:10-16`

No `#[serde(deny_unknown_fields)]` on `RawConfig`. A user who typos `api_url` as `api_urll` gets zero feedback — their config silently falls back to defaults. This is a textbook configuration footgun. Operator puts `timout = 60` in their TOML, gets the default 30, and has no idea why.

### [HIGH] `has_file_token` is never set to `true` at `config.rs:66`

The `RawConfig` deserializes a `token` field, but `has_file_token` is hardcoded to `false` on line 66 even when `raw.token.is_some()`. The `has_file_token()` method exists, tests check it works, but the detection logic is dead. If someone puts a token in their TOML file, the security warning that's supposed to fire... never fires. The whole purpose of this field is defeated.

### [MEDIUM] Nightly `rustfmt` check fails at `client.rs:88`, `completion.rs:52`, `config.rs:44`

Per the reviewer gotchas: *"Always include `cargo +nightly fmt --all --check` in the preflight."* Three files have formatting diffs under nightly. This must be fixed before merge.

### [MEDIUM] `CliError` enum is not `#[non_exhaustive]` at `error.rs:8`

The `.claude/rules/rust.md` says: *"#[non_exhaustive] on enums that will grow."* `CliError` will definitely grow as more stories add error variants. Missing `#[non_exhaustive]` means downstream `match` arms in tests won't get a compiler warning when new variants are added.

### [MEDIUM] CRLF sanitization replaces instead of rejecting at `client.rs:26`

`with_token` silently strips `\r\n` and uses the remainder. So `"evil\r\nX-Admin: true"` becomes `"evilX-Admin: true"` — a valid-looking but completely wrong token. This should return an error or at least log a warning, not silently mangle the input. The security test passes because it only checks that CRLF is gone, not that the input was rejected.

### [MEDIUM] `chrono_now_iso()` returns Unix seconds, not ISO 8601 at `output.rs:101-107`

The function name says `chrono_now_iso` but returns `"1709976543"` — that's not ISO 8601 in any universe. AC-4 says JSON includes `ResponseMetadata` with `timestamp`. A raw epoch second isn't useful to operators. This is misleading naming at minimum, potentially an AC violation.

### [MEDIUM] `with_env_override` silently drops unparseable `AXIATHON_TIMEOUT` at `config.rs:82-84`

If someone sets `AXIATHON_TIMEOUT=abc`, the `parse::<u64>()` fails silently and the value is ignored. Same for `with_cli_override`. No warning, no error. The operator thinks they set a timeout override but it was silently dropped.

### [LOW] No `main.rs` — binary cannot be built at `Cargo.toml`

There's no `main.rs` in the crate, and no `[[bin]]` section in `Cargo.toml`. The crate compiles as a library only. Story 6.1 AC says `axiathon-client` should produce the `axiathon` binary. Without `main.rs`, there's no actual CLI binary. This is technically acceptable since the story scope says "stub handlers" and the tests verify the library API, but it's worth noting that AC-3's exit code behavior via `std::process::exit()` can't be tested end-to-end.

### [LOW] `generate_request_id()` uses nanosecond timestamp — not unique under contention at `output.rs:109-114`

Two requests within the same nanosecond (unlikely but possible) produce identical IDs. A UUID v4 would be more appropriate here.
