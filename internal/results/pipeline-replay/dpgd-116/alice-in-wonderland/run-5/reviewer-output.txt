# OFF WITH THEIR HEADS! — Review of Story 6.1: CLI Framework & Structure

*The Queen of Hearts inspects the rose garden...*

## Review Findings

### [HIGH] `RawConfig` silently ignores unknown fields — config typos will slip through at `config.rs:11`

`RawConfig` uses `#[derive(serde::Deserialize)]` without `#[serde(deny_unknown_fields)]`. If an operator writes `api_ulr` instead of `api_url`, or includes a `token = "..."` field, serde silently ignores it. The test `client_config_does_not_have_token_field` at `config_loading_test.rs:174` proves the token is silently dropped — but the operator gets **zero warning** that they put a secret in a config file. This is a security concern (operator thinks token is being used, it isn't) AND a usability bug (typos go undetected).

**Fix:** Add `#[serde(deny_unknown_fields)]` to `RawConfig`, or at minimum log a warning for unknown fields.

### [HIGH] `output.rs:67,72-78` uses `expect()` / `unwrap()` in production code paths — violates Rust coding rules

The `format_as_csv` method has four `.expect()` calls and `format_as_json` has one. Per project rules in `.claude/rules/rust.md`: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` messages are present but the real issue is that `format_table` returns `String`, not `Result<String, _>`. CSV write to a `Vec<u8>` genuinely cannot fail, but this is still a pattern violation. The JSON `.expect("JSON serialization must not fail")` at line 67 **could** fail if `serde_json` encounters issues with extremely large datasets.

**Recommendation:** Consider returning `Result<String, CliError>` from `format_table`, or document why these are infallible with `// SAFETY:` comments since they write to in-memory buffers.

### [MEDIUM] `SiemClient::new` only stores the LAST header error, masking the first — `client.rs:32-39`

If both `tenant_id` AND `token` contain CRLF, only the token error is stored (it overwrites the tenant error). The operator won't know both are bad.

**Fix:** Collect errors into a `Vec<String>` or use the first error.

### [MEDIUM] `SiemClient` only has `get()` — no `post()`, `put()`, `delete()` — `client.rs:58`

AC-7 says "SiemClient wraps reqwest::Client" for API communication. Currently only GET is implemented. Stubs for other HTTP methods aren't present, meaning future stories will need to add them. This is noted but acceptable for a framework story — however, the AC says "wraps reqwest::Client" implying a general-purpose wrapper, not just GET.

**Verdict:** Acceptable for Story 6.1 scope, but worth noting.

### [MEDIUM] No `main.rs` binary entry point — `crates/axiathon-client/src/main.rs` is missing

The story scope says "main.rs: Binary entry point, tracing init, dispatch, exit codes." There is no `main.rs`, no `[[bin]]` target in `Cargo.toml`, and no binary entry point. The lib.rs exports modules, but there's no actual `axiathon` binary being produced. This means **AC-3 (exit codes via `std::process::exit()` in main)** and **AC-9 (completion script to stdout, instructions to stderr)** cannot be verified end-to-end. The `execute_stub` method returns a String but nothing calls it and pipes it to stderr/stdout with the appropriate exit code.

### [MEDIUM] `toml` version mismatch with story spec — `Cargo.toml:22` specifies `0.8`, story says `0.9`

The story's Technical Guardrails section says `toml 0.9`, but the implementation uses `toml = "0.8"`. The latest `toml` crate is 0.8.x — version 0.9 doesn't exist yet. The story spec is wrong, not the code, but this should be documented.

### [MEDIUM] Nightly `rustfmt` check fails — formatting inconsistencies in test files

Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight."* The check shows formatting diffs in `config_loading_test.rs` and `output_format_test.rs`. These must be fixed before merge.

### [LOW] `client_config_handles_missing_file_gracefully` test is vacuous — `config_loading_test.rs:62-66`

```rust
assert!(
    result.is_ok() || result.is_err(),
    "missing config file must not panic"
);
```

This assertion is **always true** — it passes regardless of the result. It tests literally nothing. The test name claims "graceful handling" but doesn't verify what that means. Should the missing file return defaults? Return a specific error? This test rubber-stamps anything.

### [LOW] `--tenant` accepts raw `String`, not `TenantId` newtype — `cli.rs:39`

Per `.claude/rules/rust.md`: *"Newtypes for IDs: `TenantId(String)` — prevents mixing ID types."* The `--tenant` flag accepts `Option<String>` rather than using the `TenantId` newtype from `axiathon-core`. Similarly, `SiemClient::new` takes `Option<&str>` for tenant_id. This weakens type safety at the boundary.

### [LOW] `OutputFormatter` is a struct, not a trait — contradicts AC-4

AC-4 specifies *"`OutputFormatter` trait with Table/Json/Csv implementations."* The implementation uses a struct with an enum dispatch pattern instead. This is functionally equivalent but doesn't match the specified architecture.

### [VERIFIED] CRLF header injection prevention works — `client.rs:30-39`

`HeaderValue::from_str()` rejects control characters including `\r\n`. Tests at `siem_client_test.rs:225-258` confirm both tenant_id and token CRLF injection are caught. Good.

### [VERIFIED] Error messages don't leak server internals — `error.rs:40-57`

`ServerMessage` Display impl returns opaque "server error" string. The test at `error_exit_codes_test.rs:139-149` confirms raw stack traces don't leak through. Good.

### [VERIFIED] `#![forbid(unsafe_code)]` in lib.rs — `lib.rs:2`

Production code is protected. Test files use `#![allow(unsafe_code)]` for `std::env::set_var` with `#[serial]` — acceptable tradeoff.

### [VERIFIED] `#[non_exhaustive]` on `CliError` — `error.rs:10`

Correctly applied, verified by test at `error_exit_codes_test.rs:175-184`.

### [VERIFIED] Config tokens excluded from TOML deserialization — `config.rs:12-16`

`RawConfig` has no `token` field. Test confirms tokens don't leak into config struct. Good security posture.
