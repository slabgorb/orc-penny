## Observations

### [CRITICAL] `main.rs` is still a stub — no CLI dispatch wired at `crates/axiathon-client/src/main.rs:5-8`

The entire `main.rs` is still the original stub:
```rust
fn main() {
    eprintln!("axiathon CLI not yet implemented");
    std::process::exit(1);
}
```
The `Cli` struct, `Commands` enum, `SiemClient`, `OutputFormatter`, `ClientConfig`, and all command modules exist in `lib.rs` but **nothing is wired into the binary entry point**. The `axiathon` binary literally does nothing except print "not yet implemented" and exit 1. No clap parsing. No dispatch. No exit code mapping. No config loading. AC-1 through AC-10 require a working binary — this doesn't even call `Cli::parse()`.

The tests all exercise library code via `use axiathon_client::*`, bypassing `main.rs` entirely. The binary is dead code.

### [HIGH] Nightly `rustfmt` fails — 41 diffs across the codebase at `crates/axiathon-client/src/cli.rs` and others

Per gotchas.md: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not."* This has 41 formatting violations. Must be fixed before approval.

### [HIGH] `toml` version mismatch vs. story spec at `crates/axiathon-client/Cargo.toml:20`

Story spec says `toml 0.9`. Cargo.toml has `toml = "0.8"`. The `toml` crate 0.9 exists and has API differences. This is either a deliberate downgrade (undocumented) or a mistake. Either way, it doesn't match the spec. Additionally, the story spec says workspace dependencies should be used — `toml`, `clap_complete`, `comfy-table`, `csv`, `dirs`, and `reqwest` are all declared locally in the crate's `Cargo.toml` instead of in `[workspace.dependencies]`.

### [HIGH] `keyring` dependency missing — AC-8 requires OS keychain credential storage

AC-8 and the Technical Guardrails explicitly require `keyring 3` for OS keychain credential storage: *"Tokens in OS keychain, NOT config file."* The `keyring` crate is not in `Cargo.toml`, not imported anywhere, and no credential loading code exists. The config `#[serde(skip)] token` field with env var fallback is there, but the primary keychain path is absent.

### [HIGH] `has_token_from_file()` always returns `false`, ignoring actual state at `crates/axiathon-client/src/config.rs:135-136`

```rust
pub fn has_token_from_file(&self) -> bool {
    false  // hardcoded
}
```
The field `token_from_file` is set correctly in `from_toml_str()` (line 64), but `has_token_from_file()` ignores it and returns `false`. This means:
1. If a user puts a token in their config file, no warning is ever issued
2. Security tests in `security.rs` that assert `!config.has_token_from_file()` are vacuous — they always pass regardless of config content

### [MEDIUM] `ClientConfig` accepts unknown TOML fields silently at `crates/axiathon-client/src/config.rs:12`

No `#[serde(deny_unknown_fields)]` on `ClientConfig`. A typo like `api_rul = "..."` is silently ignored, falling back to defaults. Operator thinks they've configured the URL but haven't. This is a classic config safety issue.

### [MEDIUM] `SiemClient` silently drops invalid header values at `crates/axiathon-client/src/client.rs:58-68`

When `HeaderValue::from_str()` fails (e.g., token contains non-ASCII), the header is silently dropped — no error, no log, no indication to the user. The request proceeds without auth, which will fail with a confusing 401 later. Should at minimum log a warning or return an error.

### [MEDIUM] `timeout` field typed as `i64` but returned as `u64` at `crates/axiathon-client/src/config.rs:16,129-131`

```rust

pub fn timeout(&self) -> u64 {

```
If `timeout` is negative (valid i64, and TOML allows it), `.max(1)` catches it... but only because 1 > any negative. The type should be `u64` in the struct, or validated on load. The `as u64` cast on a negative value after `.max(1)` is safe but the type is misleading.
