### `[HIGH]` Silent header injection failure — no error propagated
`client.rs:50-53`:
```rust
if let Ok(val) = HeaderValue::from_str(tenant) {
    headers.insert("X-Tenant-ID", val);
}
```
When `HeaderValue::from_str()` fails (e.g., newlines in tenant ID), the invalid header is **silently dropped**. The `with_tenant()` method accepts the value at line 29, stores it, but then at header-building time the tenant header is silently omitted. The caller has no indication their tenant ID was rejected. Same pattern for token at lines 56-60.

This is defense-in-depth (CWE-113 is prevented), but the silent failure means a typo or malformed tenant ID goes unnoticed — the request goes out **without tenant scoping**, which could return wrong-tenant data. Should return an error or at least log a warning.

### `[HIGH]` `expect()` calls in production output formatters
`output.rs:71-72,75-76,82,99-100,103-104` — eight `expect()` calls in `OutputFormatter` implementations:
```rust
serde_json::to_value(&data).expect("data serializable")
wtr.write_record(headers).expect("write headers")
```
Per `rust.md`: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The rules do allow `expect()` with messages, but these messages are not actionable (they don't tell the operator what to do). More importantly, these are in `format()` methods that return `String`, not `Result<String>` — so `?` isn't possible without a trait change. This is a design tension: the `OutputFormatter` trait signature prevents proper error propagation.

### `[HIGH]` `toml` version mismatch — spec says 0.9, workspace has 0.8
Story spec requires `toml 0.9`, but `Cargo.toml:51` declares `toml = "0.8"`. While 0.8 works, this is a deviation from the architecture spec that should be documented or the spec should be updated.

## NON-BLOCKING ISSUES

### `[MEDIUM]` Missing `main.rs` binary entry point
The story scope lists `main.rs` as a file to create, and AC-3 references `main.rs catches errors and calls std::process::exit()`. The crate currently builds as a library only. No `[[bin]]` section in Cargo.toml, no `src/main.rs`. This may be intentional (tests prove the library API works), but AC-3's exit-code-via-process-exit contract is unverifiable without it.

### `[MEDIUM]` Env var tests are not thread-safe
`tests/config_loading.rs:135-137,153-155,166-168` use `std::env::set_var()` / `remove_var()` which is [unsafe in Rust 2024](https://doc.rust-lang.org/std/env/fn.set_var.html) when other threads read env vars. Since `cargo test` runs tests in parallel within the same process, these tests can race with each other. The edition is 2021 so this compiles, but it's a ticking time bomb for edition upgrade.

### `[MEDIUM]` `generate_completions` returns empty string for unknown shell — no error
`lib.rs:69` — unknown shell name returns `String::new()` instead of `Err(CliError)`. The caller (`handle_command` at line 49) wraps this in `Ok(output)`, so `axiathon completion tcsh` exits 0 with empty output. Should exit with code 1 and an error message.

### `[MEDIUM]` Tenant ID uses raw `Option<String>` — no newtype validation
`cli.rs:33` — `pub tenant: Option<String>`. Per `rust.md`: *"Newtypes for IDs: TenantId(String)... prevents mixing ID types"* and *"Validated constructors at trust boundaries."* The `--tenant` flag accepts any string. Story 6.1 scope doesn't include auth (Story 9.1), but the unvalidated string flows into HTTP headers.

### `[LOW]` `table_formatter_no_color_flag_disables_ansi` test uses wrong flag value
`tests/output_format.rs:56` — comment says `no_color = true equivalent` but passes `false`:
```rust
let formatter = TableFormatter::new(false); // no_color = true equivalent
```
The test passes because `comfy_table` doesn't emit ANSI in non-TTY contexts anyway, so the assertion `!output.contains("\x1b[")` succeeds regardless. This test doesn't actually verify the `no_color` flag works — it's vacuously passing.

### `[LOW]` `ResponseMetadata` created twice in `JsonFormatter::format()`
`output.rs:66,79` — `ResponseMetadata::new()` is called to build the metadata block, then `meta.request_id.clone()` is used to add a redundant top-level `request_id` field. This means the JSON output has `request_id` at both the root level and inside `metadata`. Unclear if intentional or copy-paste error.
