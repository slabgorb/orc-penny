### `[HIGH]` `with_env_overrides_from()` panics on invalid input — `config.rs:93`
```rust
self.timeout_secs = t.parse::<u64>().expect("AXIATHON_TIMEOUT must be a valid positive integer");
```
The `expect()` panics if `AXIATHON_TIMEOUT` is set to a non-numeric value (e.g. `"30s"` or `"abc"`). Per `rust.md`: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` has an actionable message, so it technically complies, but this is user-facing input from an environment variable — a trust boundary. A panic crashing the CLI with a backtrace on bad env input is poor UX and arguably violates the spirit of the rule. The test `client_config_rejects_invalid_timeout_env_var` validates via `catch_unwind`, which is a code smell — tests shouldn't need to catch panics from production APIs.

**Recommendation:** Return `Result` from `with_env_overrides_from()` instead of panicking. Map the parse failure to `CliError::ConfigError`.

### `[MEDIUM]` `RawConfig` silently accepts unknown fields — `config.rs:10-15`
```rust

struct RawConfig {
    api_url: Option<String>,
    timeout: Option<i64>,
}
```
No `#[serde(deny_unknown_fields)]`. An operator who puts `token = "secret123"` in their config file gets zero feedback that the field is ignored. Worse, if they put `server_url` instead of `api_url` (a plausible typo), they silently get defaults. This is the exact "silent failure" pattern flagged in security tests but not actually prevented here.

**Recommendation:** Add `#[serde(deny_unknown_fields)]` to `RawConfig`. This forces operators to fix typos and prevents the false security of thinking a `token` field in config is being used.
