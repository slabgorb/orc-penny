## Critical Findings (Block PR)

### [CRITICAL] `cargo +nightly fmt --all --check` fails — `cli.rs`

Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight."* The check fails with multiple diffs in `cli.rs` — all the `#[command(after_help = "...")]` lines exceed the line length and need multi-line formatting. This will fail CI post-merge.

**Fix:** Run `cargo +nightly fmt --all` before submitting.

### [CRITICAL] Duplicate "Story" in error messages — `error.rs:31` + all stubs

The error format string is:
```rust
#[error("not yet implemented (Story {0})")]
NotImplemented(String),
```
And every stub passes `"Story X.Y"`:
```rust
Err(CliError::NotImplemented("Story 6.2".into()))
```
**Rendered output:** `"not yet implemented (Story Story 6.2)"` — "Story" appears twice.

AC-10 requires: `"not yet implemented (Story X.Y)"` — exactly one "Story".

**Fix:** Either remove "Story" from the format string: `#[error("not yet implemented ({0})")]`, or remove "Story" from the stub values: `"6.2"`.

### [CRITICAL] `Logout` and `Tui` dispatch to wrong handler — `main.rs:20-21`


Both `axiathon logout` and `axiathon tui` will print `"not yet implemented (Story Story 9.1)"` — wrong story references and misleading to operators. `Tui` should reference Epic 4, and `Logout` needs its own stub (even if it shares Story 9.1, it deserves a distinct message like "logout" not "login").

## High Findings (Block PR)

### [HIGH] `SiemClient` is async with no runtime in `main.rs` — `client.rs:63` / `main.rs:8`

`SiemClient::get()` is `async fn` but `main()` is synchronous with no Tokio runtime setup. This means no command can actually make HTTP requests. The entire HTTP client layer is dead code that can never be called from the binary.

For Story 6.1 this is technically acceptable since all commands are stubs, but it establishes a broken pattern for Stories 6.2+ — whoever implements `status` will immediately discover there's no way to call async code.

**Fix:** Either set up a Tokio runtime in `main()` (e.g., `#[tokio::main]` or manual `Runtime::new()`), or document this as a known gap. The story spec says *"Load token at CLI startup in sync context BEFORE entering Tokio runtime"* — this implies a runtime IS expected.

---

### [HIGH] Config, formatter, and client never wired in `main.rs` — `main.rs`

`main.rs` parses the CLI struct but ignores: `cli.format`, `cli.verbose`, `cli.quiet`, `cli.server`, `cli.tenant`, `cli.config`, `cli.no_color`. No config is loaded, no `SiemClient` is created, no `OutputFormatter` is constructed.

This means:
- AC-4 (output format): `--format` flag parsed but never used
- AC-8 (config loading): config file never loaded
- AC-5 (global flags): flags parsed but have no effect

For a framework story where all commands are stubs, this is borderline acceptable — but it means the framework is **not** actually established. Story 6.2 will have to do all the wiring work that should be done here.

**Fix:** Wire up at least config loading and client creation in `main.rs`, passing a context struct to command handlers. The stubs can ignore it, but the pattern needs to exist.

---

### [HIGH] `keyring` dependency imported but never used — `Cargo.toml:16`

`keyring = { version = "3", features = ["apple-native", "linux-native"] }` is declared as a dependency but never imported or used anywhere in the crate. This adds unnecessary compile-time cost and platform-specific native dependencies (Apple Security framework, Linux secret service).

**Fix:** Remove `keyring` from dependencies until Story 9.1 (login) actually needs it, or add a `#[cfg(feature = "keyring")]` gate.

---

### [HIGH] `toml` version mismatch — workspace `0.8` vs story spec `0.9`

The story spec says `toml 0.9` but `Cargo.toml` and workspace use `toml = "0.8"`. This is either a stale spec or the wrong version was pinned. `toml 0.9` doesn't exist yet at time of writing, so the spec may be wrong — but this should be documented.

**Fix:** Clarify with PM whether spec intended `0.8` and update the story doc, or if `0.9` is a future target.

---

### [HIGH] `ClientConfig` silently accepts unknown fields — `config.rs:12`

`#[derive(Deserialize)]` with `#[serde(default)]` but **no** `#[serde(deny_unknown_fields)]`. A config file with `tokken = "secret"` (typo of "token") is silently accepted. Combined with the fact that a `token` field in the config is silently ignored (per the security test), this means:

1. Users who accidentally put their token in the config file won't get warned
2. Typos in config keys are silently ignored

The test `config_does_not_store_tokens` checks that there's no `token()` accessor, but the config file happily accepts and discards a `token` field.

**Fix:** Add `#[serde(deny_unknown_fields)]` to `ClientConfig`. This would cause `token = "..."` in config to error with "unknown field `token`", which is the correct behavior (tokens belong in keychain).

## Medium Findings (Non-blocking)

### [MEDIUM] `expect()` in production code — `output.rs:69,79-85` and `completion.rs:10`

Rust rules say: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message"*. While `expect()` is permitted, these are in code paths reachable from the binary:

- `output.rs:69`: `serde_json::to_string_pretty(&output).expect("JSON serialization should not fail")`
- `output.rs:79-85`: Multiple `.expect()` calls in CSV formatter
- `completion.rs:10`: `String::from_utf8(buf).expect("completion script should be valid UTF-8")`

These are theoretically infallible operations, but the CSV writer writing to a `Vec<u8>` truly cannot fail, while the JSON serializer could panic on custom serializers. The messages are actionable, so this is acceptable but should be documented.

### [MEDIUM] No TTY detection for output format auto-selection — `output.rs`

AC-4 states: *"Table default for TTY, JSON for piped output."* The spec also says: *"Use `std::io::IsTerminal` (not deprecated `atty` crate)."* No TTY detection exists anywhere. When piped, table output with potential ANSI escapes will corrupt downstream tools.

**Fix:** Add TTY detection logic to `main.rs` or the output module to auto-select JSON when stdout is not a terminal.

### [MEDIUM] JSON `request_id` generated at format time, not request time — `output.rs:63`

The `JsonFormatter` generates `request_id: uuid::Uuid::now_v7()` during formatting, not during the actual HTTP request. This breaks tracing correlation — the `request_id` in the JSON output won't match any server-side request ID.

**Fix:** Accept `request_id` as a parameter to the formatter, generated at request time.

### [MEDIUM] `SiemClient::new()` doesn't validate `base_url` — `client.rs:16-49`

`ClientConfig::validate_api_url()` exists and correctly rejects non-HTTP URLs and embedded credentials, but `SiemClient::new()` never calls it. A client constructed with `ftp://evil.com` or `javascript:alert(1)` is happily accepted.

**Fix:** Call `ClientConfig::validate_api_url(base_url)?` in `SiemClient::new()`.

### [MEDIUM] `axiathon-core` imported but unused — `Cargo.toml:9`

`axiathon-core = { path = "../axiathon-core" }` is a dependency but no types from it are imported anywhere in the crate. The spec says the client depends on `axiathon-core` for shared types like `TenantId`, but `TenantId` is never used — tenant is a raw `String`.
