## Findings

### [CRITICAL] CWE-209: `ServerError` Display leaks internal details verbatim — `error.rs:24`

The `#[error("server error — contact your administrator")]` Display impl is **hardcoded and static**, which means it does NOT actually leak the inner `String`. However, the test `cli_error_display_server_error_does_not_leak_stack_trace` at `tests/exit_codes_integration.rs:83` **passes only because the Display ignores the inner string**. This is actually CORRECT behavior — but there's a subtle trap: `Debug` still exposes the inner value (`ServerError("NullPointerException...")`). If any code path uses `{err:?}` instead of `{err}` for user-facing output, internals leak. The comment on the error type says Display is sanitized, which is true, but `NotFound(String)` at line 17 has `#[error("resource not found")]` and also drops its inner string — **making the inner `String` dead code** that serves no purpose but could confuse future maintainers into thinking it's used.

**Recommendation:** Either use the inner string in logging (with explicit `tracing::debug!`) or remove it to avoid confusion. The `path` in `NotFound(path)` passed at `client.rs:88` is silently discarded.

### [HIGH] Missing `main.rs` — No binary entry point

There is **no `main.rs`** in `crates/axiathon-client/src/`. The crate compiles as a library only. AC-3 specifies that `main.rs` catches errors and calls `std::process::exit()` — this is entirely absent. The story scope explicitly lists `main.rs` as a key file to create. Without it, there is no `axiathon` binary, and exit code behavior, stderr routing, tracing initialization, and command dispatch are all untested at the integration level.

**Impact:** The core deliverable — an executable `axiathon` binary — does not exist. Shell completions reference a binary that cannot be built. The `Cargo.toml` has no `[[bin]]` section.

### [HIGH] Nightly `rustfmt` check fails — `siem_client_integration.rs:185`

Per gotchas.md: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not." The nightly fmt check shows formatting diffs in test files. This must be fixed before merge.

### [HIGH] Config silently accepts unknown fields — `config.rs:34`

`toml::from_str::<FileConfig>` with serde's default behavior **silently ignores unknown fields**. A user who writes `[sever]` (typo for `[server]`) or `timeout_seconds = 30` (wrong key, should be `timeout`) gets no warning. Their config is silently ignored and defaults are used. This is a classic operability footgun.

**Recommendation:** Add `#[serde(deny_unknown_fields)]` to both `FileConfig` and `ServerConfig`.

### [HIGH] Config file token field silently ignored — `config.rs:6-15`

If a user puts `token = "secret"` in their config TOML under `[server]`, it is silently accepted by serde (no unknown field denial) and ignored. The test at `config_integration.rs:123` verifies this works, but the right behavior is to **error out or warn** when a token appears in a plaintext config file. Silent acceptance could lead operators to believe their token is being used when it isn't — a security usability issue.

### [MEDIUM] `edition = "2018"` in axiathon-client/Cargo.toml — should be `edition.workspace = true`

The workspace declares `edition = "2024"` in `workspace.package`, but `axiathon-client/Cargo.toml:2` hardcodes `edition = "2018"`. This is inconsistent with the workspace and the project's MSRV of 1.85+. Edition 2018 misses language features the project should be using.

### [MEDIUM] Workspace dependency management incomplete — `Cargo.toml`

Story spec says to add `reqwest`, `comfy-table`, `keyring`, `clap_complete`, `dirs`, `csv`, and `toml` to `[workspace.dependencies]`. Only `clap` is defined at workspace level. All others (`clap_complete = "4"`, `comfy-table = "7"`, `csv = "1"`, etc.) are defined inline in the crate's Cargo.toml. This violates the workspace dependency management pattern and the technical guardrails.

### [MEDIUM] `SiemClient::with_token` / `with_tenant` silently drop invalid input — `client.rs:28-39`

When CRLF injection is detected, the builder methods silently ignore the value and return `self` with no token/tenant set. This means `client.with_token("malicious\r\nheader").has_token()` returns `false` with no error. An operator debugging "why doesn't auth work" would have no indication their token was rejected. Should return a `Result` or at minimum log a warning.

### [MEDIUM] `SiemClient::new` silently coerces bad URLs to empty string — `client.rs:14-18`

If the URL doesn't start with `http://` or `https://`, it's silently replaced with `""`. Any subsequent `.get()` call would then make a request to a path like `/api/v1/status` with no host, which would fail with a confusing reqwest error rather than a clear "invalid base URL" error. Should return `Result` or panic with a clear message.

### [MEDIUM] Env var tests are not thread-safe — `config_integration.rs:55-101`

Tests use `std::env::set_var` / `remove_var` which is global process state. Cargo runs tests in parallel by default. Two tests modifying the same env var concurrently will race. This is a known Rust test footgun. Consider using `serial_test` or a mutex, or at minimum `#[serial]` annotations.

### [MEDIUM] `OutputFormatter` uses `expect()` in production code — `output.rs:76,81-86`

`format_as_json` calls `.expect("JSON serialization should not fail")` and `format_as_csv` has four `.expect()` calls. Per project rules: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect()` messages are descriptive, but these functions return `String` not `Result`, making error propagation impossible. If CSV writing fails (e.g., on non-UTF8 data), the process panics.

### [MEDIUM] No `after_help` usage examples on any command — `cli.rs`

AC-2 specifies "include `after_help` usage examples for each command group." None of the command structs have `#[command(after_help = "...")]` attributes. The help output will compile and render, but won't include the usage examples the AC requires.

### [LOW] Test quality concern: Stub handler tests don't test actual dispatch — `stub_handlers_integration.rs`

The stub tests construct `CliError::NotImplemented` directly and check its Display output. They don't verify that dispatching `Commands::Query(...)` actually returns a `NotImplemented` error. This is because there are no command handlers or dispatch logic — there's no `main.rs`. The tests are vacuous in the sense that they test the error type's Display, not the command dispatch behavior.

### [LOW] `SiemClient` only has `get()` method — `client.rs:62`

Only `GET` requests are supported. Future commands will need `POST`, `PUT`, `DELETE`. This is fine for a stub, but worth noting.

### [LOW] `timeout_seconds` field in `ClientConfig` is never used — `config.rs:20`

The timeout is loaded and stored but `SiemClient` doesn't accept a timeout parameter. The `reqwest::Client::new()` at `client.rs:24` uses default timeout settings.
