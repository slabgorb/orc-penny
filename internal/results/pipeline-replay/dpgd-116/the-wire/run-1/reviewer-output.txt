## Findings

### `[CRITICAL]` Workspace `unsafe_code` lint downgraded from `forbid` to `deny` — `Cargo.toml:73`

The workspace root changes `unsafe_code = "forbid"` to `unsafe_code = "deny"`. This is a **workspace-wide security regression** that weakens safety for *every* crate, not just `axiathon-client`. The reason is clear — test files need `#![allow(unsafe_code)]` for `std::env::set_var` (unsafe in Edition 2024) — but the fix should be scoped to `[dev-dependencies]` or test cfg, not a global downgrade. With `deny` instead of `forbid`, any crate in the workspace can now `#[allow(unsafe_code)]` in production code.

### `[HIGH]` `main.rs` has no command dispatch — binary does nothing — `main.rs:8-10`

The binary parses arguments and discards the result. There is no match on `cli.command`, no call to any stub handler, no error printing to stderr, no `std::process::exit()`. **AC-3 (exit codes) and AC-10 (stub messages) are dead letter.** The tests call `handle_stub()` directly as library functions, which proves the functions exist, but the binary never invokes them. An operator running `axiathon status` gets... nothing. Silent success with exit code 0.

### `[HIGH]` Config silently ignores explicit missing file — `config.rs:34-44`

When a user passes `--config /path/that/doesnt/exist`, the code silently falls back to defaults. This is dangerous: the user explicitly chose a config file, expects it to be used, and gets silent default behavior instead. The test `config_handles_missing_file_gracefully` at `config_integration.rs:43-48` compounds this with a vacuous assertion: `assert!(result.is_ok() || result.is_err())` — that's a tautology. The test proves *literally nothing*.

### `[HIGH]` Silent header injection failure (CWE-113 adjacent) — `client.rs:42-45, 48-51`

When `HeaderValue::from_str()` fails (e.g., CRLF in token/tenant), the header is silently omitted. The user thinks they're authenticated but they're sending unauthenticated requests. The security tests at `siem_client_integration.rs:131-147` have a conditional assertion: `if let Some(tenant_val)` — if the header is absent (because it was rejected), the test passes vacuously. The test should assert the header IS absent or that construction errors out, not conditionally check.

### `[MEDIUM]` Completion silently falls back to bash for unknown shell — `completion.rs:15`

`_ => Shell::Bash` means a user who types `axiathon completion zssh` (typo) gets bash completions silently piped to their zsh config, corrupting their shell setup. This should return a `CliError` for unrecognized shells. The `CompletionArgs.shell` field is also a raw `String` — should use clap's `value_parser` or `ValueEnum` for validation at parse time.

### `[MEDIUM]` `init.rs` is a no-op, not "functional" — `init.rs:1-6`

AC-9 context and the story say init should be "functional, not stub." But `init.rs` contains only `is_functional() -> bool { true }`. There's no directory creation, no default config writing, no first-time setup logic. This is arguably less useful than a stub — at least a stub tells you it's unimplemented.

### `[MEDIUM]` `NotImplemented` variant missing from exhaustiveness test — `error_exit_code_integration.rs:178-195`

The `all_error_variants_have_nonzero_exit_code` test lists 8 variants but `CliError::NotImplemented` has 9 total. The `NotImplemented` variant is untested. If someone changes its exit code to 0, no test catches it.

### `[MEDIUM]` Test env var races cause multi-threaded failures — `config_integration.rs`, `cli_structure_integration.rs`

Tests that manipulate env vars with `unsafe { std::env::set_var() }` don't use proper cleanup guards (drop-based RAII). If a test panics between set and remove, the env var leaks. This is confirmed: **2 tests fail when run without `--test-threads=1`**. Tests must be deterministic regardless of thread count, or use `serial_test` crate / `temp_env`.

### `[MEDIUM]` `RawConfig` accepts unknown fields silently — `config.rs:10-14`

Missing `#[serde(deny_unknown_fields)]`. A user who puts `token = "my-secret"` in `cli.toml` gets no warning — it's silently ignored. Combined with no token accessor on `ClientConfig`, this creates a confusing UX where the user thinks their token is configured but it's not. Per AC-8, tokens belong in the keychain, but the config parser should *warn* about unexpected fields, not swallow them.

### `[MEDIUM]` JSON metadata is hardcoded zeroed placeholder — `output.rs:74-78`

`request_id` is all zeros, `timestamp` is epoch 1970. AC-4 says JSON includes `ResponseMetadata` with `request_id`, `timestamp`, `api_version`. Real timestamps and UUIDs should be generated, or at minimum the metadata should clearly indicate "placeholder" rather than looking like real data that's all zeros.

### `[LOW]` AC-1 missing `tui` and `logout` commands — `cli.rs:48-89`

AC-1 explicitly lists `login`/`logout` and `tui` as required in `--help`. Neither `Logout` nor `Tui` variants exist in the `Commands` enum. The story scope says TUI is out of scope, but AC-1 is prescriptive. At minimum, these should be stubs.

### `[LOW]` `exit_code_success_is_zero` test is a tautology — `error_exit_code_integration.rs:12-15`

`assert_eq!(0_i32, 0, "Success exit code must be 0")` tests the number zero equals zero. It doesn't test any code.
