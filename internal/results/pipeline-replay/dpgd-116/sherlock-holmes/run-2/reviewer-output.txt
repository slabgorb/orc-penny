## Findings

### [CRITICAL] Nightly `rustfmt` fails — `client.rs`, `config.rs`, `output.rs`, and multiple test files

`cargo +nightly fmt --all --check` produces formatting diffs across 7+ files. Per the reviewer gotchas (`gotchas.md`), nightly rustfmt enforces import ordering that stable does not. **This must be fixed before merge.**

Files affected: `client.rs:60`, `client.rs:125`, `config.rs:42`, `config.rs:88`, `output.rs:90-96`, plus all 6 test files.

---

### [HIGH] Missing `logout` and `tui` commands — AC-1 violation at `cli.rs`

AC-1 explicitly requires: *"`axiathon --help` must show all command groups: query, rules, alerts, ingest, config, status, tenant, **login/logout**, **tui**, completion, init."*

The `Commands` enum at `cli.rs:48` has no `Logout` variant and no `Tui` variant. These are required by the acceptance criteria even as stubs.

---

### [HIGH] `--server` flag does not read `AXIATHON_SERVER` env var — AC-5 violation at `cli.rs:28`

AC-5 states: *"`--server` supports `AXIATHON_SERVER` env var."* The `server` field at `cli.rs:28` has no `env = "AXIATHON_SERVER"` clap attribute. The doc comment *mentions* the env var, but the implementation does not wire it. This is a documentation-reality mismatch — the comment lies.

---

### [HIGH] `token_value_for_test()` exposes raw token via public API — `client.rs:84`

```rust
pub fn token_value_for_test(&self) -> Option<&str> {
    self.token.as_deref()
}
```

This is a `pub` method on a `pub` struct that returns the raw bearer token. The comment says "for testing only" but it's publicly accessible to any downstream crate. This should be gated behind `#[cfg(test)]` or a `test-support` feature flag. As-is, any code that depends on `axiathon-client` can extract the token, undermining the careful `Debug` impl that hides it.

---

### [HIGH] `has_token_from_config` is **never** set to `true` — silent security gap at `config.rs:60`

```rust
if raw.token.is_some() {
    config.has_token_from_config = false; // intentionally ignore tokens in config
}
```

The field `has_token_from_config` exists to detect when a user insecurely places a token in the config file. But it is *always* `false`. When `raw.token.is_some()`, it should be set to `true` so callers can warn the user. The test at `config_loading_tests.rs:146` passes vacuously — it asserts `!c.has_token_from_config()` which is trivially true because the field is hardcoded `false`. This means users who put tokens in their config file get **zero warnings**.

### [MEDIUM] JSON metadata missing `request_id` and `timestamp` — AC-4 partial violation at `output.rs:65-71`

AC-4 requires: *"JSON includes `ResponseMetadata` (request_id, timestamp, api_version)."* The implementation only includes `api_version` and `count`:

```rust
"meta": {
    "api_version": "v1",
    "count": rows.len(),
}
```

No `request_id`, no `timestamp`. The test at `output_format_tests.rs:109` checks `parsed.get("meta").is_some()` which passes but doesn't verify the required fields are present.

---

### [MEDIUM] `SiemClient::new` panics on empty URL — `client.rs:34`

```rust
assert!(!base_url.is_empty(), "base URL must not be empty");
```

Every other error path in this crate returns `Result<_, CliError>`. This constructor uses `assert!` which will `panic!` and crash the process with a stack trace instead of a user-friendly error message. The test at `siem_client_tests.rs:164` uses `catch_unwind` which acknowledges this is a panic, but the crate conventions call for `Result`.

---

### [MEDIUM] `generate_completion` returns error string as success — `completion.rs:13`

```rust
_ => return format!("unsupported shell: {shell}"),
```

Unsupported shell names return a `String` (not an error). Callers cannot distinguish a valid completion script from an error message. This should return `Result<String, CliError>`.

---

### [MEDIUM] `with_tenant` silently sanitizes vs `with_token` rejects — inconsistent CWE-113 handling at `client.rs:48-68`

- `with_token`: newlines → token set to `None` (rejected)
- `with_tenant`: newlines → stripped silently (sanitized)

This asymmetry means a malicious tenant ID `"evil\r\nX-Injected: true"` becomes `"evilX-Injected: true"` — silently accepted. The sanitization should either reject (like token) or at minimum log a warning.

---

### [MEDIUM] Config silently ignores unknown fields — `config.rs:11`

`RawConfig` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. A typo like `api_ur = "..."` is silently ignored, falling back to defaults. Users get no feedback that their config key was misspelled.

Workspace declares `toml = "0.8"` but the story spec requires `toml` 0.9. Minor, but deviates from the architecture document.
