## Findings

### `[HIGH]` AC-1 violation: `tui` and `logout` commands missing — `cli.rs:44-65`

AC-1 explicitly requires: *"axiathon --help must show all command groups: query, rules, alerts, ingest, config, status, tenant, login/logout, tui, completion, init."*

The `Commands` enum has no `Tui` variant and no `Logout` variant. `axiathon --help` will not show these groups. This is a direct AC failure.

### `[HIGH]` AC-5 violation: `--server` missing `AXIATHON_SERVER` env var — `cli.rs:23-24`

AC-5 states: *"`--server` supports `AXIATHON_SERVER` env var."* The clap definition is:
```rust
#[arg(long, global = true)]
pub server: Option<String>,
```
It needs `env = "AXIATHON_SERVER"` to satisfy the AC. Same applies to `AXIATHON_TIMEOUT` if intended for the `--config` or timeout flags.

### `[HIGH]` CWE-209: `NotFound` Display exposes HTTP response body — `error.rs:16`

```rust
#[error("not found: {0}")]
NotFound(String),
```

The `{0}` is populated from `from_http_status(404, &body)` at `client.rs:110`. The server's raw HTTP body is forwarded directly into the user-facing Display message. The `ServerError` variant correctly hides its inner string with `#[error("server error occurred")]`, but `NotFound` leaks it. Server response bodies can contain stack traces, internal paths, or database details.

### `[HIGH]` AC-4 violation: JSON metadata missing `timestamp` — `output.rs:90-93`

AC-4 requires `ResponseMetadata` with `request_id, timestamp, api_version`. The implementation includes `request_id` and `api_version` but omits `timestamp`:
```rust
serde_json::json!({
    "request_id": uuid::Uuid::new_v4().to_string(),
    "api_version": "v1",
})
```

### `[MEDIUM]` Fabricated `request_id` is semantically misleading — `output.rs:91`

The JSON output generates a random UUID v4 client-side as `request_id`. A request ID should correlate to the actual API request for tracing/debugging. Fabricating one client-side defeats its purpose and could mislead operators correlating logs.

### `[MEDIUM]` `config_token_not_in_toml` test is vacuous — `tests/config_loading.rs:111-125`

The test uses `if let Ok(c) = config` then checks the Debug output. Since `ClientConfig` has `#[serde(deny_unknown_fields)]`, the `token` field causes `from_toml` to return `Err`. The test accepts both `Ok` and `Err` paths, so it always passes regardless of behavior. It should assert `Err` explicitly — that's the security-relevant guarantee.

### `[MEDIUM]` `with_env_overrides` silently swallows invalid timeout — `config.rs:67-73`

```rust
if let Ok(val) = t.parse::<u64>() {
    if val > 0 { result.timeout = val; }
}
```

If an operator sets `AXIATHON_TIMEOUT=abc`, it silently falls back to the config file default. No warning, no error. The operator believes they've set a custom timeout when they haven't. This should at minimum log a warning, or return an error.

### `[MEDIUM]` `table_formatter_handles_empty_rows` assertion is vacuous — `tests/output_format.rs:143`

```rust
assert!(!output.is_empty() || output.is_empty()); // Just verifying no panic
```

This is literally `assert!(true)`. The comment says "verifying no panic" but the panic would occur on `format_table`, not in the assertion. If the intent is to verify no panic, this assertion contributes nothing — if the function panics, the test already fails. Remove the vacuous assertion or assert something meaningful about the output.

### `[MEDIUM]` `cli_error_display_does_not_leak_server_internals` test doesn't actually verify — `tests/exit_codes.rs:75-85`

The test creates a `ServerError` with internal details `"database connection pool exhausted at 10.0.0.5:5432"` but only asserts `!msg.is_empty()`. It should assert that `msg` does NOT contain `"10.0.0.5"` or `"5432"`. The Display impl happens to be safe (`"server error occurred"`), but the test doesn't verify it. This is a missed opportunity — if someone changes the Display impl to `#[error("server error: {0}")]`, this test would not catch the CWE-209 regression.

### `[MEDIUM]` `expect()` in production output formatters — `output.rs:96,101-108`

Five `expect()` calls in `format_as_json` and `format_as_csv`. While writing to in-memory `Vec<u8>` buffers makes these practically infallible, the Rust rules state *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The messages aren't actionable (e.g., "CSV header write should not fail"). Consider propagating errors via `Result` to match the project's error handling philosophy.

### `[LOW]` Missing `#[non_exhaustive]` on `Commands` enum — `cli.rs:43`

Project Rust rules: *"`#[non_exhaustive]` on enums that will grow."* `Commands` will grow (at minimum `Tui`, `Logout`). The `CliError` enum correctly has `#[non_exhaustive]` but `Commands` does not.

### `[LOW]` `init` creates config without restricting file permissions — `commands/init.rs:19`

`std::fs::write` uses the process umask (typically 0644). While the config file currently holds no secrets, AC-8 states tokens go in keychain. If this invariant ever breaks (common in practice), the config file would be world-readable. A `chmod 0600` would be defensive.

### `[LOW]` `toml` crate version `0.8` vs spec `0.9` — `Cargo.toml:25`

The technical guardrails specify `toml 0.9`. The implementation uses `0.8`. Crate `toml` 0.9 does not currently exist on crates.io, so this is a spec error. Worth flagging for spec correction.

### `[VERIFIED]` Security: Header injection prevention — `client.rs:35-48`

SiemClient correctly rejects `\r` and `\n` in both token and tenant_id, preventing CWE-113 header injection. Tests cover CR, LF, and CRLF variants. Good.

### `[VERIFIED]` Security: URL scheme validation — `client.rs:28-31`

SiemClient rejects non-http(s) schemes, preventing SSRF to `file://`, `javascript:`, `data:` URLs. Tests cover these cases.

### `[VERIFIED]` Security: `deny_unknown_fields` on `ClientConfig` — `config.rs:10`

Prevents deserialization of unexpected fields. A `token` field in the TOML file will cause a parse error, enforcing the "tokens in keychain, not config" rule.

### `[VERIFIED]` Security: `ServerError` Display hides internals — `error.rs:12`

`#[error("server error occurred")]` correctly suppresses the inner String from user-facing output. The inner detail remains accessible via `Debug` for logging only.

### `[VERIFIED]` Clap derive-only structure — `cli.rs`

All command parsing uses `#[derive(Parser)]`, `#[derive(Subcommand)]`, and `#[derive(Args)]`. No imperative builder code. AC-6 satisfied.

### `[VERIFIED]` Exit code mapping — `error.rs:55-61`

Auth → 3, Authz → 4, all others → 1. Clap handles exit code 2 for usage errors. AC-3 satisfied.

### `[VERIFIED]` Shell completion is functional — `commands/completion.rs`

Uses `clap_complete::generate()` correctly. Tests verify all four shells produce non-empty output containing the binary name and subcommands. AC-9 satisfied.

## Data Flow Trace

**Input:** `axiathon --server https://prod.example.com --tenant acme status`

1. `Cli::parse()` → `cli.server = Some("https://prod.example.com")`, `cli.tenant = Some("acme")`, `cli.command = Commands::Status(StatusArgs { component: None })`
2. `main.rs:12` → matches `Commands::Status(_)` → calls `handle_status()`
3. `handle_status()` accepts no arguments → returns `Err(CliError::NotImplemented("6.2"))`
4. `main.rs:29` → prints `"Error: not yet implemented (Story 6.2)"` to stderr
5. `main.rs:30` → exits with code 1

**Observation:** Global flags `--server` and `--tenant` are parsed correctly but discarded. This is acceptable for stub handlers (Story 6.2+ will wire them), but the handler signatures should be designed to accept these from the start to avoid a refactor later. This is a design concern, not a blocker.

## Verdict

**CHANGES_REQUESTED**

Three HIGH findings block approval:

1. **AC-1:** Missing `tui` and `logout` command groups that the AC explicitly requires in `--help` output
2. **AC-5:** `--server` flag missing `env = "AXIATHON_SERVER"` clap annotation
3. **CWE-209:** `NotFound` variant leaks raw HTTP response body to users
4. **AC-4:** JSON metadata missing required `timestamp` field

The framework is well-structured and the security posture is mostly strong (header injection prevention, `deny_unknown_fields`, `ServerError` hiding internals). Fix the four HIGH issues and the vacuous test assertions, and this will be ready for approval.
