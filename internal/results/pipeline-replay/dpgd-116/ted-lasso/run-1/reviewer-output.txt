## Observations

### [CRITICAL] Missing `main.rs` — no binary entry point at `cli_structure.rs:1`

The story requires producing the `axiathon` binary. There is no `main.rs` in `crates/axiathon-client/src/`. Without it, `cargo build -p axiathon-client` produces only a library, not the `axiathon` binary. This means AC-3 (exit code handling in `main.rs` with `std::process::exit()`), AC-9 (completion to stdout, instructions to stderr), and AC-10 (stubs printing and exiting) cannot be exercised end-to-end. The `Cargo.toml` also lacks a `[[bin]]` section. **The story's primary deliverable — a working `axiathon` binary — does not exist.**

### [HIGH] CWE-209: `NotFound` error leaks full internal URL at `client.rs:90`

```rust
404 => Err(CliError::NotFound(url)),
```

The `url` here is the fully-constructed internal URL (e.g., `http://internal-host:8080/api/v1/status`). The `CliError::NotFound` Display impl is `#[error("not found: {0}")]`, so this internal URL is exposed to the user. Per the security comment on `error.rs:1-4`, Display impls should not include internal details like connection strings or server paths. The base URL can reveal internal infrastructure topology.

### [HIGH] `ServerError` variant accepts arbitrary strings — CWE-209 risk at `client.rs:76,92`

```rust
CliError::ServerError(e.to_string())
```

The `reqwest` error `.to_string()` can include connection details, DNS resolution info, and internal hostnames. This is passed straight to `Display` via `#[error("server error: {0}")]`. The error type's own security doc comment warns against this, but the implementation doesn't follow it.

### [HIGH] Nightly `rustfmt` check fails at `stub_handlers.rs:79,89`

Per the reviewer gotchas: "Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval." The nightly fmt check shows formatting diffs in `stub_handlers.rs`. This is a blocking finding per project rules.

### [MEDIUM] `toml` version mismatch: workspace has `0.8`, story spec requires `0.9` at `Cargo.toml:49`

The Technical Guardrails specify `toml 0.9`, but the workspace `Cargo.toml` declares `toml = "0.8"`. Version 0.9 doesn't exist on crates.io yet (latest is 0.8.x), so the spec is wrong — but this should be documented/acknowledged rather than silently diverged from.

### [MEDIUM] `ConfigFile` silently ignores unknown fields at `config.rs:7-13`

`serde::Deserialize` defaults to ignoring unknown fields. If a user puts `tokne = "..."` (typo) or `api_key = "secret"` in their config, it's silently ignored. For a security-sensitive config file, `#[serde(deny_unknown_fields)]` would catch typos and prevent accidental credential exposure in the config file. The test `client_config_does_not_store_token_in_file` even verifies a `token` field is ignored — but this means the token value sits in a plain-text file with no warning.

### [MEDIUM] `tenant` field uses raw `String`, not `TenantId` newtype at `cli.rs:22,client.rs:9`

The project's Rust rules require "newtypes for IDs: `TenantId(String)` — prevents mixing ID types." Both `Cli::tenant` and `SiemClient::tenant_id` use `Option<String>`. The `axiathon-core` crate exports `TenantId`, and the client depends on `axiathon-core`. Using raw strings here undermines the type safety the project has invested in.

### [MEDIUM] `handle_init` returns `NotImplemented` — AC says it should be functional at `commands/init.rs:3`

The story scope says: "Shell completion generation (functional, not stub)" and "`axiathon init` first-time setup (functional, not stub)." The completion command is implemented functionally via `generate_completion()`, but `init` is a stub returning `NotImplemented`. This violates the story's scope boundary.

### [MEDIUM] `output.rs:70` uses `expect()` in production code at `output.rs:70,79,83,84`

The Rust rules say "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect()` calls here arguably have actionable messages, but `CsvFormatter::format` has four `expect()`s in sequence. If the `OutputFormatter` trait returned `Result<String, CliError>` instead, these would use `?` — which is more idiomatic and testable.

### [MEDIUM] `SiemClient` only implements `get()` — no `post`/`put`/`delete` at `client.rs:57`

Most command groups will need methods beyond GET (e.g., `rules create`, `alerts acknowledge`, `ingest pause`). The client wrapper only has `get()`. While this is a stub phase, the test coverage for header injection only exercises GET. Future methods must replicate the same header injection and status mapping logic — a design where headers are injected once (e.g., via `reqwest::Client::builder().default_headers()`) would be safer.

### [LOW] No test for `SiemClient` trailing-slash URL normalization at `client.rs:45`

`SiemClient::new` trims trailing slashes from `base_url`, but no test verifies this. A URL like `http://localhost:8080/` combined with path `/api/v1/status` would produce `http://localhost:8080//api/v1/status` without this normalization. Worth a test since it's defense logic.

### [LOW] `Completion` and `Init` commands have no `Shell` argument in the CLI enum at `cli.rs:86-90`

`Commands::Completion` is a unit variant with no shell argument. The `generate_completion` function takes a `Shell` parameter, but there's no way to pass it from the CLI. The command would need something like `axiathon completion bash`, which requires a subcommand or argument. As-is, the CLI has no mechanism to select the shell.

### [VERIFIED] Header injection prevention works correctly

`validate_header_value` at `client.rs:12-19` checks `\n`, `\r`, and `\0`. Tests cover all three injection vectors. Validated.

### [VERIFIED] Exit code mapping is correct and complete

All `CliError` variants map to expected codes. Tests cover every variant. Exit code 2 (usage) is handled by clap automatically. Validated.

### [VERIFIED] Shell completion scripts generate correctly for all four shells

`generate_completion` produces non-empty, distinct scripts for bash/zsh/fish/PowerShell. Validated.

### [VERIFIED] `#![forbid(unsafe_code)]` on the lib crate

`lib.rs:2` has `#![forbid(unsafe_code)]`. Test files use `#![allow(unsafe_code)]` only where needed for `set_var`/`remove_var` in edition 2024. Validated.
