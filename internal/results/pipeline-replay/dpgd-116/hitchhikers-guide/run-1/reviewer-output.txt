## Findings

### [CRITICAL] CWE-209: ServerError Display leaks raw response body — `error.rs:19`

The `ServerError` variant's `#[error]` Display format is:

```rust
#[error("server returned error {0}")]
ServerError(u16, String),
```

This only renders the status code (`{0}`), but the test at `exit_codes.rs:80-93` checks that the Display output doesn't contain the body string — and it passes **only because `{0}` is the u16, not the String `{1}`**. However, the body is still stored in the variant and accessible via `Debug`. The SECURITY comment at the top of `error.rs` claims "ServerError intentionally hides raw response bodies to prevent information leakage," yet the body is stored and could be logged via `{err:?}` in any tracing call. If anyone adds `{1}` to the format string or uses Debug formatting in a user-facing context, the body leaks. The body string in the variant is a ticking time bomb.

**Recommendation:** Either don't store the raw body at all (just store status code), or store a sanitized/truncated version. Storing it "hidden" behind a `{0}` that skips it is brittle.

### [HIGH] Config silently accepts unknown fields — `config.rs:5-9`

The `RawConfig` struct uses default serde deserialization, which **silently ignores unknown fields**. A user who writes `api_ur = "..."` (typo) or `tokens = "secret"` gets no feedback. The `#[serde(deny_unknown_fields)]` attribute is absent.

This is especially dangerous because:
1. A user could put `token = "secret"` in the config file (the test at `config_loading.rs:151` checks Debug output doesn't contain it, but serde silently drops it — the user never learns they're doing something wrong)
2. Typos in `api_url` → `api_ur` silently fall back to defaults

**Recommendation:** Add `#[serde(deny_unknown_fields)]` to `RawConfig`, or at minimum warn on unknown fields.

### [HIGH] Nightly rustfmt check fails — `cli.rs`

Per the gotchas sidecar: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not." The nightly fmt check shows diffs in `cli.rs` (long `#[command(after_help = ...)]` lines need wrapping). This is a blocking CI issue per project conventions.

### [MEDIUM] Config env var override skips validation — `config.rs:51-52`

The `AXIATHON_API_URL` env var override at line 51-52 does **no validation** at all:

```rust
if let Ok(url) = std::env::var("AXIATHON_API_URL") {
    config.api_url = url;  // No http:// check, no URL validation
}
```

The file-based `api_url` at least checks `url.starts_with("http")`, but the env var path bypasses this entirely. An operator could set `AXIATHON_API_URL=ftp://evil` or even garbage, and it would be accepted silently.

### [MEDIUM] `OutputFormatter` uses `expect()` in production code — `output.rs:61-74`

Six `expect()` calls in `format_as_json` and `format_as_csv`. While these are arguably infallible (serializing known types to JSON, writing CSV to a Vec), the project rules at `rust.md` say: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect()` messages are descriptive, so this technically complies, but `format_table` returns `String` not `Result<String>`, preventing proper error propagation. If the formatter is ever used with pathological input (e.g., a string containing invalid UTF-8 that somehow got past Rust's type system — unlikely but the pattern is fragile), it panics instead of returning an error.

### [MEDIUM] CRLF injection tests are vacuous — `siem_client.rs:116-141`

The CRLF injection tests at lines 116-141 catch panics but then **do nothing** if the function succeeds:

```rust
if result.is_ok() {
    // The tenant should not contain the injected header
    // (exact assertion depends on API — the point is it must not pass through)
}
```

Empty `if` body = no assertion = vacuous test. The implementation does sanitize (good!), but the test doesn't verify the sanitization actually worked. It should assert the stored value doesn't contain `\r` or `\n`.

### [MEDIUM] `verbose_level_increments` test is non-vacuous but fragile — `global_flags.rs:37-44`

```rust
fn global_flag_verbose_exists_and_repeatable() {
    let cli = Cli::try_parse_from(["axiathon", "-v", "status"]);
    assert!(cli.is_ok() || cli.is_err(), "...");
```

`is_ok() || is_err()` is always true. This test asserts literally nothing — it only checks that parsing doesn't panic. The later `verbose_level_increments` test does properly assert values, so coverage exists, but this test is misleading.

### [LOW] Missing `main.rs` — no binary entry point

There's no `main.rs` or `[[bin]]` in `Cargo.toml`. The story spec says `main.rs` should exist as the binary entry point with tracing init, dispatch, and exit code handling. Currently only `lib.rs` exists. This is acceptable for a TDD phase (tests come first), but the absence should be noted.

### [LOW] `OutputFormatter` is a struct, not a trait — `output.rs:11`

AC-4 and the architecture doc specify "OutputFormatter trait with Table/Json/Csv implementations." The implementation uses a struct with an `OutputFormat` enum and match dispatch. This is functionally equivalent and arguably simpler, but diverges from the spec. No trait exists.

### [VERIFIED] Header injection (CWE-113) is sanitized — `client.rs:21-23, 27-29`

CRLF characters are stripped from both token and tenant values before they're stored. Good pattern.

### [VERIFIED] Exit code mapping is correct — `error.rs:39-45`

0=success (implicit), 1=general error, 3=auth expired, 4=unauthorized. Clap handles exit code 2 for usage errors automatically.

### [VERIFIED] Dependency rule respected — `Cargo.toml:9`

Only depends on `axiathon-core` for shared types. No server-side crate imports.

### [VERIFIED] Token not stored in config — `config.rs:5-9`

`RawConfig` deliberately excludes a `token` field with a comment explaining tokens belong in OS keychain.

### [VERIFIED] No `unwrap()` in production code

Grep confirms zero `unwrap()` calls in `src/`. Only `expect()` with messages (debatable but compliant).
