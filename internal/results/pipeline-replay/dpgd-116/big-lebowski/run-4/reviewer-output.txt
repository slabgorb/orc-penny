# Adversarial Code Review: Story 6.1 — CLI Framework & Structure

*"Your revolution is over, Mr. Developer. Condolences. The bums lost."*

I have examined every file, traced data flows, run the tests, run the linter, and run nightly fmt. Here are my findings, in descending severity order. And unlike some people, I actually earned my findings through rigorous analysis.

## CRITICAL

### 1. `[CRITICAL]` Missing `main.rs` — the binary has no entry point at `crates/axiathon-client/src/main.rs`

The entire `axiathon` binary cannot be built or executed. There is no `main.rs`, no command dispatch, no CLI arg parsing orchestration, no config loading pipeline, no credential fetching, no exit code mapping at the process level. The crate compiles as a **library only**. The `Cargo.toml` doesn't even define `[[bin]]`. Every AC that involves the binary actually running (AC-1 through AC-10 in production) is unmet. The tests work because they test library APIs, not the binary.

## HIGH

### 2. `[HIGH]` Silent rejection of CRLF-injected values — CWE-391 at `client.rs:40-56`

`with_token()` and `with_tenant()` silently discard values containing `\r` or `\n`, returning `Self` as if nothing happened. The caller has **no way to know** the value was rejected. A downstream API call proceeds without authentication or tenant context, potentially causing a confusing 401/403 error or operating in the wrong tenant scope. This should return `Result<Self, CliError>` or at minimum log a warning.

### 3. `[HIGH]` `is_secure_or_local()` always returns `true` — security theater at `client.rs:90-92`

The method is documented as "Whether the URL passes security checks" but hardcoded to `return true`. The test at `siem_client_integration.rs:140-148` asserts `is_secure_or_local()` on `http://production.example.com` — this **passes** because the function is a no-op. The test comment says "Should either reject or warn" but it does neither. The test is **vacuous** — it asserts the constant `true`.

### 4. `[HIGH]` `init.rs` is empty — spec says "functional, not stub" at `commands/init.rs:1`

The story scope explicitly says: "Shell completion generation (functional, not stub)" and "axiathon init first-time setup (functional, not stub)". Completion is implemented. Init is a single doc comment. AC-10 carves out completion and init as exceptions that should be implemented, not stubbed.

### 5. `[HIGH]` No `logout` command handler — `cli.rs:85` defines `Logout(LogoutArgs)` but no `commands/logout.rs` handler exists

The `commands/mod.rs` has no `logout` module. Running `axiathon logout` would require dispatch logic (which doesn't exist per #1), but even if it did, there's no handler to dispatch to. Unlike login (deferred to Story 9.1), logout is listed in AC-1 as a required command group and needs at minimum a stub.

### 6. `[HIGH]` Nightly `rustfmt` check fails — 38 formatting violations

Per the project's gotchas.md: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval." 38 diffs found. This is a blocking finding per project rules.

## MEDIUM

### 7. `[MEDIUM]` `RawConfig` silently ignores token field — config.rs:23

The `token` field in `RawConfig` is `#[allow(dead_code)]` and silently parsed then discarded. If an operator puts `token = "..."` in their config, there's no warning that it's being ignored. A warning to stderr would guide them to use the keychain instead. The `has_token_from_file()` method always returns `false` but doesn't tell the operator why.

### 8. `[MEDIUM]` `toml` crate version mismatch — Cargo.toml:21 specifies `"0.8"` but spec says `"0.9"`

The Technical Guardrails specify `toml 0.9` as a key dependency. The implementation uses `0.8`. This may be intentional (0.9 may not exist yet), but it deviates from the spec without documentation.

### 9. `[MEDIUM]` `rules` stub references "Story 6.6" — `commands/rules.rs:6`

The rules stub says `not yet implemented (Story 6.6)` but the epic doc doesn't assign rules to Story 6.6. Story 6.6 is for shell completions. This will confuse operators trying to find implementation status.

### 10. `[MEDIUM]` Vacuous test: `exit_code_success_is_zero` — `error_exit_code_integration.rs:14-18`

```rust
assert_eq!(0i32, 0, "Success exit code convention is 0");
```
This asserts `0 == 0`. It tests nothing. It doesn't verify that any code path produces exit code 0.

### 11. `[MEDIUM]` Vacuous test: `crate_forbids_unsafe_code` — `security_integration.rs:141-146`

```rust
assert!(true, "Compile-time guarantee via #![forbid(unsafe_code)]");
```
`assert!(true)` always passes. If someone removes `#![forbid(unsafe_code)]` from `lib.rs`, this test still passes. The comment claims "workspace lint catches it" but that's not verified by this test.

### 12. `[MEDIUM]` TTY auto-detection not implemented — `output.rs`

AC-4 requires: "Table default for TTY, JSON for piped output. Use `std::io::IsTerminal`." There is no TTY detection anywhere. The `OutputFormatter::new()` defaults `color: true` unconditionally.

### 13. `[MEDIUM]` No `OutputFormatter` trait — just a struct at `output.rs:15`

AC-4 specifies "OutputFormatter trait with Table/Json/Csv implementations." The implementation is a struct with a format enum, not a trait. This affects extensibility and testability.

### 14. `[MEDIUM]` URL embedded credentials check is fragile — `config.rs:86-95`

The check `server_url.contains('@') && split("://").nth(1).contains('@')` is a pattern match, not URL parsing. URLs like `https://host/?email=user@domain.com` have `@` after `://` but no credentials. The `url` crate (or `reqwest::Url`) would be more robust for userinfo detection.

### 15. `[MEDIUM]` `SiemClient::new()` doesn't validate — non-fallible constructor at `client.rs:18-25`

The doc comment says "Panicking constructor for known-good URLs" but it doesn't panic on bad input — `SiemClient::new("not-a-url")` happily creates a client. The `try_new()` fallible constructor exists but `new()` accepts garbage silently.
