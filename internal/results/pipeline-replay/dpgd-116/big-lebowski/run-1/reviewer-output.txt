## Review Findings

### `[HIGH]` Nightly `rustfmt` violations block CI — 252 lines of diff

`cargo +nightly fmt --all --check` produces 252 lines of formatting diff across production code and tests. Per `gotchas.md`: "Always include `cargo +nightly fmt --all --check` in the preflight." This blocks merge.

Files affected: `client.rs:1-5` (import ordering), `output.rs:75-83` (chaining), `cli_structure.rs:3` (import ordering), and multiple test files.

---

### `[HIGH]` No binary entry point — `axiathon` executable does not exist

The story scope explicitly states: "produces binary `axiathon`." AC-1 requires `axiathon --help` to show command groups. There is no `main.rs`, no `[[bin]]` section in `Cargo.toml`. The crate compiles as a library only. The entire operator-facing binary is missing.

This is not a minor omission. The story deliverable is a CLI *binary*. Without it, AC-1, AC-2, AC-3 (exit code behavior via `std::process::exit()`), AC-9 (stdout/stderr separation), and AC-10 (stub handlers printing and exiting) are untestable as end-to-end behaviors.

At: `crates/axiathon-client/Cargo.toml` — missing `[[bin]]` section.

---

### `[HIGH]` `--server` flag missing `AXIATHON_SERVER` env var support (AC-5 violation)

AC-5 states: "`--server` supports `AXIATHON_SERVER` env var." The `cli.rs:29` `--server` arg has no `env = "AXIATHON_SERVER"` attribute. Clap supports this natively via `#[arg(env = "AXIATHON_SERVER")]`. The env var is completely absent from the codebase. This is a direct AC violation.

At: `crates/axiathon-client/src/cli.rs:29`

---

### `[HIGH]` Silent header drop on injection attempt — no error, no log

In `client.rs:76-84`, when `HeaderValue::from_str()` fails (e.g., newlines in tenant ID or token), the header is **silently dropped**. The request goes out without `Authorization` or `X-Tenant-ID`. No error. No warning. No log.

This means: if a tenant ID containing `\r\n` is supplied, the request silently goes out **without tenant isolation**. An attacker who can influence the tenant ID value causes silent scope escalation — requests hit the API with no tenant context, potentially accessing default/admin scope.

The fix: return a `CliError` when header construction fails, don't silently drop.

At: `crates/axiathon-client/src/client.rs:76-84`

---

### `[HIGH]` `apply_env_override` and `apply_cli_override` bypass URL validation

`config.rs:72-82`: `apply_env_override("AXIATHON_API_URL", ...)` sets `server_url` directly without calling `validate_server_url()`. Same for `apply_cli_override` at line 85-95. An attacker controlling `AXIATHON_API_URL` can set `javascript:`, `file:///etc/passwd`, or empty URLs — all of which `from_toml()` correctly rejects.

The validation is only applied in one code path but bypassed in the two higher-precedence override paths.

At: `crates/axiathon-client/src/config.rs:74`, `crates/axiathon-client/src/config.rs:87`

---

### `[MEDIUM]` `SiemClient::try_new()` claims URL validation but does nothing

Documented as "Create a new client with URL validation" at `client.rs:31`, but the implementation is identical to `new()` — just wrapped in `Ok()`. No scheme validation, no URL parsing. The doc comment is a lie that creates false confidence.

At: `crates/axiathon-client/src/client.rs:32-40`

---

### `[MEDIUM]` AC-2 violation — no `after_help` usage examples on any command

AC-2 requires: "include `after_help` usage examples for each command group." Zero instances of `after_help` exist anywhere in the codebase. `grep` confirms no matches. Every command group is missing its required usage examples.

At: all `commands/*.rs` files

---

### `[MEDIUM]` OutputFormatter trait locked to 2-column data

The trait signature `format_rows(&self, headers: &[&str], data: &[(&str, &str)])` accepts only 2-column tuples. Real CLI commands (rules list, alerts list) will need 5+ columns. This is an architectural limitation that will require a breaking trait change.

Should be `&[Vec<String>]` or similar. The current design can't serve any real command beyond stubs.

At: `crates/axiathon-client/src/output.rs:16`

---

### `[MEDIUM]` Workspace dependency versions don't match story spec

Story spec requires `dirs 6`, `toml 0.9`, `keyring 3`. Actual: `dirs 5`, `toml 0.8` (aliased as `toml_crate`), `keyring` missing entirely. The `keyring` crate is critical — AC-8 requires "tokens in OS keychain, NOT config file." Without `keyring`, there's no mechanism to implement credential storage.

At: `Cargo.toml:49,51` (dirs/toml versions), keyring absent.

---

### `[MEDIUM]` `RawConfig` silently ignores unknown fields — typos and secrets swallowed

`config.rs:12`: `RawConfig` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. Typos like `servr_url` or dangerous fields like `token = "secret"` are silently ignored. While the test at `config_loading.rs:140` verifies `token()` returns `None`, the config file successfully parsed with a `token` field — no warning to the operator that they put a secret in a plaintext file.

At: `crates/axiathon-client/src/config.rs:12`

---

### `[LOW]` `generate_completion()` takes `&str` instead of `Shell` enum

`lib.rs:18` defines `generate_completion(shell: &str)` which manually matches strings to `Shell` variants. Meanwhile `CompletionArgs` already has `shell: Shell` (the clap enum). The string-based API duplicates enum semantics and has a silent fallback (`_ => String::new()`) that returns empty output with no error for invalid shells.

At: `crates/axiathon-client/src/lib.rs:18-27`

---

### `[VERIFIED]` Security: credential redaction in Debug impl — sound

`error.rs:73-89`: `sanitize_credentials()` correctly redacts `://user:pass@host` patterns. Debug impl on `SiemClient` shows `has_token: true/false` without the value. Good.

### `[VERIFIED]` `#[non_exhaustive]` on `CliError` — correct

Forces wildcard arm in downstream matches, preventing silent error swallowing when new variants are added.
