# Story 6.1 Review — First Speaker's Assessment

*The Plan requires precision. Every flaw left unchecked compounds across future stories. Let me share what my Speakers of the Table have perceived.*

## Findings

### [HIGH] F1 — No `main.rs` binary entry point — `crates/axiathon-client/src/main.rs` is missing

**AC-3** requires `main.rs` to catch errors and call `std::process::exit()`. The story spec explicitly lists `main.rs` as a key file to create: "Binary entry point, tracing init, dispatch, exit codes." Without it, there is no `axiathon` binary, no exit code mapping at the process level, and no command dispatch. The crate is a library only. This is a fundamental gap — the entire CLI framework has no executable.

### [HIGH] F2 — `toml` workspace version is `"0.8"`, not `"0.9"` as specified — `Cargo.toml:49`

The Technical Guardrails state: *"toml 0.9"*. The workspace declares `toml = "0.8"`. While 0.8 works, this contradicts the spec. If the architecture decision was deliberate (e.g., 0.9 doesn't exist yet), it should be documented. As-is, it's a spec violation.

### [HIGH] F3 — `RawConfig` silently ignores unknown fields (no `deny_unknown_fields`) — `config.rs:8-13`

`#[serde(default)]` on `RawConfig` without `#[serde(deny_unknown_fields)]` means a typo in the config file (e.g., `api_ur = "..."`) is silently ignored and defaults are used. The test `config_handles_unknown_fields_gracefully` at `config_loading.rs:163-178` explicitly doesn't assert any behavior — it does `let _ = ...`, which is a vacuous non-assertion. An operator with a typo in their config gets default `localhost:8080` with no warning. This is a config safety issue per the review checklist.

### [MEDIUM] F4 — `output.rs` uses `expect()` 6 times in production code — `output.rs:96,104,109,111,113,114`

The Rust rules state: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` messages here are descriptive, but `render_csv` and `render_json` could theoretically fail on malformed input. These functions return `String`, not `Result`, so the panics are baked in. For a CLI tool, a panic on CSV serialization of user data is a poor user experience. Should return `Result<String, CliError>`.

### [MEDIUM] F5 — `keyring` dependency listed in story spec but absent from implementation

AC-7 and the Technical Guardrails require: *"Credential storage: OS keychain via `keyring` crate. Load token at CLI startup in sync context BEFORE entering Tokio runtime."* The `keyring` crate is not in workspace dependencies nor in `axiathon-client/Cargo.toml`. The `ClientConfig::token()` method hardcodes `None`. While actual login is Story 9.1, the infrastructure (keyring dependency, sync-context loading pattern) is specified for this story.

### [MEDIUM] F6 — `init.rs` is an empty file (comment only) — `commands/init.rs:1`

AC says `axiathon init` should be "functional, not stub." The file contains only `// Init command — first-time setup (functional, not stub)`. There's no function, no implementation, no stub handler. The `Init` variant in `Commands` enum has no dispatch. This is less implemented than the stub commands.

### [MEDIUM] F7 — No `Completion` shell type validation using `clap::ValueEnum` — `cli.rs:108-111`

The `Completion` command takes `shell: String` instead of a typed enum. `clap_complete::Shell` implements `ValueEnum` and could be used directly, giving clap automatic validation and tab-completion of shell names. Currently, invalid shell names silently produce empty output (per `completion.rs:14`), which is poor UX per AC-9. The AC says "generates static completions" — an invalid shell should error, not silently succeed.

### [MEDIUM] F8 — `ServerError` Display leaks internal details — `error.rs:7`

`#[error("Server error occurred")]` is safe, but `ServerError(String)` stores the raw server message. The `Display` impl ignores the inner string (good for security), but `Debug` will print it. If any error path logs at debug level or if `{err:?}` is used in user-facing output, internals leak. The test at `exit_codes.rs:102-111` correctly verifies Display doesn't leak, but there's no test that Debug output isn't accidentally sent to the user.

### [LOW] F9 — `cargo +nightly fmt --all --check` fails — `cli.rs`

Per the gotchas sidecar: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not."* The formatting diff shows `cli.rs` needs reformatting of imports and long `#[command(...)]` attributes.

### [LOW] F10 — `tenant` flag uses raw `String` instead of validated `TenantId` — `cli.rs:33`

The Rust rules mandate: *"Newtypes for IDs: `TenantId(String)` — prevents mixing ID types."* The `--tenant` flag accepts any string. While full validation may be deferred to the server, accepting `--tenant ""` or `--tenant "../../"` at the CLI level with no validation is a weak trust boundary.

## Verdict: **CHANGES_REQUESTED**

Three High-severity findings block approval:

1. **No `main.rs`** — the story's primary deliverable (a working `axiathon` binary) doesn't exist. There is no executable entry point, no command dispatch, no exit code process handling.
2. **`toml` version mismatch** — spec says 0.9, impl has 0.8. Needs alignment or documented rationale.
3. **Silent config field ignoring** — unknown fields in `cli.toml` are silently dropped with no warning. A typo in `api_url` → `api_ur` gives the operator `localhost:8080` with zero feedback.

The implementation quality of what *is* present is solid — clean error types, proper header injection prevention, good test coverage of the SiemClient and output formatting. But the missing binary entry point is a showstopper; without `main.rs`, this is a library, not a CLI.
