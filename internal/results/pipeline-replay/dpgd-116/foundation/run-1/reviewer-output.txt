## Findings

### `[HIGH]` Nightly rustfmt violations — 4 diffs at `main.rs:4`, `output.rs:1`, `completion.rs:35`, `cli_structure.rs:16`

Per project gotchas: "Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval." Four formatting violations exist: import ordering in `main.rs` and `output.rs`, function signature wrapping in `completion.rs`, and array literal formatting in `cli_structure.rs`. These are mechanical fixes but are a blocking quality gate.

### `[MEDIUM]` `SiemClient` never produces `ConnectionTimeout` — `client.rs:52-66`

The `CliError::ConnectionTimeout` variant exists in the error enum but `SiemClient::get()` never produces it. All network errors (including timeouts) map to `ServerUnavailable`. The `reqwest::Client` is constructed with `Client::new()` which uses default timeouts, and timeout errors are indistinguishable from connection failures in the current error mapping at line 66. The `ClientConfig.timeout` field is loaded but never wired into the reqwest client builder. This means `ConnectionTimeout` is dead code and the configured timeout is silently ignored.

### `[MEDIUM]` Table/CSV formatters silently skip non-object rows — `output.rs:51`, `output.rs:104`

Both `TableFormatter::format()` and `CsvFormatter::format()` use `if let serde_json::Value::Object(map)` which silently drops any row that serializes to a non-object JSON value (e.g., a tuple struct, a primitive). No warning is emitted, no error returned. A caller passing `Vec<String>` would get headers with zero rows and no indication why.

### `[MEDIUM]` `toml` workspace version is `0.8`, story specifies `0.9` — `Cargo.toml:50`

The story's Technical Guardrails section explicitly specifies `toml 0.9`. The workspace declares `toml = "0.8"`. This is likely because `toml 0.9` doesn't exist yet (latest is 0.8.x), so the story spec is aspirational. Noting the discrepancy for traceability.

### `[MEDIUM]` `tenant` field uses raw `Option<String>`, not `TenantId` newtype — `cli.rs:31`, `client.rs:8`

The project's Rust rules mandate newtypes for IDs: "`TenantId(String)` — prevents mixing ID types." Both `Cli::tenant` and `SiemClient::tenant_id` use raw `Option<String>`. While clap integration with newtypes requires extra work, this allows passing any string as a tenant ID without validation at the CLI boundary. The `axiathon-core` crate already defines `TenantId`.

### `[MEDIUM]` Config silently accepts unknown fields including `token` — `config.rs:17-44`

Config uses `toml::Table` (generic map) rather than a typed struct with `#[serde(deny_unknown_fields)]`. A config file containing `token = "secret"` is silently accepted and ignored. While `token()` always returns `None` (correct security decision), the operator gets no warning that their config file has a field that will never be used. The test `config_handles_unknown_fields` at `config_loading.rs:226` explicitly passes with no assertion — just "didn't panic." This is a vacuous test.

### `[LOW]` `init` command only creates directory, doesn't write a default config file — `init.rs:10-22`

`axiathon init` creates `~/.config/axiathon/` but doesn't write a skeleton `cli.toml`. The operator gets "Initialized Axiathon CLI configuration at ~/.config/axiathon/cli.toml" printed, but no file exists at that path. The message is misleading — it implies a config file was created.

### `[LOW]` Stub story references use placeholder "6.X" — `main.rs:22`, `main.rs:27`

`Commands::Rules` maps to `"6.X"` and `Commands::Tenant` maps to `"6.X"`. AC-10 requires stubs to reference specific story numbers. These should be specific (e.g., "6.X" should indicate the actual story number for rules/tenant commands).
