# Story 6.1 CLI Framework — Adversarial Code Review

## Findings

### [HIGH] No `main.rs` binary entry point — `cli.rs:1`

The story explicitly requires `main.rs` as the "Binary entry point, tracing init, dispatch, exit codes." There is no `main.rs` in `crates/axiathon-client/src/`. The `Cargo.toml` has no `[[bin]]` section and the crate name is `axiathon-client`, not `axiathon`. Without `main.rs`, there is **no binary produced**, meaning the entire CLI is a library with no runnable artifact. The story's AC-3 exit code logic (`std::process::exit()`), AC-1 (`axiathon --help`), and AC-10 (stub handlers printing to stderr) are all untestable in their intended form.

### [HIGH] `cargo +nightly fmt --all --check` fails — 476 lines of diff

Per the reviewer gotchas sidecar: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not." The code has 476 lines of formatting diff, primarily import ordering issues across every file. This must be fixed before merge.

### [MEDIUM] `RawConfig` silently ignores unknown fields — `config.rs:18`

The `RawConfig` struct uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. If a user has a typo like `servre_url = "..."`, TOML parsing succeeds silently and the default is used. This is a usability footgun — operator thinks they configured the server URL but it was silently ignored. The `token` field is intentionally ignored (documented), but all other unknown fields should be caught.

### [MEDIUM] `--server` flag does not read `AXIATHON_SERVER` env var — `cli.rs:33`

AC-5 states: "`--server` supports `AXIATHON_SERVER` env var." The `--server` flag has no `env = "AXIATHON_SERVER"` attribute. The config module uses `AXIATHON_API_URL` for a different purpose (config file override), but the CLI-level `--server` flag is disconnected from any env var. This is an AC violation.

### [MEDIUM] `with_token`/`with_tenant` silently discard invalid values — `client.rs:38-49`

When `is_header_safe()` returns false, the builder methods silently do nothing — no error, no warning, no log. The caller has no way to know their token was rejected. A `Result` return or at minimum a `tracing::warn!` would be appropriate. As-is, an operator with a corrupted token from a keychain would get silent auth failures with no diagnostic path.

### [MEDIUM] `SiemClient` only implements `get()` — `client.rs:73`

The client only has a `get()` method. While this is a framework story, several stub commands (rules create/update/delete, alerts acknowledge, ingest start/stop) will need POST/PUT/DELETE. The architecture mentions a wrapper — having only GET means every future story must extend SiemClient, which is fine, but the current test suite only validates GET flows.

### [MEDIUM] `OutputFormatter` is not a trait — `output.rs:15`

AC-4 specifies: "The `OutputFormatter` trait provides consistent formatting across all command groups." The implementation is a concrete struct, not a trait. This means commands cannot be tested with a mock formatter, and the architecture's intent for polymorphic formatting is not met.

### [LOW] Env var tests use `set_var`/`remove_var` without synchronization — `config_loading.rs:98`

`std::env::set_var` is not thread-safe. If tests run in parallel (which they do by default in `cargo test`), these tests can interfere with each other or other tests reading environment variables. Should use a serial test mechanism or scoped env var approach.

### [LOW] `toml` dependency version mismatch with story spec — `Cargo.toml:21`

Story spec says `toml` 0.9, `Cargo.toml` has `toml = "0.8"`. Minor, but if the spec was written for 0.9 features, this could matter.

### [LOW] `expect()` calls in output formatting — `output.rs:79,85,86,90,91`

Five `expect()` calls in `format_as_json` and `format_as_csv`. Per project rules: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect()` messages are present but these are in a library used by a not-yet-existing binary. If CSV write fails (e.g., out of memory), the binary panics instead of returning a clean error. These should return `Result`.

### [VERIFIED] CWE-209 protection — `error.rs:47-74`

`ServerErrorDetail` wraps the raw server message but its `Display` impl only outputs "server error". The raw body is captured via `Debug` for internal logging but never shown to users through the Display chain. Correctly implemented.

### [VERIFIED] Header injection (CWE-113) — `client.rs:24-27`

`is_header_safe()` checks for `\n`, `\r`, and `\0` — the three injection vectors for HTTP headers. Combined with reqwest's own header validation, this is adequate.

### [VERIFIED] `#![forbid(unsafe_code)]` present — `lib.rs:2`

### [VERIFIED] Credential not in Debug output — `client.rs:13-21`

`SiemClient` implements `Debug` manually, showing `has_token` boolean instead of the actual token value.

### [VERIFIED] Config token field ignored — `config.rs:21`

`RawConfig` has a `token` field that is deserialized but never transferred to `ClientConfig`. Token stays in OS keychain only.

## Verdict: **CHANGES_REQUESTED**

### Blocking Issues (2)

1. **No `main.rs`** — The story requires a binary entry point. Without it, there is no `axiathon` binary and AC-1/AC-3/AC-10 cannot function as specified.
2. **Nightly fmt fails** — 476 lines of formatting diff. Per project gotchas, this blocks approval.

### Required Before Approval (3)

3. `--server` flag must support `AXIATHON_SERVER` env var (AC-5 violation)
4. Silent discard on header injection should at minimum log a warning
5. `RawConfig` should use `#[serde(deny_unknown_fields)]` (with explicit `token` handling)
