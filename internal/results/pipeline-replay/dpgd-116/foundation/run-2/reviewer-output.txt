## CRITICAL Findings

### `[CRITICAL]` No `main.rs` — binary cannot be built

**crates/axiathon-client/src/** — `main.rs` does not exist. No `[[bin]]` section in `Cargo.toml`.

The story spec explicitly requires: *"`axiathon-client` crate producing binary `axiathon`"* and AC-3 states *"main.rs catches errors and calls `std::process::exit()`"*.

Without `main.rs`, there is:
- No binary entry point — operators cannot run `axiathon status`
- No command dispatch logic (`Commands` enum → handler functions)
- No tracing initialization
- No error-to-exit-code wiring (`CliError::exit_code()` → `std::process::exit()`)
- No TTY detection for default output format

**All 100 tests pass by calling library functions directly, bypassing the entire command dispatch path.** This is a false confidence signal — the system is untested end-to-end.

### `[CRITICAL]` Missing `logout` handler — `commands/mod.rs` has no logout module

**crates/axiathon-client/src/commands/mod.rs:1-10** — The `Commands::Logout` variant exists in `cli.rs:102` but there is no `commands/logout.rs` and no `pub mod logout` in `mod.rs`. When `main.rs` is added and attempts to dispatch `Commands::Logout`, there will be no handler to call. No test covers logout.

## HIGH Findings

### `[HIGH]` `ServerError` Display leaks raw server response body — CWE-209

**crates/axiathon-client/src/error.rs:24** — `#[error("server error ({0}): {1}")]` where `{1}` is the raw HTTP response body. A 500 response could contain HTML error pages, stack traces, internal paths, or database errors. The `/// **SECURITY:**` doc comment claims Display is sanitized for user output, but `ServerError` passes through unfiltered server content.

```rust
#[error("server error ({0}): {1}")]
ServerError(u16, String),
```

The test at `security_integration.rs:43-57` only checks for `<html` and `<div` tags — but server error bodies commonly contain paths like `/var/app/...`, SQL errors, or Java/Python stack traces that wouldn't contain those specific tags.

### `[HIGH]` Config silently accepts unknown fields including `token`

**crates/axiathon-client/src/config.rs:9** — `ConfigFile` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. AC-8 says *"Tokens in OS keychain, NOT config file"*, but the config parser will silently accept and ignore a `[server] token = "secret"` field.

The test at `config_loading_integration.rs:153-181` verifies the token isn't *exposed* through the `server_url()` getter, but the real risk is that an operator puts their token in the config file thinking it works, and it's stored in plaintext on disk with no warning. The config should either:
1. Reject unknown fields with `#[serde(deny_unknown_fields)]`, or
2. Warn when a `token` field is present

### `[HIGH]` `with_env_overrides()` skips URL validation

**crates/axiathon-client/src/config.rs:112-121** — `AXIATHON_API_URL` env var override is applied without calling `validate_url()`. An operator could set `AXIATHON_API_URL=javascript:alert(1)` and bypass the config file validation entirely. Same issue for CLI overrides at line 125-133.

### `[HIGH]` `init` stub contradicts AC — should be functional

**crates/axiathon-client/src/commands/init.rs:3-4** — Returns `NotImplemented("Story 6.1")`. But AC-10 scope says *"axiathon init first-time setup (functional, not stub)"*. The stub references its own story (6.1), creating a circular dependency — the story can't be complete if a feature it should deliver is marked as "not implemented in this story."

## MEDIUM Findings

### `[MEDIUM]` Output formatter uses `.expect()` in 5 places — panics in production

**crates/axiathon-client/src/output.rs:89, 95, 98, 100, 101-102** — The render_csv and render_json methods use `.expect()` for CSV writes and JSON serialization. Per project rules (`rust.md`): *"No `unwrap()` in production code — use `?` or `expect()` with actionable message"*. While `expect()` is technically allowed, these are in output formatting paths that take user-supplied data. If a row contains data that somehow breaks the CSV writer, the CLI panics instead of returning a user-friendly error.

### `[MEDIUM]` `toml` dependency version mismatch — `Cargo.toml` says `0.8`, story spec says `0.9`

**crates/axiathon-client/Cargo.toml:21** — `toml = "0.8"` but the Technical Guardrails section says `toml 0.9`. This may be intentional if 0.9 isn't released yet, but should be documented.

### `[MEDIUM]` Unused import warning in test

**crates/axiathon-client/tests/config_loading_integration.rs:8** — `use std::io::Write;` is unused. This will fail CI if warnings are errors for test code.

### `[MEDIUM]` `SiemClient` only has `get()` — no POST/PUT/DELETE

**crates/axiathon-client/src/client.rs** — Only `get()` is implemented. Stories 6.3-6.6 will need write operations. While acceptable for a stub phase, the `SiemClient` won't support `axiathon config set`, `axiathon rules create`, `axiathon alerts acknowledge` without these methods. The error mapping and header injection logic will need to be duplicated or extracted.

### `[MEDIUM]` `NotFound` error leaks full URL with server hostname

**crates/axiathon-client/src/client.rs:93** — `Err(CliError::NotFound(url))` where `url` is the full constructed URL. This reveals internal server infrastructure to the operator. Not a major risk for a CLI tool (the operator knows the server), but deviates from the security comment's intent.
