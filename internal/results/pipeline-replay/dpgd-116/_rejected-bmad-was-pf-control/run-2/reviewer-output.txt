## Code Review Findings — Story 6.1: CLI Framework & Structure

**Files Reviewed:** 16 source files across `crates/axiathon-client/src/` + workspace `Cargo.toml`

---

### HIGH Severity

**[HIGH] H1 — CWE-113: Header injection via unsanitized `tenant_id` and `token`**
`client.rs:79-84` — `inject_headers` passes user-controlled `tenant_id` and `token` values directly into HTTP headers via `req.header()`. While reqwest 0.12 rejects bare `\r\n` in `HeaderValue::from_str`, the `impl Into<String>` constructors on `with_tenant`/`with_token` (lines 38-47) accept arbitrary strings with no validation. A tenant ID containing non-ASCII or non-visible characters could bypass reqwest's checks depending on the `HeaderValue` constructor path used. Add explicit validation in `with_tenant`/`with_token` to reject values containing control characters (`\r`, `\n`, `\0`).

**[HIGH] H2 — CWE-209: Server response bodies leaked to users in error messages**
`client.rs:95-104` — `map_response` captures the full `resp.text()` body and embeds it in error variants like `ServerError(body)`, `NotFound(body)`, `AuthenticationExpired(body)`. Then `main.rs:22` prints these via `eprintln!("Error: {e}")`. The `error.rs` doc comment explicitly warns "Display output is for internal logging only. Sanitize before showing to end users" but `main.rs` violates this by printing `Display` output directly. Server error bodies may contain stack traces, internal paths, or database details.

**[HIGH] H3 — Hardcoded `Retry-After` value ignores actual server header**
`client.rs:100-102` — `TOO_MANY_REQUESTS` response maps to `RateLimited { retry_after_secs: 60 }` with a hardcoded 60s. The actual `Retry-After` header from the server is discarded. This makes the retry logic completely fictional and could cause clients to either hammer the server (if actual backoff is >60s) or wait unnecessarily.

### MEDIUM Severity

**[MEDIUM] M1 — Config silently ignores unknown fields (typos go undetected)**
`config.rs:18` — `ClientConfig` derives `Deserialize` without `#[serde(deny_unknown_fields)]`. A config file with `api_ulr = "..."` (typo) will be silently accepted, and the user gets the default `http://localhost:8080` with no warning. This is a common source of hard-to-debug misconfiguration.

**[MEDIUM] M2 — Invalid `AXIATHON_TIMEOUT` env var silently ignored**
`config.rs:82-84` — If `AXIATHON_TIMEOUT=banana`, the parse fails silently and the file/default value is used. The user has no indication their env var was rejected. Should at minimum log a warning or return an error.

**[MEDIUM] M3 — Duplicate `Format`/`OutputFormat` types with no bridging**
`cli.rs:57` defines `Format { Table, Json, Csv }` and `output.rs:16` defines `OutputFormat { Table, Json, Csv }`. There is no `From<Format> for OutputFormat` conversion. When real commands need to use `OutputFormatter` with the CLI's `--format` flag, there's no type-safe bridge. This will force ad-hoc matching or `unsafe` transmutation patterns in future stories.

**[MEDIUM] M4 — `write_table` hardcodes `stdout().is_terminal()` check instead of using writer**
`output.rs:138` — `self.no_color && std::io::stdout().is_terminal()` checks the real stdout even when writing to an arbitrary `&mut dyn Write`. If the writer is a file or buffer but stdout is a TTY, the table gets styling it shouldn't. The terminal detection should be done at format selection time, not inside the writer.

**[MEDIUM] M5 — `tenant` flag is `Option<String>` instead of validated newtype**
`cli.rs:37` — The project's Rust coding rules mandate "Newtypes for IDs: `TenantId(String)` — prevents mixing ID types." The `--tenant` flag accepts raw `String`. While validation at the CLI boundary is reasonable for clap parsing, there should be immediate conversion to `TenantId` after parse.

**[MEDIUM] M6 — No async runtime in `main.rs` but `SiemClient` methods are all `async`**
`main.rs` has no `#[tokio::main]` and `run()` is sync, but `SiemClient::get`/`post` are `async`. When future stories implement the actual commands, they'll need to retrofit async into main. This is an architectural mismatch that should be documented or preemptively addressed.

**[MEDIUM] M7 — `toml` version mismatch between workspace and dev summary**
`Cargo.toml:50` specifies `toml = "0.8"` but the dev output summary claims `toml 0.9`. The code works with 0.8, but the documentation is inaccurate.

### LOW Severity

**[LOW] L1 — `handle_with_dir` accepts `&PathBuf` instead of `&Path`**
`init.rs:65` — Rust convention (and clippy lint `ptr_arg`) prefers `&Path` over `&PathBuf`. This is a minor API cleanliness issue.

**[LOW] L2 — No test coverage for `SiemClient` error mapping logic**
`client.rs` tests only cover construction and builder chain. The `map_response` and `map_reqwest_error` methods — the most security-critical code in the file — have zero test coverage. These are async and hard to unit test without a mock server, but the gap should be acknowledged.

**[LOW] L3 — No test coverage for `OutputFormatter::format_value`**
`output.rs:112` — `format_value` method has no test. It behaves differently for JSON (wraps in metadata envelope) vs Table/CSV (just pretty-prints JSON), but neither path is tested.

**[LOW] L4 — No test for `ClientConfig::load_with_overrides`**
`config.rs:90` — The orchestrating method that combines file loading + env overrides is untested. Individual parts are tested but not the composition.

**[LOW] L5 — `ResponseMetadata::request_id` uses UUID v4, project rules prefer v7**
`output.rs:69` — Project rules state "UUID v7 for time-ordered IDs." While `request_id` isn't a domain entity ID, using v7 would provide chronological ordering for debugging. Minor inconsistency with project conventions.

**[LOW] L6 — `exit_code 2` (usage error) documented in AC but not in constants**
`error.rs` has constants for 0, 1, 3, 4 and a comment that "EXIT_USAGE (2) is handled automatically by clap." This is correct behavior but the comment should note that clap uses exit code 2 for parse failures, making the coverage implicit.

**Key Concerns:**
1. The header injection and error information disclosure issues (H1, H2) are real security risks that will carry into production if not addressed before the client sends real HTTP traffic.
2. The silent config failure modes (M1, M2) will cause hard-to-diagnose operational issues.
3. Test coverage gaps in the HTTP client error mapping (L2) and output formatting (L3) leave the most complex logic unverified.

## Verdict: **CHANGES_REQUESTED**

The three HIGH findings — header injection surface, server error body leakage to users, and hardcoded retry-after — represent real security and correctness risks. H1 and H2 should be fixed before merge. H3 and the MEDIUM items can be tracked as follow-up tasks if the team prefers, but H1 and H2 are blocking.
