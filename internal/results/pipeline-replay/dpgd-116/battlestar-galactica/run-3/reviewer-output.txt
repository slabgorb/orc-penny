# Story 6.1 Review: CLI Framework & Structure

## Review Findings

### [CRITICAL] CWE-209: `ServerError` Display leaks internal details — `error.rs:25`

The `ServerError` variant's `Display` impl is `#[error("server error — please try again later")]` which looks safe, BUT the actual `ServerError(String)` payload is **not** used in the Display output. However, **the security test at `security.rs:20-29` FAILS**. The test creates `CliError::ServerError("internal: database connection pool exhausted at 10.0.0.5:5432")` and asserts the Display output does NOT contain "10.0.0.5". But wait — the `#[error]` attribute on `ServerError` is `"server error — please try again later"` which does NOT interpolate `{0}`. So the Display output won't contain the IP. BUT: the `Display` impl says `"server error — please try again later"` while the inner string is silently discarded. This means the `ServerError` variant carries detail that's never shown to users — which is fine for security but means the inner string is dead data. **Actually, this is VERIFIED GOOD for CWE-209**. However, the inner string is still used in `map_status_code` at `client.rs:86` (`CliError::ServerError(format!("HTTP {s}"))`) — this detail is captured but never displayed. Not a vulnerability, but a code smell.

**Verdict:** Not blocking. `[VERIFIED]` CWE-209 is handled correctly — Display doesn't leak internals.

### [HIGH] `main.rs` is a no-op stub — does not wire CLI to handlers — `main.rs:3-5`

```rust
fn main() {
    std::process::exit(0);
}
```

The `main.rs` does **nothing**. It doesn't parse CLI args, dispatch commands, initialize tracing, load config, or call any handler. This means:
- `axiathon --help` won't work from the binary
- No exit code mapping is wired
- No error-to-stderr behavior exists
- The binary is a hollow shell

AC-3 (exit codes via `std::process::exit`), AC-8 (config loading at startup), and the credential-loading-before-tokio requirement from the story are all unimplemented at the integration level. The unit tests pass because they test library code directly, not the binary entry point.

### [HIGH] `with_server_override` skips URL validation — `config.rs:108-113`

```rust
pub fn with_server_override(mut self, server: Option<&str>) -> Self {
    if let Some(url) = server {
        self.api_url = url.into();
    }
    self
}
```

CLI `--server` flag bypasses `validate_url()`. A user could pass `--server "ftp://evil.com"` or `--server "javascript:alert(1)"` and it would be accepted without validation. All other URL entry points (`from_raw`, `from_file_with_env`) validate. This is an inconsistency that breaks the precedence security guarantee.

### [HIGH] `RawConfig` silently ignores unknown fields — `config.rs:17-22`

```rust
#[derive(Debug, Deserialize)]
struct RawConfig {
    api_url: Option<String>,
    timeout: Option<u64>,
    // Ignore unknown fields (including "token") silently
}
```

Serde's default is `#[serde(deny_unknown_fields)]` is OFF, meaning any unknown key is silently ignored. The comment says this is intentional for "token", but this means typos like `api_rul` or `tmeout` are silently ignored and the user gets defaults without knowing their config is wrong. This is a configuration footgun. At minimum, warn on unknown fields; at best, use `#[serde(deny_unknown_fields)]` and explicitly handle `token` with a deprecation warning.

### [MEDIUM] `with_token`/`with_tenant` silently drop invalid values — `client.rs:24-36`

```rust
pub fn with_token(mut self, token: String) -> Self {
    if is_safe_header_value(&token) {
        self.token = Some(token);
    }
    self  // silently returns without token
}
```

If a token contains `\r\n` (header injection), it's silently dropped. The caller has no way to know the token was rejected. This should return a `Result` or log a warning. Silent failure here means a legitimate token with an accidental encoding issue would cause mysterious 401 errors with no diagnostic path.

### [MEDIUM] Missing `logout` command in CLI — `cli.rs:47-84`

AC-1 explicitly requires: "login/logout". The `Commands` enum has `Login` but no `Logout` variant. The help text won't show `logout` as a command.

### [MEDIUM] Missing `tui` command in CLI — `cli.rs:47-84`

AC-1 explicitly requires the `tui` command group to appear in `axiathon --help`. It's absent from the `Commands` enum.

### [MEDIUM] `wiremock` not declared as workspace dependency — `Cargo.toml:35`

```toml
wiremock = "0.6"
```

All other dependencies use workspace declarations. `wiremock` is declared inline, violating the workspace dependency management pattern established in the root `Cargo.toml`.

### [MEDIUM] `#[non_exhaustive]` test is vacuous — `exit_codes.rs:175-192`

The `cli_error_is_non_exhaustive` test matches all known variants plus `_ => {}`. This test would compile and pass **even without** `#[non_exhaustive]` on the enum, because the wildcard arm is always valid. The test doesn't actually verify the attribute exists. The `security.rs:231-236` `include_str!` approach would be more reliable here.

### [MEDIUM] `OutputFormatter` uses `expect()` (panics) in production code — `output.rs:63-69`

```rust
wtr.write_record(headers).expect("write CSV header");
```

The `CsvFormatter::format()` method uses five `expect()` calls. If `format()` is called with data that causes a CSV writing error (e.g., interior I/O error on the `Vec<u8>` writer — unlikely but contractually wrong), this panics in production. The return type should be `Result<String, CliError>` per the project's "no `unwrap()` in production code" rule.

### [LOW] Nightly `rustfmt` import ordering fails — `cli.rs:3-9`

`cargo +nightly fmt --all --check` fails. Imports in `cli.rs` are not in the order nightly rustfmt expects (`clap`/`clap_complete` should come before `crate::` imports). Per the reviewer gotchas, this must be flagged before approval.

### [VERIFIED] Header injection (CWE-113) prevention exists at `client.rs:99-102`

The `is_safe_header_value` function rejects `\n`, `\r`, and `\0`. Tests in `security.rs:49-93` verify this behavior for both tenant and token. Correctly implemented.

### [VERIFIED] Token not in config file — `config.rs:18-22`, `security.rs:156-177`

`RawConfig` has no `token` field. The test verifies that even if `token` appears in the TOML, it doesn't leak into `ClientConfig`'s Debug output. Correctly implemented.

### [VERIFIED] Exit code mapping is correct — `error.rs:44-49`

AuthenticationExpired → 3, Unauthorized → 4, everything else → 1. Matches AC-3 spec.

### [VERIFIED] `#![forbid(unsafe_code)]` in `lib.rs`, `deny` in Cargo.toml for tests

The crate-level lint is `deny` (not `forbid`) to allow `unsafe { std::env::set_var }` in edition 2024 tests. `lib.rs` has `#![forbid(unsafe_code)]` for production code. This is a well-reasoned split, documented in the Cargo.toml comment.

### [VERIFIED] Clap derive macros used throughout — all command modules

No imperative `Command::new()` calls. All CLI structure uses `#[derive(Parser)]` and `#[derive(Subcommand)]`. Satisfies AC-6.
