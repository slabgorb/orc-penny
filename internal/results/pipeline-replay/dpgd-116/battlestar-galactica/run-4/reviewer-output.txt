### `[HIGH]` Edition mismatch: crate uses `edition = "2021"` while workspace uses `edition = "2024"` at `crates/axiathon-client/Cargo.toml:2`

Every other crate in the workspace uses `edition.workspace = true` (inheriting 2024). This crate hardcodes 2021, breaking workspace consistency and missing 2024 edition features. The `rust.md` rules explicitly state `Edition 2024, MSRV 1.85+`.

### `[HIGH]` `cargo +nightly fmt --all --check` fails with 563 lines of diff

Per `gotchas.md`: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not." The implementation has widespread import ordering and formatting violations. This is a blocking quality gate per project rules.

### `[HIGH]` `apply_env_overrides` silently swallows invalid env var values at `config.rs:88-97`

When `AXIATHON_API_URL` is set, it's accepted without any `validate_url()` call. A user could set `AXIATHON_API_URL=ftp://evil.com` and bypass the URL scheme validation that `from_toml_str` enforces. Similarly, `AXIATHON_TIMEOUT` silently ignores unparseable values AND skips `validate_timeout()` on parsed values — a timeout of `0` or `999999` from env var would be accepted despite being rejected from the config file.

### `[HIGH]` No `main.rs` binary entry point exists

The story explicitly requires creating `main.rs` as the binary entry point. The `Cargo.toml` has no `[[bin]]` section and no `src/main.rs`. There is no binary to run. AC-3 specifies `main.rs` catches errors and calls `std::process::exit()` — this entire flow is unimplemented. Without it, the `axiathon` binary cannot be built.

### `[MEDIUM]` `generate_completion` silently returns empty output on invalid shell at `commands/completion.rs:10-11`

When an invalid shell string is passed, the function silently returns without writing anything to the buffer. No error, no message to stderr. AC-9 says `axiathon completion <shell>` should generate completions. A typo like `axiathon completion bsh` would produce silent nothing. This should return a `CliError` variant so the caller can exit with code 1.

### `[MEDIUM]` Workspace dependency version mismatches vs story guardrails

The story specifies `dirs` 6, `toml` 0.9, and `reqwest` with `rustls-tls` feature. The workspace declares `dirs = "5"`, `toml = "0.8"`, and `reqwest` with only `json` (no `rustls-tls`). The `rustls-tls` omission means the binary defaults to OpenSSL (or no TLS), which contradicts the architecture decision for a hermetic build with vendored TLS.

### `[MEDIUM]` `keyring` crate not added to workspace dependencies

Story requires `keyring` 3 in workspace dependencies for OS keychain credential storage. It's completely absent. While the actual login flow is Story 9.1, the infrastructure (dependency declaration) was explicitly called out as Story 6.1 scope.

### `[MEDIUM]` `default_headers` silently drops invalid header values at `client.rs:91-103`

If `tenant` or `bearer` contain values that `HeaderValue::from_str` rejects, the code silently omits the header. This means a request could be sent without the tenant isolation header, potentially accessing wrong-tenant data. The `try_with_tenant`/`try_with_token` validators exist but `with_tenant`/`with_token` bypass them — and `default_headers` has no defense-in-depth logging for the silent drop.
