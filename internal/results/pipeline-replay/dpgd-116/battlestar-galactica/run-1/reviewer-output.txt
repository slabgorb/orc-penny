## Observations

### 1. `[CRITICAL]` Missing `main.rs` — No binary entry point exists

**`crates/axiathon-client/src/main.rs`** does not exist. The story explicitly requires "the `axiathon-client` crate producing the `axiathon` binary" and the Technical Architecture specifies `main.rs` as "Binary entry point, tracing init, dispatch, exit codes." Without `main.rs`:

- There is no `axiathon` binary — `cargo build -p axiathon-client` produces only a library, not an executable.
- There is no command dispatch logic (the `match cli.command { ... }` that routes to handlers).
- There is no exit code wiring via `std::process::exit(err.exit_code())`.
- There is no tracing initialization.
- AC-3 (exit codes applied at process level) is structurally unverifiable without this file.

This is the single most important file in the story — it's the glue between clap parsing and command execution.

### 2. `[HIGH]` `ServerError` Display leaks internal details (CWE-209)

At `error.rs:12-13`:
```rust
#[error("server error")]
ServerError(String),
```

The `#[error("server error")]` attribute means `Display` prints only "server error" — the inner `String` is silently discarded. This is safe from CWE-209 but creates a **different problem**: the error message stored in the `String` (e.g., "HTTP 502") is lost at the Display layer. Operators get zero diagnostic information. The test at `exit_codes.rs:100-111` (`cli_error_display_does_not_leak_server_internals`) is **vacuous** — it only checks `!display.is_empty()`, which will always pass for any `#[error]` attribute. The test does not actually verify that internal details are suppressed; it just checks the string is non-empty. This is a rubber-stamp assertion.

Meanwhile, `NotFound` at line 15 **does** leak: `#[error("not found: {0}")]` exposes the full URL (including internal hostnames/ports) to the operator. The `SiemClient` feeds it the full URL at `client.rs:78`: `CliError::NotFound(url)` where `url = format!("{}{path}", self.base_url)`. An operator running against `http://10.0.0.5:8080` sees that internal address in the error message.

### 3. `[HIGH]` Token not sanitized for header injection (CWE-113)

At `client.rs:27-33`, tenant ID is sanitized by stripping CR/LF. Good. But at `client.rs:51`:
```rust
req = req.header("Authorization", format!("Bearer {token}"));
```
The `token` string is **not sanitized**. If a malicious or corrupted token contains `\r\n`, it could inject headers. The test at `siem_client.rs:243-257` (`siem_client_rejects_newlines_in_token`) is **vacuous** — it asserts `result.is_err() || result.is_ok()` which is a tautology that always passes. This test proves nothing.

Note: reqwest's `header()` method does reject invalid header values at runtime, so exploitation is unlikely. But the code relies on an implicit library guarantee rather than explicit defense, and the test gives false confidence.

### 4. `[HIGH]` Config silently accepts unknown fields — secret leakage risk

At `config.rs:10-11`:
```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct ClientConfig {
```

No `#[serde(deny_unknown_fields)]`. The test at `config_loading.rs:131-155` verifies that `token = "should-be-ignored"` doesn't appear in the serialized output, but the field is silently consumed during deserialization. An operator who puts `token = "my-secret"` in their TOML file gets no warning that the token is being ignored — they think they've configured auth but haven't. This is a configuration safety issue that should at minimum log a warning.

### 5. `[HIGH]` `toml` version mismatch with story spec

The story specifies `toml` 0.9 in the Technical Guardrails. `Cargo.toml:20` uses `toml = "0.8"`. This is a spec deviation. While 0.9 may not exist yet (the story spec may be aspirational), the deviation should be documented.

### 6. `[MEDIUM]` `format_csv` panics on write failure instead of returning `Result`

At `output.rs:69-74`:
```rust
wtr.write_record(headers).expect("CSV header write failed");
```

Five `.expect()` calls in `format_csv()`. The Rust coding rules say "No `unwrap()` in production code — use `?` or `expect()` with actionable message." The `expect()` with messages satisfies the letter of the rule, but writing to a `Vec<u8>` in memory effectively cannot fail, so this is acceptable. Flagging as medium because if the function signature changes to accept a `Write` impl, these panics become real risks.

### 7. `[MEDIUM]` `OutputFormatter` trait defined but never implemented

At `output.rs:48-52`, the `OutputFormatter` trait is defined with three methods. There are free functions `format_table()` and `format_csv()` that do the actual work, but **no struct implements `OutputFormatter`**. The trait exists only to satisfy a test that creates a `MockFormatter`. The story AC-4 says "OutputFormatter trait with Table (comfy-table), JSON (serde_json), CSV implementations" — the implementations don't exist as trait impls.

### 8. `[MEDIUM]` `cargo +nightly fmt --all --check` fails

Per the gotchas sidecar: "Always include `cargo +nightly fmt --all --check` in the preflight." The nightly fmt check shows diffs in `cli.rs:31` and `commands/init.rs:9`. This must be fixed before merge.

### 9. `[MEDIUM]` AC-1 missing `tui` and `logout` commands

AC-1 states: "`axiathon --help` must show all command groups: `query`, `rules`, `alerts`, `ingest`, `config`, `status`, `tenant`, `login`/`logout`, `tui`, `completion`, `init`." The `Commands` enum in `cli.rs` has no `Tui` variant and no `Logout` variant. While `tui` is arguably Epic 4 scope, AC-1 explicitly lists it, and `logout` is listed alongside `login`.

### 10. `[LOW]` `with_env_overrides` silently swallows parse errors

At `config.rs:65`:
```rust
if let Ok(val) = t.parse::<u64>() {
    self.timeout = val;
}
```

If `AXIATHON_TIMEOUT=abc`, the invalid value is silently ignored. The test at `config_loading.rs:120-126` documents this behavior but an operator with a typo in their env var gets no feedback. A warning log would be appropriate.

### 11. `[LOW]` Several workspace dependencies not declared at workspace level

`clap_complete`, `comfy-table`, `csv`, `dirs`, `reqwest`, `toml` are declared directly in the crate `Cargo.toml` rather than in `[workspace.dependencies]`. The story spec says "Add to `[workspace.dependencies]`" for these. This makes version management harder across the workspace.
