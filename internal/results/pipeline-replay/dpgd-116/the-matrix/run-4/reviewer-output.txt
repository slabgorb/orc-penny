## Observations

### CRITICAL

**[CRITICAL] Missing `main.rs` — no binary entry point** at `crates/axiathon-client/src/main.rs` (DOES NOT EXIST)

The story explicitly requires `main.rs` as a "Key File to Create" and Cargo.toml has no `[[bin]]` section. This crate compiles only as a library (`libaxiathon_client.rlib`). There is no `axiathon` binary. Users cannot run `axiathon --help`. The entire CLI framework is inert — config loading, SiemClient, output formatting, error-to-exit-code mapping, command dispatch — none of it is wired together. AC-1 through AC-10 presume a working binary. This is the single most critical gap.

**[CRITICAL] Nightly `rustfmt` fails with 47 diffs** across `config.rs`, `output.rs`, and test files

Per the **Reviewer Gotchas**: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval — don't let it slip to post-merge."* This is a CI gate blocker.

**[CRITICAL] `Commands` enum has no subcommand structures — all unit variants** at `crates/axiathon-client/src/cli.rs:50-99`

Every command (`Query`, `Rules`, `Alerts`, etc.) is a bare unit variant with no associated `Args` struct. AC-2 requires detailed help text, options with defaults, and `after_help` usage examples per command group. Bare unit variants provide none of this. There are no command-specific args (`QueryArgs`, `RulesArgs`, etc.), no subcommands (`axiathon rules list`), and no dispatch handlers.

### HIGH

**[HIGH] No command handler modules — `commands/mod.rs` only exports `completion`** at `crates/axiathon-client/src/commands/mod.rs:3`

AC-10 requires stub handlers for all unimplemented commands that print "not yet implemented (Story X.Y)" and exit with code 1. The required files (`query.rs`, `rules.rs`, `alerts.rs`, `ingest.rs`, `config.rs`, `status.rs`, `tenant.rs`, `login.rs`, `init.rs`) do not exist. The stub handler tests (`tests/stub_handlers.rs`) only test `CliError::NotImplemented` message formatting — they never invoke an actual handler function. These tests would pass even if no handler existed (because they don't test handlers, they test error message strings).

**[HIGH] `with_env_overrides()` silently swallows invalid env var values** at `crates/axiathon-client/src/config.rs:83-89`

Invalid `AXIATHON_TIMEOUT` values (e.g., `"not-a-number"`, `"-5"`, `"999999"`) are silently ignored. The comment even acknowledges this: `// Invalid or out-of-range values are silently ignored (keep current)`. This violates the principle of least surprise. Operators setting `AXIATHON_TIMEOUT=abc` expect an error, not silent fallback. Furthermore, `with_env_overrides` does **not** validate the URL override at all — line 81 blindly accepts any string for `api_url`, bypassing the `validate_url()` check that `from_toml()` applies.

**[HIGH] `with_env_overrides()` bypasses URL validation** at `crates/axiathon-client/src/config.rs:80-82`

`from_toml()` calls `validate_url()` to enforce `http://` or `https://` scheme and max length. But `with_env_overrides()` sets `self.api_url = url.to_string()` directly without validation. An attacker/operator setting `AXIATHON_API_URL=javascript:alert(1)` or `AXIATHON_API_URL=ftp://evil.com` would bypass the URL validation entirely.

**[HIGH] `toml` version mismatch: workspace declares `0.8`, story requires `0.9`** at `Cargo.toml:49`

The story's Technical Guardrails specify `toml 0.9`. The workspace declares `toml = "0.8"`. This should either be updated or explicitly justified.

**[HIGH] `output.rs` uses `expect()` 5 times in production code** at `crates/axiathon-client/src/output.rs:77,82,84,86,87-88`

The project's Rust rules state: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` calls here have messages, but they're in fallible I/O paths (CSV writer writing to a `Vec<u8>`). While writing to a `Vec` won't fail in practice, the `format_csv` and `format_json` methods return `String` not `Result`, making it impossible for callers to handle errors gracefully. These methods should return `Result<String, CliError>`.

### MEDIUM

**[MEDIUM] `RawConfig` accepts unknown TOML fields without warning** at `crates/axiathon-client/src/config.rs:22-27`

`RawConfig` uses default `serde::Deserialize`, which silently ignores unknown keys. If a user has `server_url = "..."` (typo of `api_url`), it will be silently ignored and the default will be used. Adding `#[serde(deny_unknown_fields)]` would catch typos at parse time.

**[MEDIUM] `NotFound` variant leaks its inner string in Display** at `crates/axiathon-client/src/error.rs:17-18`

The `Display` for `NotFound` is `"Resource not found"` (hardcoded, good), but the inner `String` is still stored and accessible via `Debug`. However, the security test at `tests/security.rs:36-43` is **weak**: it creates `CliError::NotFound("/api/v1/internal/admin/users/12345".into())` and checks that the **Display** doesn't contain it, which passes because Display is hardcoded. But the inner string is still there and could be logged via `Debug`. The test gives false confidence.

**[MEDIUM] `ServerError` variant stores but doesn't display its inner string** at `crates/axiathon-client/src/error.rs:23-24`

The Display for `ServerError` is `"Server error — please try again or contact your administrator"` (hardcoded, good for CWE-209). But the `ServerError(String)` inner value is exposed in `Debug` output. If any code path logs errors with `{:?}` instead of `{}`, internal details like IP addresses from `map_http_status` (line 62: `format!("HTTP {status}")`) would leak. This is acceptable but worth noting.

**[MEDIUM] SiemClient does not wrap `reqwest::Client` as specified in AC-7** at `crates/axiathon-client/src/client.rs:8-12`

AC-7 states: *"SiemClient wraps reqwest::Client."* The current `SiemClient` stores `base_url`, `token`, and `tenant_id` as strings but has **no** `reqwest::Client` field. There are no HTTP methods (`get()`, `post()`, etc.). The struct is a data holder, not an HTTP client wrapper.

**[MEDIUM] Stub handler tests are vacuous — they test error message formatting, not handlers** at `crates/axiathon-client/tests/stub_handlers.rs`

Every test constructs a `CliError::NotImplemented("...")` manually and checks its Display output. No test invokes an actual command handler. These tests would pass identically if the Commands enum and handler dispatch didn't exist at all. They test the error type, not the CLI behavior.

### LOW

**[LOW] `config_has_no_token_field` test has weak assertion** at `crates/axiathon-client/tests/config_loading.rs:141-157`

The test parses TOML with a `token` field and checks... nothing meaningful. It calls `config.api_url()` but doesn't assert anything about token absence. The comment says "The type system enforces this" but the test itself doesn't verify anything — it should `assert!(result.is_err())` if `deny_unknown_fields` were used, or explicitly verify the parsed config has no token accessor.

**[LOW] Security tests use `if let Ok(config) = result` pattern** at `crates/axiathon-client/tests/security.rs:96-103,109-117,122-131,136-145`

Four security tests parse invalid configs but use `if let Ok(config)` — meaning if the parser correctly rejects them (returns `Err`), the assertion body is skipped entirely. The test passes vacuously. These should use `assert!(result.is_err())` to **require** rejection, not silently accept it.
