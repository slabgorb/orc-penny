## Findings

### [CRITICAL] Missing `main.rs` — Binary cannot be built (AC-1, AC-3, AC-9, AC-10)
**at `crates/axiathon-client/src/main.rs` (missing)**

There is no `main.rs`. The `Cargo.toml` does not declare `[[bin]]`. This crate is a library only — it **cannot produce the `axiathon` binary**. The story explicitly requires: *"the `axiathon-client` crate producing the `axiathon` binary"* and *"`main.rs` catches errors and calls `std::process::exit()`"*. Without `main.rs`, there is:
- No command dispatch
- No exit code mapping via `std::process::exit()`
- No tracing initialization
- No keyring token loading before Tokio runtime
- No integration between `Cli::parse()`, `SiemClient`, `ClientConfig`, and command handlers

This is the **entire glue layer** of the story. Everything compiles as a library, but nothing is wired together.

### [CRITICAL] Missing `logout` and `tui` commands (AC-1)
**at `crates/axiathon-client/src/cli.rs:65-101`**

AC-1 explicitly states: *"`axiathon --help` must show all command groups: `query`, `rules`, `alerts`, `ingest`, `config`, `status`, `tenant`, `login`/`logout`, `tui`, `completion`, `init`."* The `Commands` enum is missing:
- `Logout` — required per AC-1
- `Tui` — required per AC-1

These must be present as stub commands (like the others), not omitted entirely.

### [HIGH] `cargo +nightly fmt --all --check` fails
**at `crates/axiathon-client/src/cli.rs:3`, `commands/alerts.rs:1`, and others**

Per the gotchas sidecar: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval."* The nightly fmt check shows import ordering violations in multiple files. This blocks merge in CI.

### [HIGH] `--tenant` accepts raw `String` instead of validated `TenantId` (AC-5, Type Safety)
**at `crates/axiathon-client/src/cli.rs:41`**

The `--tenant` flag is `Option<String>`. The project has a validated `TenantId` newtype in `axiathon-core` that enforces UUID format. The story's technical guardrails state the crate depends on `axiathon-core` for shared types. While full validation could happen downstream, the `Cli` struct accepts arbitrary strings including `"evil\r\nHeader: injected"` as tenant IDs. At minimum, the `main.rs` dispatch (which doesn't exist — see Critical #1) should validate this before passing to `SiemClient`.

### [HIGH] `toml` version mismatch — `Cargo.toml` says `0.8`, story spec says `0.9`
**at `crates/axiathon-client/Cargo.toml:20`**

The story's Technical Guardrails specify `toml 0.9` as a key dependency. The implementation uses `toml = "0.8"`. This could cause API incompatibilities with the expected parsing behavior. The workspace `Cargo.toml` does not declare `toml` as a workspace dependency, meaning each crate manages its own version — a violation of the workspace dependency management pattern.

### [HIGH] Several dependencies not declared as workspace dependencies
**at `crates/axiathon-client/Cargo.toml:11-16`**

The story spec says: *"Add to `[workspace.dependencies]`: `reqwest` 0.12, `comfy-table` 7, `keyring` 3, `clap_complete` 4, `dirs` 6, `csv` 1, `toml` 0.9."* None of these were added to the root `Cargo.toml` `[workspace.dependencies]`. Instead, they are declared with inline versions in the crate's `Cargo.toml`. This violates workspace dependency management and means future crates can't share pinned versions.

### [MEDIUM] `ServerError.message` is stored but never surfaced, yet never logged either
**at `crates/axiathon-client/src/error.rs:16` and `client.rs:76-79`**

The `ServerError` variant stores a `message: String` from the server response body. The `Display` impl correctly hides it (good for CWE-209), but the message is also never logged via `tracing`. This means server errors are completely opaque for debugging — operators get `"server error (HTTP 500)"` with no way to diagnose.

### [MEDIUM] `JsonFormatter.request_id` is nanosecond timestamp, not a UUID
**at `crates/axiathon-client/src/output.rs:61`**

AC-4 specifies `ResponseMetadata` with `request_id`. The implementation generates `request_id` as a zero-padded hex nanosecond timestamp. This is not a proper request ID — it's non-unique (two calls in the same nanosecond collide), not trace-correlatable, and inconsistent with `axiathon-core::ApiMeta` which is the server's response format. Should use `Uuid::now_v7()` or similar.

### [MEDIUM] `output.rs` uses `expect()` in 5 places — potential panics in production
**at `crates/axiathon-client/src/output.rs:72,90,91,95,96-97`**

The Rust rules state: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* While `expect()` is used (not `unwrap()`), these are in formatting paths that could fail with unusual inputs (e.g., non-UTF-8 in CSV writer). The `OutputFormatter` trait returns `String`, not `Result<String, _>`, which forces infallible output. This is a design-level concern — the trait should return `Result`.

### [MEDIUM] `init` command is an empty struct — story says it should be functional
**at `crates/axiathon-client/src/commands/init.rs:1-7`**

The story scope says: *"Shell completion generation (functional, not stub)"* and *"`axiathon init` first-time setup (functional, not stub)"*. The `init` command is just an empty `InitArgs` struct with no handler at all — not even a stub. This is below the minimum scope.

### [MEDIUM] `with_env_overrides_from` silently ignores invalid timeout values
**at `crates/axiathon-client/src/config.rs:71-74`**

If `AXIATHON_TIMEOUT=banana`, the method silently keeps the old value. No warning, no log, no error. An operator who sets `AXIATHON_TIMEOUT=5s` (with unit suffix) will silently get the default 30s timeout with no indication their setting was ignored.
