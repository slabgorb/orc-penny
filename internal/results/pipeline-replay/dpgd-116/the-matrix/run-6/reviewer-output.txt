# Code Review: Story 6.1 — CLI Framework & Structure

*Ah, you think you've built a foundation? Let me examine every cause and its effect...*

## Observations

### `[HIGH]` Missing `main.rs` binary entry point — `crates/axiathon-client/src/main.rs`
The story explicitly requires creating a binary entry point (`main.rs`) that catches errors and calls `std::process::exit()` with the correct exit code. No `main.rs` exists, no `[[bin]]` section in Cargo.toml. The crate is a library only — there is no `axiathon` binary being produced. AC-3 requires `main.rs` to map `CliError::exit_code()` to `std::process::exit()`, and AC-10 requires stub handlers to "print and exit with code 1." Without a binary, none of this actually works end-to-end. The exit code tests only test the `exit_code()` method on the enum, not actual process exit behavior.

### `[HIGH]` Missing `keyring` dependency — `crates/axiathon-client/Cargo.toml`
AC-8 requires OS keychain credential storage via the `keyring` crate. The workspace `Cargo.toml` doesn't declare `keyring` in `[workspace.dependencies]`, and `axiathon-client/Cargo.toml` doesn't depend on it. The `SiemClient::new()` accepts a token as `Option<&str>` but there is no mechanism to load tokens from the OS keychain. The story spec says "Load token at CLI startup in sync context BEFORE entering Tokio runtime to avoid deadlocks." This is entirely absent.

### `[HIGH]` Token null byte injection not validated — `crates/axiathon-client/src/client.rs:27-33`
The CRLF injection check on tokens validates `\r` and `\n`, but does NOT check for null bytes (`\0`). The tenant ID validation checks for `\0` (line 36), but the token check is inconsistent — it omits null byte validation. A token containing `\0` would pass the custom validation and only be caught (or not) by `HeaderValue::from_str`. This is an asymmetric security check that should be consistent.

### `[MEDIUM]` `ServerError` Display leaks the HTTP status code but the body is stored and not displayed — `crates/axiathon-client/src/error.rs:26`
The `ServerError(u16, String)` variant stores the response body in its second field, but the `Display` impl only shows "server returned an error (HTTP {0})". While this is good for CWE-209 (the body isn't shown to users), the body is still stored. If this error is ever logged at debug level with `{:?}` (Debug), the raw server body including potential stack traces will appear in logs. The SECURITY doc comment warns about Display, but Debug will bypass this.

### `[MEDIUM]` `expect()` calls in production code violate Rust rules — `crates/axiathon-client/src/output.rs:126,143,145,147,148`
The project's Rust rules explicitly state: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." While `expect()` is used here (not `unwrap()`), these are in the `OutputFormatter::format()` trait methods which return `String`, not `Result`. If CSV write fails (e.g., on malformed input), the program panics instead of returning an error. The trait should return `Result<String, CliError>` to handle errors gracefully. The `expect` messages are descriptive but still crash the process.

### `[MEDIUM]` `ClientConfig` silently ignores unknown TOML fields — `crates/axiathon-client/src/config.rs:10-12`
`#[serde(default)]` is applied but `#[serde(deny_unknown_fields)]` is not. The test `config_ignores_unknown_fields` explicitly validates this behavior and calls it "forward compatibility." However, this means typos in config files (e.g., `api_ur` instead of `api_url`) are silently ignored, and the default value is used. This is a common source of "my config isn't working" issues. At minimum, a warning log for unknown fields would be appropriate.

### `[MEDIUM]` `CompletionArgs.shell` field is `String` instead of typed `Shell` enum — `crates/axiathon-client/src/cli.rs:155-157`
The `CompletionArgs` struct accepts `shell` as a raw `String`, yet there's a well-typed `Shell` enum in `commands/completion.rs`. Clap supports `ValueEnum` derive for enums. Using a raw string means invalid shell names are not rejected at the clap parsing level — they pass through and would only fail at runtime in the handler. This defeats clap's purpose of early validation.

### `[MEDIUM]` `init` command is a stub contrary to story spec — `crates/axiathon-client/src/commands/init.rs`
AC-9 says "Shell completion generation (functional, not stub)" and "axiathon init first-time setup (functional, not stub)." The completion command IS functional. But `init` returns a stub message. The scope boundary says init should be functional. This is a gap.

### `[MEDIUM]` Nightly fmt check fails — `crates/axiathon-client/src/config.rs`, `crates/axiathon-client/src/output.rs`
`cargo +nightly fmt --all --check` shows formatting differences. Per the gotchas file: "Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not." This will fail CI.

### `[LOW]` `tenant` field is `Option<String>` not `TenantId` — `crates/axiathon-client/src/cli.rs:32`
The story's technical guardrails reference `axiathon-core` shared types including `TenantId`. The `--tenant` flag accepts a raw `String` with no validation. Per the Rust rules: "Newtypes for IDs: `TenantId(String)` — prevents mixing ID types." The tenant value should be parsed/validated into `TenantId` at the boundary.

### `[LOW]` No `after_help` usage examples on command groups — `crates/axiathon-client/src/cli.rs`
AC-2 requires "include `after_help` usage examples for each command group." None of the command structs have `#[command(after_help = "...")]` attributes. The help tests only verify help *renders without panic*, not that examples are present.

### `[LOW]` JSON metadata `request_id` is always `null` — `crates/axiathon-client/src/output.rs:116`
AC-4 says JSON includes `ResponseMetadata` with `request_id, timestamp, api_version`. The `request_id` is hardcoded to `null`. While this may be acceptable for stubs, the formatter has no mechanism to accept a request ID. The API should support setting it.

## Verdict: **CHANGES_REQUESTED**

Three High-severity issues block approval:

1. **No binary exists.** The entire story is about producing the `axiathon` CLI binary. Without `main.rs` and a `[[bin]]` entry, there is no binary. The exit code mapping, command dispatch, and tracing init all depend on `main.rs`.

2. **Missing `keyring` dependency.** The story explicitly requires OS keychain integration for token storage with sync-before-async loading to avoid deadlocks. This is entirely absent.

3. **Asymmetric null byte validation.** Tenant ID checks for `\0` but token does not. Security checks must be consistent — an attacker will target the weaker path.

*Persephone whispers: "The code is well-structured, the patterns are sound. But a CLI framework without a binary is like a door without a room behind it. Fix the three blocking issues and this will be solid."*
