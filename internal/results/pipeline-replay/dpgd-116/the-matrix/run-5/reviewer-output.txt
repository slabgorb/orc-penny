## Findings

### `[HIGH]` Missing `main.rs` binary entry point — `cli.rs:1`
The story explicitly requires `crates/axiathon-client/src/main.rs` as the binary entry point. It is absent. There is no `[[bin]]` section in `Cargo.toml`. The crate is a library only — it cannot produce the `axiathon` binary. Without this, AC-3 (exit code enforcement via `std::process::exit`) is unverifiable end-to-end, and the story's primary deliverable (an operator CLI binary) does not exist.

### `[HIGH]` Missing `commands/init.rs` module — `commands/mod.rs`
The `commands/mod.rs` does not declare `pub mod init;`, and there is no `init.rs` file under `commands/`. AC-1 requires `init` as a functional command (not stub). AC-10 explicitly scopes `init` as functional. The `Init` variant in `Commands` enum exists but has no handler to dispatch to.

### `[HIGH]` `RawConfig` silently ignores unknown fields (secret exposure risk) — `config.rs:13-17`
The `RawConfig` struct uses serde's default behavior which silently ignores unknown TOML keys. A user who accidentally puts `token = "my-secret"` or `password = "hunter2"` in their config file gets no warning. The test `client_config_does_not_store_tokens` at `config_loading.rs:122-138` explicitly acknowledges this gap with an `if let Ok(config)` branch — meaning it passes either way. This is a **vacuous assertion**: it cannot fail. Add `#[serde(deny_unknown_fields)]` to `RawConfig` to reject unknown keys, which catches misplaced secrets.

### `[HIGH]` `ServerError` Display leaks internal details (CWE-209) — `error.rs:17-18`
`ServerError(String)` uses `#[error("server error")]` which is safe, BUT the inner `String` is accessible via `Debug` and the variant is constructed with raw HTTP status text at `client.rs:58`: `CliError::ServerError(format!("HTTP {status}"))`. While the `Display` impl is safe, the `Debug` output (used in `{:?}` formatting) leaks the full inner string. If any logging or error handler uses `{:?}` (common in Rust error chains), internal details leak. The test at `security.rs:11-19` only checks `Display`, not `Debug`.

### `[MEDIUM]` `cargo +nightly fmt --all --check` fails — `output.rs:89`, `cli_structure.rs:87`
Per the reviewer gotchas, nightly fmt must pass. Two files have formatting diffs. This blocks merge per project conventions.

### `[MEDIUM]` `SiemClient` has no actual `reqwest::Client` — no HTTP functionality — `client.rs:1-62`
`SiemClient` is documented as wrapping `reqwest::Client` per AC-7, but it contains no `reqwest::Client` field, no HTTP methods (`get`, `post`), and no actual header injection. It's a data struct with a static `map_http_status` method. While stubs are acceptable for command handlers, the `SiemClient` itself is listed as in-scope for Story 6.1. There is no `reqwest` usage at all — it's a dead dependency.

### `[MEDIUM]` `Completion` shell parameter is a raw `String`, not a `ValueEnum` — `cli.rs:63-66`
The `Completion` variant takes `shell: String` instead of using `clap::ValueEnum` with a proper `Shell` enum. This means `axiathon completion nonsense` silently defaults to bash at `completion.rs:12` rather than returning a usage error (exit code 2). This violates the principle of least surprise and undermines AC-3's exit code contract.

### `[MEDIUM]` `with_env_overrides` doesn't read actual env vars — `config.rs:57-78`
The method takes `&[(&str, &str)]` rather than reading from the environment. There is no caller that actually reads `std::env::var("AXIATHON_API_URL")` and passes it in. The config precedence chain (CLI flags > env vars > config file > defaults) per AC-8 is architecturally incomplete — there's no integration point.

### `[MEDIUM]` `toml` version mismatch — `Cargo.toml:49` vs `crates/axiathon-client/Cargo.toml`
The workspace declares `toml = "0.8"` but the story spec says `toml 0.9`. The story's technical guardrails explicitly state `toml 0.9`. This is a spec divergence.

### `[LOW]` `JsonFormatter` uses hardcoded placeholder metadata — `output.rs:66-69`
`request_id` is `00000000-0000-0000-0000-000000000000` and `timestamp` is `1970-01-01T00:00:00Z`. While this is acceptable for a stub, the test at `output_format.rs:86-99` only checks that a `metadata` key exists — it doesn't verify the AC-4 required fields (`request_id`, `timestamp`, `api_version`) are all present individually.

The `/// **SECURITY:**` doc comment says "Display impls are for user-facing output only" but the project's `rust.md` rules say "`Display` impl is for internal logging only — sanitize before sending to clients." These contradict each other.
