# Story 6.1 Code Review — Mike Ehrmantraut

*Look, I'm not gonna sugarcoat this. I've been through every file. Tests pass — all 49 of them. The bones are decent. But this thing isn't finished, and I don't approve unfinished work.*

## Findings

### CRITICAL

**[CRITICAL] Missing `main.rs` — no binary entry point** — `crates/axiathon-client/src/main.rs` does not exist. The story spec explicitly requires it: "Binary entry point, tracing init, dispatch, exit codes." Cargo.toml declares no `[[bin]]` section either. The crate builds as a library only. There is no `axiathon` binary. No command dispatch. No exit code handling. No config loading. No token retrieval. The entire runtime path is absent. Every piece of library code is dead code from a user's perspective.

**[CRITICAL] `init` handler is a stub — spec requires it functional** — `commands/init.rs:3-4` returns `Err(CliError::NotImplemented(...))`. The story scope explicitly states: "Shell completion generation (functional, not stub)" and "axiathon init first-time setup (functional, not stub)". Completion is functional. Init is not. This directly violates the AC.

**[CRITICAL] Nightly `rustfmt` fails with 38 diffs** — Per `gotchas.md`: "Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval — don't let it slip to post-merge." It fails. 38 formatting diffs across `cli.rs`, all command handler files, `output.rs`, `config.rs`, and multiple test files. Non-negotiable blocker.

### HIGH

**[HIGH] `SiemClient::new()` silently blanks invalid URLs instead of erroring** — `client.rs:12-16`: if the URL doesn't start with `http://` or `https://`, it gets replaced with `""`. No error. `SiemClient::new("javascript:alert(1)").server_url()` returns `""`. Callers get a usable client object that will silently fail on every request. Should return `Result<Self, CliError>` and reject bad URLs at construction.

**[HIGH] `SiemClient._http` is dead code — no HTTP methods exist** — `client.rs:7`: `_http: reqwest::Client` is underscore-prefixed (acknowledging it's unused) and there are zero methods that make HTTP requests. `map_http_status()` is a static function unconnected to the client. The AC-7 SiemClient "wraps reqwest::Client" and "injects X-Tenant-ID and Authorization headers" — none of this wiring exists beyond field storage.

**[HIGH] `NotFound` error variant leaks raw HTTP body** — `client.rs:49-51`: `map_http_status(404, body)` passes the raw server response body directly into `CliError::NotFound { id: body.into() }`. The `error.rs:18` Display impl renders it as `"{resource} not found: {id}"`. If the server returns a verbose 404 with internal details (SQL errors, stack traces), those get printed to the operator's terminal. CWE-209 information exposure.

**[HIGH] `ServerError` variant also leaks raw body** — `client.rs:54`: `CliError::ServerError(body.into())` and `error.rs:24` renders as `"server error: {0}"`. Same CWE-209 risk. Despite the doc comment on `error.rs:3-4` saying "Do not leak internal server details," the `map_http_status` implementation does exactly that.

### MEDIUM

**[MEDIUM] `chrono_now()` produces non-standard timestamps** — `output.rs:108-113` generates `"1741876234Z"` (Unix seconds + "Z"). This is not ISO 8601 / RFC 3339. Any downstream consumer parsing `ResponseMetadata.timestamp` as a standard datetime will fail. AC-4 says JSON includes `ResponseMetadata` with timestamp — an epoch integer with a "Z" suffix is misleading.

**[MEDIUM] `with_env_overrides_from()` silently ignores invalid `AXIATHON_TIMEOUT`** — `config.rs:60-63`: `val.parse::<u64>()` failure is swallowed with no warning. User sets `AXIATHON_TIMEOUT=five`, gets the default 30s with zero feedback. Should at minimum log a warning, ideally return an error.

**[MEDIUM] CSV/JSON formatters use `expect()` / `unwrap()` in production paths** — `output.rs:59,75-76,79-81`: five `expect()` calls. The Rust rules say "No `unwrap()` in production code — use `?` or `expect()` with actionable message." These use `expect()` with messages, which satisfies the letter but not the spirit — a CSV write failure will panic the process instead of returning a clean error to the user.

**[MEDIUM] `RawConfig` ignores unknown TOML fields silently** — `config.rs:7-11`: `serde::Deserialize` by default ignores unknown keys. If an operator has `servre_url = "..."` (typo), no error or warning. The misspelled key silently falls back to the default. Consider `#[serde(deny_unknown_fields)]`.

**[MEDIUM] CRLF header injection: strip vs. reject** — `client.rs:26,32`: tokens and tenant IDs containing `\r\n` are silently sanitized by stripping. This prevents injection (good) but masks a potentially compromised input source. A token with CRLF is suspicious — rejecting with an error would be more secure than silent acceptance.

### LOW

**[LOW] `TableFormatter.color` field semantics are confusing** — `output.rs:9,13,21`: `color: bool` where `true` means "colors enabled" but `!self.color` triggers `force_no_tty()`. The logic is correct but inverted naming — `force_no_tty()` is called when color is *disabled*. Works, but maintenance hazard.

**[LOW] No `--config` path validation** — `cli.rs:23`: `config: Option<String>` accepts any string. No validation that the path exists or is readable at parse time. Errors surface later during config loading, which is acceptable but late.

- `SiemClient::new()` should return `Result` and reject non-HTTP URLs

The library pieces are solid. The glue is missing. No half measures.
