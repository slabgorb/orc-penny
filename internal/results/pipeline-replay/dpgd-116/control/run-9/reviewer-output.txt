# Story 6.1 Review: CLI Framework & Structure

## Review Findings

### [CRITICAL] F1: No `main.rs` — the `axiathon` binary does not exist
**`crates/axiathon-client/src/main.rs` — missing**

The entire deliverable of Story 6.1 is the `axiathon` operator binary. There is no `main.rs`, no `[[bin]]` section in `Cargo.toml`, and therefore no executable is produced. Without it:
- No command dispatch (clap parse → match on `Commands` → call handler)
- No tracing initialization
- No keychain token loading in sync context before Tokio (AC-8 requirement)
- No `process::exit(error.exit_code())` (AC-3)
- No stderr/stdout separation for errors vs output

This is not a stub — it's the missing skeleton that makes everything else usable.

### [HIGH] F2: `cargo +nightly fmt --all --check` fails on 8 files
**Per gotchas.md: "Always include nightly fmt check in the preflight"**

Nightly rustfmt enforces import ordering (std before external before crate) that stable does not. Confirmed violations in: `completion.rs`, `config.rs`, `output.rs`, and 5 test files. This is a mandatory gate per project rules.

### [HIGH] F3: JSON timestamp is Unix epoch seconds, not ISO 8601
**`crates/axiathon-client/src/output.rs:83-90`**

`chrono_now_iso()` outputs `"1741929034Z"` — a raw Unix epoch with a `Z` suffix. This is not ISO 8601 (`"2025-03-09T12:34:56Z"`). The function name is misleading (`chrono_now_iso` suggests ISO format) and AC-4 requires proper `ResponseMetadata`. Any consumer parsing the `timestamp` field as ISO 8601 will fail. The test at `output_format.rs:57-69` only checks for `"meta"` key existence — it never validates the timestamp format, so this bug passes silently.

### [HIGH] F4: JSON `ResponseMetadata` is missing `request_id` field
**`crates/axiathon-client/src/output.rs:56-63`**

AC-4 specifies: "JSON includes ResponseMetadata (request_id, timestamp, api_version)." The implementation includes only `api_version` and `timestamp` — no `request_id`. The test also doesn't verify this field exists.

### [HIGH] F5: `SiemClient` has no method to execute HTTP requests
**`crates/axiathon-client/src/client.rs`**

AC-7 requires the client to map HTTP status codes from *actual responses*. `build_get_request()` builds a `reqwest::Request` but there's no `execute()`, `get()`, `post()`, or `send()` method. The `http: reqwest::Client` field is stored but never used to send anything. The `map_http_status()` is a static utility disconnected from actual request flow. Without this, no command can actually talk to the server. Story 6.1 should at minimum provide the wired-up method even if no command calls it yet.

### [HIGH] F6: `completion.rs` panics on unsupported shell instead of returning `CliError`
**`crates/axiathon-client/src/commands/completion.rs:14`**

```rust
other => panic!("unsupported shell: {other}"),
```

Per the Rust rules: "No `unwrap()` in production code — use `?` or `expect()` with actionable message." A `panic!` on user input (invalid shell name) is worse than `unwrap()`. This should return a `CliError` and exit with code 2 (usage error). User-supplied input must never trigger a panic.

### [MEDIUM] F7: `RawConfig` silently ignores unknown fields including typos
**`crates/axiathon-client/src/config.rs:8-12`**

The comment says "All other fields silently ignored (serde default behavior)." This means `servr_url = "..."` (typo) is silently accepted and the default is used. While this is a deliberate design choice (noted in the comment), it means operators with config typos get no feedback. Consider at least a log warning for unknown fields, or use `#[serde(deny_unknown_fields)]` for fail-fast behavior.

### [MEDIUM] F8: `with_env_overrides_from` silently ignores unparseable `AXIATHON_TIMEOUT`
**`crates/axiathon-client/src/config.rs:76-79`**

```rust
"AXIATHON_TIMEOUT" => {
    if let Ok(t) = value.parse::<u64>() {
        self.timeout = t;
    }
}
```

If `AXIATHON_TIMEOUT=abc` is set, it's silently ignored and the default is used. The operator gets no feedback. This should at minimum emit a warning or return an error.

### [MEDIUM] F9: `toml` version mismatch — Cargo.toml says `0.8`, story spec says `0.9`
**`crates/axiathon-client/Cargo.toml:21`**

The Technical Guardrails specify `toml 0.9` in workspace dependencies. The crate uses `toml = "0.8"`. This is a minor divergence from the spec but should be documented or corrected.

### [MEDIUM] F10: `SiemClient::new()` does not validate URL scheme
**`crates/axiathon-client/src/client.rs:15-21`**

`SiemClient::new("ftp://evil.com")` or `SiemClient::new("not-a-url")` is accepted without validation. The test `siem_client_validates_server_url_scheme` at `security.rs:108-117` only checks that https and http are *accepted* — it never verifies non-http schemes are *rejected*. This is a vacuous test that proves nothing about validation.

### [LOW] F11: `build_get_request` uses `expect()` instead of error propagation
**`crates/axiathon-client/src/client.rs:80`**

```rust
builder.build().expect("failed to build GET request")
```

Per Rust rules, production code should use `?` not `expect()`. This could panic if the URL is malformed.

### [LOW] F12: Missing `#[cfg(test)]` module tests in source files
All unit tests are in `tests/` integration test files. While the `tests/` directory structure is fine, there are zero inline `#[cfg(test)] mod tests` blocks in any source file. The Rust rules state: "Unit: `#[cfg(test)] mod tests {}` in same file." This is a convention gap.
