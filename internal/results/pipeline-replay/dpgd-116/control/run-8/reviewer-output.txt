# Story 6.1 Review: CLI Framework & Structure

- `cargo +nightly fmt --all --check`: **FAILS** — formatting diffs in `client.rs`

## Findings

### [HIGH] Nightly `rustfmt` check fails — `client.rs`
Formatting differences detected in `crates/axiathon-client/src/client.rs:27` and `:47`. Per `gotchas.md`, nightly fmt is a mandatory gate. This must be fixed before merge.

### [HIGH] Missing `main.rs` — no binary entry point
AC-3 and AC-9 require the `axiathon` binary to exist. There is no `main.rs` in `crates/axiathon-client/src/`, and no `[[bin]]` section in `Cargo.toml`. The crate produces only a library. Without a binary, none of the following work: `axiathon --help` (AC-1), exit code mapping via `std::process::exit()` (AC-3), tracing initialization, command dispatch, or real shell completion generation. This is the skeleton the entire story is built around.

### [HIGH] `OutputFormatter` is a struct, not a trait (AC-4 violation)
AC-4 specifies: *"The `OutputFormatter` trait provides consistent formatting."* The implementation at `output.rs:11` defines `OutputFormatter` as a plain `struct`, not a `trait`. This blocks future extensibility (custom formatters, per-command formatting) and contradicts the story's acceptance criteria. The architecture doc also says "trait."

### [HIGH] `build_headers()` silently drops invalid header values — CWE-113 bypass
At `client.rs:34-35` and `:39-40`, `HeaderValue::from_str()` failures are silently swallowed with `if let Ok(val)`. If a tenant ID or token contains characters that reqwest rejects, the header is simply omitted with **no error, no warning, no log**. The `validate_tenant_id()` and `validate_token()` methods exist but are **never called** by `build_headers()` — they're dead code unless the caller remembers to call them first. This means:
- A malformed tenant ID silently sends requests without `X-Tenant-ID`, leading to cross-tenant data access or 403 errors with no diagnostic.
- A malformed token silently sends unauthenticated requests.
This is a silent failure bug. Either `build_headers()` should call the validators and return `Result`, or the validators should be integrated into the construction path.

### [MEDIUM] Missing `logout` and `tui` command groups (AC-1 violation)
AC-1 requires: *"`axiathon --help` must show all command groups: query, rules, alerts, ingest, config, status, tenant, login/**logout**, **tui**, completion, init."* The `Commands` enum in `cli.rs` has neither `Logout` nor `Tui` variants. Two of the eleven required command groups are absent.

### [MEDIUM] No TTY auto-detection for output format
AC-4 specifies: *"Table default for TTY, JSON for piped output."* The guardrails require using `std::io::IsTerminal`. There is no TTY detection anywhere in the crate. The format always defaults to `table` regardless of whether stdout is a terminal or a pipe. This breaks scriptability — piping `axiathon status` into `jq` would get table output, not JSON.

### [MEDIUM] `ClientConfig` does not reject unknown TOML fields
`config.rs:7` uses `#[derive(Deserialize)]` without `#[serde(deny_unknown_fields)]`. A config file with `tokne = "..."` (typo for `token`) would be silently accepted. Operators would not discover misconfiguration until runtime failures. This is a classic silent-failure vector.

### [MEDIUM] `toml` version mismatch — `Cargo.toml` says `0.8`, story spec says `0.9`
The workspace `Cargo.toml:48` declares `toml = "0.8"`, but the story's Technical Guardrails specify `toml` 0.9. This is a minor version gap that may matter if 0.9 has breaking API changes or features the implementation depends on.

### [MEDIUM] `keyring` dependency missing from `axiathon-client/Cargo.toml`
The story requires OS keychain credential storage via the `keyring` crate (AC-8). While the workspace `Cargo.toml` does not declare `keyring` at all, and the client `Cargo.toml` does not list it. There's no credential loading infrastructure. While login implementation is Story 9.1, the story spec says *"Load token at CLI startup in sync context BEFORE entering Tokio runtime"* — the plumbing should exist even if login itself is deferred.

### [MEDIUM] `expect()` calls in `render_csv` and `render_json` — production panics
At `output.rs:81`, `86-91`: five `expect()` calls in production code paths. The Rust rules say *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* These `expect()` messages are not actionable ("write CSV header" tells the user nothing). More importantly, CSV writing to a `Vec<u8>` can fail if the data contains certain edge cases. These should return `Result<String, CliError>`.

### [LOW] `completion.rs` returns empty string for unknown shell instead of error
At `completion.rs:14`, an unrecognized shell string returns `String::new()` silently. The user runs `axiathon completion nushell` and gets... nothing. No error, no exit code 2. This should return `Err(CliError::...)` or at minimum print a diagnostic to stderr.

### [LOW] `_http` field prefix suggests unused — `SiemClient` never makes HTTP calls
The `SiemClient` at `client.rs:8` names the reqwest client `_http` (underscore prefix = intentionally unused). For a story delivering the HTTP wrapper, the client should have at least a `get()`/`post()` method wired up, even if all command handlers are stubs. As-is, `SiemClient` is a struct with validation methods but no HTTP capability.
