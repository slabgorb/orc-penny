# Story 6.1 — Adversarial Code Review

## Observations

### [HIGH] Missing `main.rs` binary entry point — AC-3 exit code routing untested at `config.rs`

There is no `main.rs` file in `crates/axiathon-client/src/`. The story spec explicitly requires it: *"main.rs — Binary entry point, tracing init, dispatch, exit codes"*. Without it, the `axiathon` binary cannot be built, `std::process::exit()` with exit code mapping is not wired, and all downstream CLI stories (6.2–6.7) have nothing to dispatch through. The `[[bin]]` section is also absent from `Cargo.toml`. This is not a "stub" situation — the entire binary entry point is missing.

**File:** `crates/axiathon-client/src/main.rs` (absent)

### [HIGH] Missing per-file command modules per architecture spec at `commands/mod.rs`

The architecture spec requires individual command module files: `commands/query.rs`, `commands/rules.rs`, `commands/alerts.rs`, `commands/ingest.rs`, `commands/config.rs`, `commands/status.rs`, `commands/tenant.rs`, `commands/login.rs`, `commands/init.rs`. Instead, all stubs are collapsed into a single `commands/stubs.rs`. The `commands/init.rs` module (supposed to be functional, not a stub per AC scope) is entirely absent. This violates the file structure laid out in the story's "Key Files to Create" section and will force refactoring when later stories fill in each command group.

**File:** `crates/axiathon-client/src/commands/mod.rs:1-2`

### [HIGH] `with_token()` bypasses header injection validation at `client.rs:39-42`

`SiemClient::with_token()` (builder pattern) accepts any string including `\r\n` — only `try_with_token()` validates. Since `with_token()` is public API and the more ergonomic builder method, callers are likely to use it. A malicious or corrupt token containing CRLF could inject HTTP headers (CWE-113). The same issue exists for `with_tenant()` at line 62. Either the validation should happen in both paths, or the non-validating path should be `pub(crate)` / removed.

**File:** `crates/axiathon-client/src/client.rs:39-42`, `client.rs:62-65`

### [MEDIUM] `ConfigError` Display leaks arbitrary user-controlled strings at `error.rs:28-29`

`#[error("configuration error: {0}")]` for `ConfigError(String)` passes through the inner string verbatim. While this is a config error (not server-sourced), the inner string could contain file paths or TOML parse errors that reveal internal directory structures. This is inconsistent with the `ServerError` and `NotFound` variants which correctly sanitize their Display output. The `/// **SECURITY:** ...` doc comment on the error enum notes this concern.

**File:** `crates/axiathon-client/src/error.rs:28-29`

### [MEDIUM] `toml` version mismatch: workspace declares `0.8`, story spec says `0.9` at `Cargo.toml:49`

The workspace `Cargo.toml` declares `toml = "0.8"` but the story technical guardrails specify `toml` 0.9. This may be intentional (0.9 not yet released or compatible), but it's a spec deviation worth noting.

**File:** `Cargo.toml:49`

### [MEDIUM] `RawConfig` silently ignores unknown fields at `config.rs:13-17`

The `RawConfig` struct uses default serde deserialization which silently ignores unknown TOML keys. A user who types `servre_url` (typo) gets no feedback — the typo is silently ignored and the default URL is used. Adding `#[serde(deny_unknown_fields)]` would catch configuration mistakes. The test `client_config_ignores_token_field_in_toml` passes precisely because of this — it silently drops the `token` field rather than warning the user.

**File:** `crates/axiathon-client/src/config.rs:13-17`

### [MEDIUM] `format_json` uses `expect()` in production code at `output.rs:125`

`serde_json::to_string_pretty(&output).expect("JSON serialization should not fail")` violates the Rust coding rule: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* While `expect()` with a message is technically allowed, this is in a formatting function that could be called in production. The same issue appears with `csv::Writer` at lines 131, 134, 136, 137. The `expect` messages are descriptive but these should propagate errors via `Result` rather than panicking.

**File:** `crates/axiathon-client/src/output.rs:125,131,134,136,137`

### [MEDIUM] `completion.rs` returns empty string for unknown shell — silent failure at `completion.rs:11`

`generate_completion("tcsh")` returns `String::new()` silently. Per AC-9, installation instructions should go to stderr. An unsupported shell should return an error (or at minimum print a warning), not silently succeed with empty output. The test at `completion_tests.rs:68` only checks it doesn't panic, not that it communicates the failure.

**File:** `crates/axiathon-client/src/commands/completion.rs:11`

### [MEDIUM] `with_env_override` silently ignores unparseable `AXIATHON_TIMEOUT` at `config.rs:78-80`

If `AXIATHON_TIMEOUT=abc`, the `parse::<u64>()` failure is silently swallowed and the config retains its previous value. The operator gets no warning that their env var was ignored. This violates the "no silent error swallowing" principle.

**File:** `crates/axiathon-client/src/config.rs:78-80`

### [MEDIUM] Nightly `rustfmt` check fails — import ordering issues

`cargo +nightly fmt --all --check` reports diffs in `cli_structure_tests.rs` (import ordering) and formatting. Per the gotchas file: *"Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval."*

### [LOW] `Commands` enum missing `Tui` and `Logout` variants per AC-1 at `cli.rs:47-68`

AC-1 requires `--help` to show: `login`/`logout`, `tui`. The `Commands` enum has `Login` but no `Logout` or `Tui` variants. The story scope says TUI implementation is out of scope but the command group stub should be present.
