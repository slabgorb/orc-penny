# Story 6.1 CLI Framework — Adversarial Code Review

## Observations

### 1. `[HIGH]` Nightly `rustfmt` check fails — `cli.rs` and multiple test files

`cargo +nightly fmt --all --check` fails with formatting diffs in `cli.rs`, `cli_structure.rs`, `config_loading.rs`, `exit_codes.rs`, `global_flags.rs`, and `shell_completion.rs`. Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight. Nightly rustfmt enforces import ordering that stable does not. If it fails, flag it before approval."*

**Files:** `src/cli.rs`, `tests/cli_structure.rs`, `tests/config_loading.rs`, `tests/exit_codes.rs`, `tests/global_flags.rs`, `tests/shell_completion.rs`

### 2. `[HIGH]` No `main.rs` — crate produces no binary

The crate has no `main.rs` and no `[[bin]]` target in `Cargo.toml`. AC-1 requires `axiathon --help` to work, and the entire story is about delivering the `axiathon` binary. Without a `main.rs`, there is no binary entry point. The story spec explicitly lists `main.rs` as a key file: *"Binary entry point, tracing init, dispatch, exit codes"*. This is the most critical missing piece — the crate is library-only.

**File:** `crates/axiathon-client/Cargo.toml` (missing `[[bin]]` or `src/main.rs`)

### 3. `[HIGH]` `CliError` does not use `thiserror` — violates Rust coding rules

The project's `rust.md` rules state: *"Use `thiserror` for error enums — structured, semantic variants (not string bags)."* `CliError` at `error.rs` manually implements `fmt::Display` and `std::error::Error` instead of using `#[derive(thiserror::Error)]`. The `thiserror` dependency is declared in `Cargo.toml` but unused.

**File:** `crates/axiathon-client/src/error.rs:7-18`

### 4. `[MEDIUM]` Config silently accepts unknown TOML fields — no `#[serde(deny_unknown_fields)]`

`RawConfig` at `config.rs:16` deserializes TOML without `deny_unknown_fields`. A typo like `api-url` (hyphen) or `timout` would be silently ignored, and the user would get defaults without any warning. This is a common source of operator confusion.

**File:** `crates/axiathon-client/src/config.rs:16`

### 5. `[MEDIUM]` `SiemClient` doesn't construct a `reqwest::Client` — AC-7 incomplete

AC-7 states: *"SiemClient wraps `reqwest::Client`."* The current `SiemClient` stores `base_url`, `tenant`, and `token` as strings but never creates or holds a `reqwest::Client`. The `default_headers()` method builds a `HeaderMap` but there's no method to actually make HTTP requests. While future stories will implement handlers, the AC explicitly calls for wrapping `reqwest::Client`. The `reqwest` dependency is in `Cargo.toml` but only used for `HeaderMap`/`HeaderValue` types.

**File:** `crates/axiathon-client/src/client.rs:6-10`

### 6. `[MEDIUM]` `--format` uses raw `String` instead of `OutputFormat` enum in clap

The `--format` flag at `cli.rs:28` is `Option<String>` with a `PossibleValuesParser`. Since `OutputFormat` already implements `FromStr`, it should be `Option<OutputFormat>` with `#[arg(value_enum)]` or `value_parser`. Using a raw string means downstream code must re-parse and handle the error case, which defeats the purpose of clap validation. The `OutputFormat` enum already exists for this.

**File:** `crates/axiathon-client/src/cli.rs:28-29`

### 7. `[MEDIUM]` `--tenant` accepts raw `String` — not validated as `TenantId`

Per `rust.md`: *"Newtypes for IDs: `TenantId(String)` — prevents mixing ID types."* The story depends on `axiathon-core` which provides `TenantId`, but `--tenant` at `cli.rs:20` accepts `Option<String>`. This allows any string (including empty) to be passed as a tenant ID without validation at the trust boundary.

**File:** `crates/axiathon-client/src/cli.rs:20`

### 8. `[MEDIUM]` `output.rs` uses `expect()` in 5 places — potential panic in production

At `output.rs:71,77,79,82,83-84`, the CSV and JSON formatters use `.expect()` on operations that should be infallible but violate the spirit of the project's rule: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* The `expect()` messages are descriptive, so this is borderline acceptable, but `format_table` returns `String` rather than `Result<String, _>`, which means callers can't handle formatting errors gracefully.

**File:** `crates/axiathon-client/src/output.rs:71-84`

### 9. `[MEDIUM]` `rules` stub references Story 6.6 — likely incorrect story number

At `commands/rules.rs:6`, the stub says `story: "6.6"`. The epic context doesn't list a story 6.6 for rules management specifically. The story mapping may be wrong (e.g., rules might be a different story number). Other stubs like alerts (6.5), config (6.3), ingest (6.4) appear correct per the epic.

**File:** `crates/axiathon-client/src/commands/rules.rs:6`

### 10. `[MEDIUM]` `toml` version mismatch — crate uses 0.8, story spec says 0.9

The story technical guardrails specify `toml` 0.9, but `Cargo.toml:21` declares `toml = "0.8"`. This should be the version specified in the story.

**File:** `crates/axiathon-client/Cargo.toml:21`

### 11. `[LOW]` Missing `keyring` dependency — AC-8 credential storage not wired

AC-8 and the technical guardrails require: *"Credential storage: OS keychain via `keyring` crate."* The `keyring` dependency is not in `Cargo.toml` and there's no keyring integration. While login implementation is Story 9.1, the `keyring` dependency was listed as a Story 6.1 requirement in the key dependencies table, and `config.rs` has a `token()` method that always returns `None`.

**File:** `crates/axiathon-client/Cargo.toml`

### 12. `[LOW]` `init` command is minimal — only prints to stderr

`commands/init.rs` just does `eprintln!("Initializing...")` and returns `Ok(())`. The story says init should be "functional, not stub" but the current implementation is effectively a no-op. At minimum it could create the config directory and a default config file.

**File:** `crates/axiathon-client/src/commands/init.rs:3-6`

### 13. `[LOW]` Test `config_handles_large_timeout_gracefully` has no assertion

At `config_loading.rs:216`, the test assigns to `_result` with no assertion. This is a vacuous test — it verifies no panic but doesn't check whether the value was accepted or rejected.

**File:** `crates/axiathon-client/tests/config_loading.rs:211-217`

### 14. `[LOW]` Test `unmapped_error_codes_still_produce_error` has no assertion

At `siem_client.rs:228`, `let _ = err;` does nothing. The test name claims to verify errors are produced but the assertion is vacuous — `map_status_code` always returns `CliError`, so this test proves nothing.

**File:** `crates/axiathon-client/tests/siem_client.rs:224-229`

### 15. `[VERIFIED]` Header injection (CWE-113) protection is implemented correctly

`client.rs:32,40` checks for `\n` and `\r` before constructing `HeaderValue`, and `HeaderValue::from_str` provides additional validation. Tests verify this at `siem_client.rs:148-192`.

### 16. `[VERIFIED]` Error display does not leak internal paths (CWE-209)

The `CliError::Display` impl uses sanitized user-facing messages. Test at `exit_codes.rs:111-131` verifies no `/src/` paths or panic traces leak.

### 17. `[VERIFIED]` Token not stored in config file

`config.rs:85-87` always returns `None` for `token()`. The `RawConfig` struct has the `token` field with `#[allow(dead_code)]` to silently consume it. Test at `config_loading.rs:85-103` verifies this.

### 18. `[VERIFIED]` Exit code mapping is correct and complete

Exit codes 0/1/3/4 are correctly mapped. Code 2 is reserved for clap. Tests exhaustively verify all variants.

## Data Flow Trace

**Trace: tenant ID from CLI flag to HTTP header**
1. User passes `--tenant foo` → clap parses to `cli.tenant: Option<String>` (raw, unvalidated)
2. Code would pass to `SiemClient::new(url, tenant, token)`
3. `default_headers()` checks for CR/LF injection, then creates `HeaderValue`
4. **Gap:** No `TenantId` newtype validation (finding #7). An empty string `""` would produce a valid but meaningless `X-Tenant-ID: ` header.

## Verdict

**CHANGES_REQUESTED**

Three HIGH-severity findings block approval:

1. **No `main.rs`** — the binary doesn't exist. This is the deliverable of the story.
2. **Nightly `rustfmt` fails** — per `gotchas.md`, this must pass before approval.
3. **`CliError` doesn't use `thiserror`** — violates project coding standards with the dependency declared but unused.

The implementation quality is generally solid — security properties are handled well (header injection, token storage, error sanitization), test coverage is thorough (99 tests), and the architecture follows the two-binary pattern correctly. But the missing binary entry point is a fundamental gap that makes the crate unusable for its stated purpose.
