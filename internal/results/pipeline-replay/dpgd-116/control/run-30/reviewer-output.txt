## Devil's Advocate

Assume this code is broken. Where would it fail?

**A malicious user** could craft `AXIATHON_TIMEOUT=abc` and the CLI silently ignores it, using the file-based timeout instead. The user has no feedback that their env var is wrong — they think they set a 30-second timeout but are running with whatever the config file says, or the default. In a production incident scenario, an operator setting `AXIATHON_TIMEOUT=120` to increase timeout for a slow query could accidentally typo `AXIATHON_TIMEOUT=12O` (letter O) and silently get the wrong timeout. This is a real operational hazard. [SILENT]

**A confused user** adds `token = "sk-..."` to their `cli.toml`. The test `config_has_no_token_field` passes because the config doesn't have a `token` field in the struct. But with `serde(default)` and no `deny_unknown_fields`, the token string is silently ignored and the user has no idea their token isn't being used. This is acceptable behavior (tokens go in keychain per AC-8), but a warning would be better.

**A stressed filesystem** produces an error at `client.rs:64-72`. If `reqwest` returns a non-connect, non-timeout error (e.g., TLS certificate error, DNS resolution failure, redirect loop), it falls into `CliError::General(e.to_string())`. The `e.to_string()` from reqwest could contain: the full URL including path, TLS error details mentioning certificate subjects, DNS resolver details. All of this is echoed to the user via `#[error("error: {0}")]`. This contradicts the **SECURITY** doc comment at `error.rs:7-9`. This is the most serious finding — the security comment explicitly forbids this behavior, but the code does it anyway.

**CRLF header injection:** `with_token("evil\r\nX-Injected: true")` stores the value. When `.header("Authorization", format!("Bearer evil\r\nX-Injected: true"))` is called at `client.rs:58`, reqwest's `HeaderValue::from_str()` rejects newlines and panics in debug mode. In release mode, reqwest returns an error from `send()`. So reqwest protects at runtime, but the tests `tenant_id_rejects_newlines` and `token_rejects_newlines` claim to test this and don't — they only check `base_url()`. These tests are misleading: their names promise rejection but their assertions verify nothing about rejection.

**Config file with URL >2048:** `normalize()` silently sets it to `None`. The operator gets "server unavailable" or similar because no server URL is configured, with no indication their config was silently truncated. This is a real debugging trap.

**My Devil's Advocate uncovered:** The `CliError::General` info leakage is the critical finding. The tests for CWE-209 at `error_exit_codes.rs:106-124` test `Config` and `ServerError` variants which HAVE sanitized Display output — but they never test the `General` variant which is the one that actually leaks. The test suite provides false confidence on CWE-209.
