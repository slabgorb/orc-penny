## Findings

### BLOCKING

**[HIGH] F1 — Nightly `rustfmt` check fails** at `output.rs:102-104`, `cli_framework_integration.rs:119,126,143,270`, and others

`cargo +nightly fmt --all --check` produces diffs in 2 source files and at least 4 test files. Per `gotchas.md`: *"Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval."* This is a blocking CI gate.

**Fix:** Run `cargo +nightly fmt --all`.

---

**[HIGH] F2 — No `main.rs` binary entry point exists**

The `axiathon-client` crate is library-only. There is no `src/main.rs`, no `[[bin]]` section in `Cargo.toml`, and no command dispatch loop. The story spec requires a working `axiathon` binary (AC-1: `axiathon --help`, AC-3: exit codes enforced via `std::process::exit`, AC-10: stub handlers print messages and exit 1).

Without `main.rs`:
- No command dispatches to handlers
- No exit code enforcement (`CliError::exit_code()` is defined but never called)
- No token loading from keyring before Tokio runtime (AC-8 spec)
- No stderr/stdout routing (AC-3: "Errors printed to stderr, normal output to stdout")

The tests only exercise the library API in isolation. The binary contract is untested.

**Fix:** Implement `src/main.rs` with `fn main()` that parses `Cli`, dispatches to stub handlers returning `CliError::NotImplemented("Story X.Y")`, prints errors to stderr, and calls `std::process::exit(err.exit_code())`.

---

**[HIGH] F3 — `expect()` panics in production formatter code** at `output.rs:71,87,102-108`

The `OutputFormatter` implementations use 7 `expect()` calls. Per `rust.md`: *"No `unwrap()` in production code — use `?` or `expect()` with actionable message."* While `expect()` is technically allowed by the letter of the rule (it has a message), these are in production code paths that will panic on failure rather than returning errors. The `OutputFormatter` trait returns `String` (not `Result<String, CliError>`), which forces this pattern.

The `expect()` messages ("CSV header write should not fail") are descriptive but not actionable to an operator. A CSV write to an in-memory `Vec<u8>` is practically infallible, but `format_json` calling `serde_json::to_string_pretty` on user-influenced data is less certain.

**Severity rationale:** This is at the boundary between HIGH and MEDIUM. The JSON formatter operates on `serde_json::Value` which is always serializable, so the panic is practically unreachable. Downgrading to **MEDIUM** after tracing the data flow — but the trait design should be noted for future stories when formatters handle untrusted data.

*Revised:* **[MEDIUM]**

### NON-BLOCKING

**[MEDIUM] F4 — `dirs` version mismatch: spec says 6, workspace has 5** at `Cargo.toml:55`

The story spec states `dirs` 6 in the workspace dependencies table. The actual workspace `Cargo.toml` declares `dirs = "5"`. The crate `Cargo.toml` uses `dirs = { workspace = true }` so it inherits v5. This may be intentional (v6 may not exist yet or was a spec error), but it's a deviation from the documented architecture.

---

**[MEDIUM] F5 — `RawConfig` silently ignores unknown TOML fields** at `config.rs:27-37`

The `RawConfig` struct uses `#[derive(serde::Deserialize)]` without `#[serde(deny_unknown_fields)]`. An operator who typos `server_url` as `server_ur` gets no warning — the field is silently ignored and defaults are used. This is a classic config safety issue. The test `config_does_not_store_token_field` (`config_integration.rs:136-157`) actually exploits this: it writes `token = "should-be-ignored"` and verifies it's ignored. But this means ANY typo is silently ignored.

**Risk:** An operator sets `timout = 120` (missing 'e'), gets the 30s default, and blames the system for timeouts. No feedback.

---

**[MEDIUM] F6 — `timeout` field is `i64` with unsafe cast to `u64`** at `config.rs:35,79-81`

```rust
timeout: Option<i64>,  // line 35
...
if timeout > 0 {
    config.timeout_secs = timeout as u64;  // line 80
}
```

The TOML field is `i64`. Values like `i64::MAX` cast to `u64` correctly, but negative values are excluded by the `> 0` check. However, the test `config_rejects_negative_timeout` (`config_integration.rs:163-181`) is **non-assertive on the error path** — it uses `if let Ok(c)` which means if `load()` returns `Err`, the test silently passes without checking anything. This is a vacuous assertion pattern.

---

**[MEDIUM] F7 — `siem_client_rejects_newline_in_token` test is vacuous** at `siem_client_integration.rs:144-152`

```rust
fn siem_client_rejects_newline_in_token() {
    let client = SiemClient::new("https://axiathon.example.com")
        .with_token("valid-token\r\nX-Injected: malicious");
    let _ = client; // Construction should not panic
}
```

This test verifies construction doesn't panic — but doesn't verify the token was sanitized. Compare with `siem_client_rejects_newline_in_tenant_id` which actually inspects `client.tenant_id()` for `\r`/`\n`. The token test should verify `has_token() == true` AND that the stored value doesn't contain injection characters. The asymmetry suggests incomplete coverage.

---

**[MEDIUM] F8 — No server URL validation at config load time** at `config.rs:72-76,88-91`

Any non-empty string is accepted as `server_url`: `"not-a-url"`, `"file:///etc/passwd"`, `"localhost"` (no scheme). The operator discovers the error only when `SiemClient` makes its first HTTP request, with a cryptic reqwest error. Early validation (at least scheme + host) would provide better UX.

---

**[LOW] F9 — `toml_edit` used instead of `toml` per spec** at `Cargo.toml:21`, `config.rs:69`

The architecture spec says `toml` 0.9. The implementation uses `toml_edit` 0.22 with serde features. `toml_edit` is a superset (preserves formatting for round-tripping), so this works, but diverges from spec. Not a correctness issue.

---

**[LOW] F10 — Missing command modules** at `commands/mod.rs`

The spec lists 10 command modules under `commands/`: `query.rs`, `rules.rs`, `alerts.rs`, `ingest.rs`, `config.rs`, `status.rs`, `tenant.rs`, `login.rs`, `completion.rs`, `init.rs`. Only `completion.rs` exists. The others are presumably where stub handlers would live, and their absence is directly related to the missing `main.rs` (F2).
