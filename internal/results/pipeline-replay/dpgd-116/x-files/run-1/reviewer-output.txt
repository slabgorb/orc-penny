# Story 6.1 Review: CLI Framework & Structure

## Findings

### `[HIGH]` Nightly `rustfmt` check fails — `cli.rs` formatting violations
`cargo +nightly fmt --all --check` shows multiple formatting diffs in `cli.rs:50-73`. Per the project's `gotchas.md`: "Always include `cargo +nightly fmt --all --check` in the preflight. If it fails, flag it before approval." This blocks approval.
**At:** `crates/axiathon-client/src/cli.rs:50-73`

### `[HIGH]` `main.rs` is a dead stub — binary does not wire up the CLI framework
`main.rs` just prints "axiathon CLI not yet implemented" and exits with code 1. The entire CLI structure exists in `lib.rs` (tested via integration tests), but the actual binary is non-functional. The story scope says "producing binary `axiathon`" with functional completion and init commands. A binary that exits immediately with an error is not "producing" anything.
**At:** `crates/axiathon-client/src/main.rs:6-9`

### `[HIGH]` `Logout` command variant exists but has no handler module
`Commands::Logout(LogoutArgs)` is declared in `cli.rs:83` but there is no `commands/logout.rs` module and `commands/mod.rs` does not export one. When `main.rs` is eventually wired up to dispatch commands, `Logout` will have no handler to call. This is a missing module — not just a missing implementation.
**At:** `crates/axiathon-client/src/cli.rs:83`, `crates/axiathon-client/src/commands/mod.rs`

### `[MEDIUM]` `rules.rs` stub references wrong story — says "Story 6.4" (ingestion), should reference rules story
The rules stub says `"Story 6.4 — not yet implemented"` but Story 6.4 is ingestion control. Rules management is a different story. AC-10 requires stubs to print the correct story reference.
**At:** `crates/axiathon-client/src/commands/rules.rs:6`

### `[MEDIUM]` `ServerError` Display leaks raw server response body — CWE-209
The `#[error("Server error: {0}")]` variant passes through `response.text().await` verbatim from the server at `client.rs:94,103`. The `error.rs` header comment warns "Do not expose internal server details" but the implementation does exactly that. Server error pages can contain stack traces, internal paths, or deployment info.
**At:** `crates/axiathon-client/src/error.rs:14`, `crates/axiathon-client/src/client.rs:94-108`

### `[MEDIUM]` Dead dependencies: `axiathon-core`, `keyring`, `tokio`, `tracing` are declared but never imported
`Cargo.toml` lists four dependencies that have zero `use` statements in the source. `axiathon-core` is required by the architecture ("depends on axiathon-core ONLY for shared types") but isn't used yet. `keyring` is listed but credential storage isn't implemented. These inflate compile times for no benefit.
**At:** `crates/axiathon-client/Cargo.toml:13,19,24,26`

### `[MEDIUM]` `toml` workspace version is 0.8, story spec says 0.9
The technical guardrails specify `toml 0.9` but the workspace declares `toml = "0.8"`. If 0.9 doesn't exist yet, the spec needs updating; if it does, the dependency is behind.
**At:** `Cargo.toml:50`

### `[MEDIUM]` `--tenant` uses raw `String` instead of `TenantId` newtype
Per `rust.md` rules: "Newtypes for IDs: `TenantId(String)` — prevents mixing ID types." The `--tenant` flag at `cli.rs:26` is `Option<String>` and flows through as raw string into `SiemClient::with_tenant(&str)`. Since `axiathon-core` exports `TenantId`, this should use the validated type.
**At:** `crates/axiathon-client/src/cli.rs:26`, `crates/axiathon-client/src/client.rs:33`

### `[MEDIUM]` JSON metadata `timestamp` uses Rust Debug format, not ISO 8601
`format!("{:?}", std::time::SystemTime::now())` produces output like `SystemTime { tv_sec: ..., tv_nsec: ... }` — a Rust debug representation, not a usable timestamp. AC-4 specifies JSON includes `ResponseMetadata` with `timestamp`, which should be an ISO 8601 string.
**At:** `crates/axiathon-client/src/output.rs:113`

### `[MEDIUM]` JSON metadata `request_id` is timestamp-derived hex, not a UUID
The `request_id` is `format!("{:x}", nanos_since_epoch)` — a monotonic counter, not a unique identifier. Two requests in the same nanosecond would get the same ID. Should be a UUID v4 or similar.
**At:** `crates/axiathon-client/src/output.rs:109-111`

### `[LOW]` `exit_code()` returns `u32` but `std::process::exit()` takes `i32`
The return type mismatch will require a cast at the call site. Should return `i32` for direct compatibility.
**At:** `crates/axiathon-client/src/error.rs:44`

### `[LOW]` `tenant_stub_returns_not_implemented` test doesn't verify story reference
Unlike other stub tests (login → "Story 9.1", status → "Story 6.2"), the tenant stub message is just `"not yet implemented"` with no story reference. Inconsistent with AC-10 pattern.
**At:** `crates/axiathon-client/src/commands/tenant.rs:6`

### `[VERIFIED]` Header injection prevention — CRLF stripped from tenant and token values
`sanitize_header_value()` at `client.rs:14` removes `\r` and `\n` before values reach headers. Defense-in-depth with reqwest's own validation.

### `[VERIFIED]` Tokens never loaded from config file — `ClientConfig::token()` always returns `None`
Correctly prevents secret exposure via config file. Comment at `config.rs:98` documents this.

### `[VERIFIED]` `#[non_exhaustive]` on `CliError` — future variants won't break downstream
Correct usage per `rust.md` guidelines.

### `[VERIFIED]` `#![forbid(unsafe_code)]` on both `lib.rs` and `main.rs`

### `[VERIFIED]` Unknown TOML fields silently ignored via `#[serde(flatten)]` — correct forward-compatibility strategy
