## Problem
(From pennyfarthing gh #97.) Long-lived `pf.frame.app` uvicorn servers accumulate enormous kernel-side memory on macOS. Observed: four frame servers (one per Claude Code session) each at ~3.3GB physical footprint (~13GB total) — `footprint` attributes ~3.2GB to **Mach message** memory across 206k+ kernel regions, while Python heap (RSS) stays unremarkable (~700MB). Signature points at FSEvents/kqueue file-watcher or IPC-notification traffic received but never drained/deallocated. The frame server watches session state to drive the GUI; that channel accumulates kernel message regions unboundedly for the life of the process.

**Two issues in one (both in scope):**
1. **The leak** — drain/deallocate whatever Mach-port traffic the watcher generates (suspect FSEvents stream / notification queue never serviced or freed). Verification: `vmmap <pid>` / `footprint <pid>` — Mach-message regions should stay flat with uptime.
2. **The lifecycle** — frame servers outlive their sessions: four were running, at most one had a live session. Frame should exit or idle-timeout when its owning session ends, so even a slow leak can't compound across orphans.

Repro context: `Python -m uvicorn pf.frame.app:create_app --factory --host 127.0.0.1 --port <5xxxx>`, one per Claude Code session; matching `pf launch tui --foreground` processes are fine (~160MB).

## Technical Approach
Diagnose first: identify the file-watcher mechanism in `pennyfarthing-dist/src/pf/frame/` (e.g. `watchfiles`/watchdog/FSEvents-backed polling, WebSocket notification queues) and how observers/streams are created per request/connection vs per process. Likely fixes:
- Leak: ensure watcher streams/observers are bounded — single shared watcher rather than per-connection/per-poll instantiation; close/cancel streams on disconnect; drain notification queues; prefer stat-polling on macOS if FSEvents is the culprit.
- Lifecycle: idle-timeout and/or owner-liveness check (e.g. parent PID / session heartbeat / last-client-disconnect timer) that shuts the uvicorn server down cleanly when the owning session ends.

The Mach-region leak itself is not unit-testable in CI; TDD targets the *behavioral* invariants (watcher instance counts, resource cleanup on disconnect, shutdown trigger logic) plus a documented manual verification procedure with `footprint`/`vmmap`.

## Scope
- In scope: frame server watcher resource hygiene (leak), frame server lifecycle/idle-exit (orphan prevention), tests for both behaviors, manual leak-verification notes.
- Out of scope: TUI (`pf launch tui`) processes (healthy), Frame feature work, broader server refactors.

## Acceptance Criteria
1. File-watching/notification resources are bounded: one shared watcher per process (not per connection/poll), and per-connection resources are released on disconnect — proven by tests.
2. Frame server self-terminates when its owning session ends (idle-timeout or owner-liveness), proven by tests of the shutdown trigger logic.
3. Manual verification procedure documented (footprint/vmmap before/after) showing Mach-message regions stay flat with uptime under watcher activity.
4. Existing frame tests still pass.
