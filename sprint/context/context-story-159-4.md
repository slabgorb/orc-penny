## Problem
(From pennyfarthing gh #74.) The `sm-setup` subagent sometimes writes the session file's `**Phase Started:**` field (and Phase History rows) as a human-readable, non-ISO timestamp, e.g. `2026-06-03 22:00 UTC`. `pf handoff complete-phase` then crashes in `_calc_duration` (`pf/handoff/complete_phase.py` ~line 265):

```
started = datetime.fromisoformat(started_str.replace("Z", "+00:00"))
ValueError: Invalid isoformat string: '2026-06-03 22:00 UTC'
```

`fromisoformat` can't parse the trailing ` UTC`; the code only normalizes a trailing `Z`. This blocks every phase handoff until a human edits the session file, and the traceback points at click/complete_phase internals — not at the offending session file — so the root cause is non-obvious.

## Technical Approach
Both fixes from the issue (producer + consumer):
1. **Consumer (defensive, primary):** make `_calc_duration` (and any sibling timestamp parsing in the handoff path) tolerant — normalize trailing ` UTC` (and `Z`) to `+00:00`, accept the `YYYY-MM-DD HH:MM UTC` shape; on a still-unparseable string, degrade gracefully (e.g. duration `-`/unknown) or fail with a message naming the session file and the bad string — never a raw ValueError traceback.
2. **Producer:** ensure the sm-setup template/instructions and any Python code that stamps `Phase Started` / Phase History rows emit ISO-8601 (`2026-06-03T22:00:00+00:00` or `...Z`). Note the producer is partly an agent (markdown instructions in `pennyfarthing-dist/agents/sm-setup*.md` or templates) — fix the template/instruction text AND any code path.

Relevant code: `pennyfarthing-dist/src/pf/handoff/complete_phase.py` (`_calc_duration`), session templates under `pennyfarthing-dist/templates/`, sm-setup agent definition under `pennyfarthing-dist/agents/`.

## Scope
- In scope: tolerant timestamp parsing in handoff duration calc, actionable error naming the session file on unparseable input, ISO-8601 emission in sm-setup template/instructions and code stampers.
- Out of scope: broader session-schema changes, other epic-159 stories.

## Acceptance Criteria
1. `_calc_duration` (complete-phase path) accepts `YYYY-MM-DD HH:MM UTC`, trailing `Z`, and ISO-8601 with offset — no crash; duration computed correctly.
2. A genuinely unparseable timestamp does not raise a raw ValueError: handoff degrades gracefully and/or the error names the session file and the offending string.
3. Whatever stamps session timestamps (template text/code) specifies/emits ISO-8601.
4. Existing handoff tests still pass.
