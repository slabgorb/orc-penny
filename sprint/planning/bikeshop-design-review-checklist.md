# BikeShop / BikeRack Design Review Checklist

**Created:** 2026-02-20
**Source:** Design review of bikerack-prd-ideas.md, bikerack-extraction-proposal.md, bikeshop-prd-revised.md
**Status:** In progress

## Issues

### 1. Panel data abstraction layer missing
- [x] **Resolved**
- **Severity:** Architectural — blocks both BikeRack extraction and BikeShop
- **Problem:** The extraction proposal says BikeRack, Cyclist, and BikeShop are peers sharing panel components from core. The revised PRD says BikeShop has "its own data pipeline" (SQLite → WebSocket → panels). But panels today are tightly coupled to BikeRack's specific WebSocket channel contracts. For panels to render "regardless of where data comes from," a data abstraction layer is required. The extraction proposal explicitly rejects this need ("does not need to make BikeRack's data sources pluggable"), but the revised PRD requires it by putting the same panels in both pipelines.
- **Resolution:** Introduce a typed DataSource provider abstraction in `@pennyfarthing/core` during the BikeRack extraction. Panel hooks (`useSprint`, `useGitStatus`, `useDiffs`, etc.) consume a `DataSource<T>` interface instead of hardcoded WebSocket URLs. Each data source (BikeRack live, BikeShop SQLite, capture replay) implements the same typed interface. TypeScript enforces the contract at compile time. This is dependency inversion — panels depend on the abstraction, sources implement it. The extraction already breaks every import path, so the marginal cost of introducing the provider interface during that work is lower than a second refactoring pass. Also enables mock providers for testing. The extraction proposal must be revised to include this work and remove the "no phantom interfaces" claim — the interface is real, justified, and load-bearing. Add ~3 points to the extraction estimate for the provider refactor across 11+ hooks.

### 2. BikeShop data pipeline duplicates BikeRack channel contracts
- [x] **Resolved**
- **Severity:** Architectural — affects BikeShop Phase 1 scope
- **Problem:** BikeShop must serve ShowRoom and BikeShow views from SQLite, but panels expect data shaped by BikeRack's 15 WebSocket channels. BikeShop would need to re-implement each channel's contract backed by SQLite, create adapters, or refactor panels to accept a generic data provider. None of these options are acknowledged or sized in the PRD.
- **Resolution:** Resolved by Issue 1. The DataSource provider abstraction eliminates the duplication problem. BikeShop implements the typed DataSource interface backed by SQLite — it doesn't re-implement WebSocket channel contracts. BikeRack implements it backed by live WebSocket + file watchers. Replay implements it backed by capture files. Each is N + M (N sources implement one interface, M panels consume one interface) instead of N * M (N sources each re-implementing M channel contracts). The revised PRD's "own data pipeline" language is correct — BikeShop does have its own pipeline — but the shared surface is the DataSource interface in core, not the WebSocket message format. Multi-session composition (BikeShow) works by parameterizing providers: `useDataSource('sprint', { session: 'holden' })`. The PRD should be updated to reference the DataSource interface as the integration contract between panel components and data sources.

### 3. Journey 8 BikeShow is a layout engine, not a feature
- [x] **Resolved**
- **Severity:** Scope — Phase 2 is undersized
- **Problem:** Journey 8 describes a multi-session composed view with per-session identity blocks, context sparklines, workflow iconographs, velocity indicators, and configurable panel rows. This is a full layout composition system — essentially dockview for the web with cross-session data composition. It's described in a user journey as if it's a feature but it's an infrastructure project comparable to the BikeRack extraction itself.
- **Resolution:** Two-step approach within Phase 2. Step 1: single-bike view — BikeShop serves a SQLiteDataSource (DR-1) for one remote session, panels render in the browser. Validates the DataSource pipeline end-to-end without layout complexity. Step 2: multi-session BikeShow using dockview-react (already a Cyclist dependency, framework-agnostic) for layout composition. Per-session identity cards (portrait, workflow iconograph, velocity) are custom components; arrangement and resize are off-the-shelf dockview. No custom layout engine. Journey 8 stays in Phase 2 but is acknowledged as the larger half — the PRD should size it accordingly rather than treating it as a single line item. See DR-5 in the extraction proposal.

### 4. BikeShop Views section forces Phase 2 architecture into Phase 1
- [x] **Resolved**
- **Severity:** Scope / Architectural — Phase 1 cost inflation
- **Problem:** The BikeShop Views section defines three view types (ShowRoom, BikeShow, single-bike) and asserts BikeShop has "its own pipeline." This architectural stance forces Phase 1 design decisions (data storage, panel serving) to accommodate Phase 2 features (multi-session composition). Building MVP ShowRoom without this architecture means rebuilding for Phase 2. Building with it makes Phase 1 much bigger than scoped.
- **Resolution:** Resolved by the DataSource provider abstraction (Issue 1). The interface in core bridges Phase 1 and Phase 2 cleanly. Phase 1 BikeShop builds ShowRoom as its own native UI (session tiles, status metrics — no panel components, no DataSource wiring needed). BikeShop stores telemetry in SQLite with a schema designed to support future DataSource queries. Phase 2 BikeShow adds a `SQLiteDataSource` implementation and feeds shared panel components through the typed interface. No Phase 1 rebuild required — the only Phase 1 obligation is schema design that doesn't paint BikeShow into a corner. The PRD's BikeShop Views section should be reframed: ShowRoom is Phase 1 scope (BikeShop-native UI), BikeShow and single-bike view are Phase 2 scope (DataSource-backed panel composition). The "own data pipeline" language is correct but should reference the DataSource interface as the shared contract that makes Phase 2 incremental rather than architectural.

### 5. "Intelligence at the edge" notification filtering is misplaced
- [x] **Resolved**
- **Severity:** Design — affects notification architecture
- **Problem:** The notification architecture says each BikeRack "evaluates relevance" of team-wide notifications. But BikeRack is a single-session local product without team context. It can't know whether "story #185 completed" matters to its session without understanding story dependency graphs, epic context, and developer roles. Either BikeShop must filter (sending only relevant notifications per BikeRack) or BikeRack needs team context it shouldn't own.
- **Resolution:** Stepped approach. MVP: BikeShop broadcasts all notifications (Option B). BikeRack applies a naive local filter matching on current epic, repo, and story. Functional for 5–10 sessions. Validates notification value before investing in routing. Post-MVP: upgrade to pub/sub topic-based filtering (Option C). BikeRack declares subscription topics on connect and updates them as context changes. BikeShop routes by topic. BikeRack continues fine-filtering locally. Backward-compatible — BikeRacks that don't declare topics get everything. The BikeShop connection protocol should reserve space for topic subscription from MVP even though it's not implemented yet. See DR-3 in the extraction proposal for full rationale.

### 6. Shared-secret auth is operationally hostile at team scale
- [x] **Resolved**
- **Severity:** Design — affects MVP viability
- **Problem:** Shared-secret means one token for the whole team. Revoking one person requires rotating everyone's token and redistributing. The PRD's own Journey 6 demonstrates this. For 5 people it's annoying; for 15 it's hostile. Forced reconnections from token rotation disrupt the persistent connections that the push notification / catch-up system depends on. The original ideas doc proposed SSH keypair auth (BikeShopPass) which handles per-identity revocation cleanly.
- **Proposed direction:** Introduce SSH keypair auth from MVP instead of deferring to Phase 2.
- **Resolution:** OpenSSH keypair auth (BikeShopPass) from MVP. No shared-secret phase. Per-identity keys give clean revocation without team-wide disruption. Developers already have `~/.ssh/` infrastructure. BikeShop operator registers public keys; BikeRack authenticates with its private key on connect. Removes the throwaway shared-secret implementation entirely. Revised PRD must move SSH keypair auth from Phase 2 to Phase 1 and remove shared-secret references.

### 7. Docker deployment adds unjustified friction
- [x] **Resolved**
- **Severity:** Design — affects adoption
- **Problem:** Target audience already has Node.js (they run Pennyfarthing). Docker adds dependency, port mapping, volume mounting, and container lifecycle for what could be `npx @pennyfarthing/bikeshop start`. SQLite works fine without Docker. The PRD doesn't justify Docker over a simple Node process.
- **Resolution:** Docker is correct. No PRD revision needed. The team is k8s-first infrastructure — every team member runs OrbStack locally, and production deployments target Kubernetes. Docker is not added friction for this audience; it's the expected deployment model. Container isolation, reproducibility, and consistency with the team's infrastructure stack outweigh the marginal simplicity of a bare Node process. See DR-7 in the extraction proposal.

### 8. Cyclist becomes paper-thin — should it remain a separate package?
- [x] **Resolved**
- **Severity:** Architectural — affects package model
- **Problem:** If BikeRack is "everything that isn't Electron," Cyclist is ~2,000 lines: Electron main process, ClaudeService, MessagePanel, IPC. The extraction proposal doesn't question whether Cyclist should remain a separate package or become a build target of BikeRack. This matters because the three-peer model (BikeRack / Cyclist / BikeShop) is load-bearing — if Cyclist is just "BikeRack + Electron flag," the peer model collapses to two things.
- **Resolution:** Cyclist remains a separate package. The "paper-thin" framing is wrong — it confuses shared infrastructure with product identity. Cyclist is an IDE that owns the AI coding session. BikeRack observes a session it doesn't control. BikeShop aggregates sessions it doesn't control. Cyclist controls the session it owns. The extraction moves observability and data infrastructure into BikeRack. What stays in Cyclist is the irreducible control plane: ClaudeService (session lifecycle ownership, not just subprocess management), MessagePanel (the primary interaction surface — the IDE's editor pane), bell mode (conversation queue injection), permissions/ApprovalModal (tool approval UI), Reflector markers (agent-to-UI protocol driving QuickActions), TirePump (context clearing with session reload), and dockview layout (the IDE's spatial workspace). These are unique Cyclist capabilities that must not be present in BikeRack or BikeShop. Measuring post-extraction value by lines of code is a statistical illusion — the extraction removes shared infrastructure that happened to live in Cyclist first, not Cyclist's unique contribution. The three-peer model holds because the peers have distinct control boundaries, not just distinct codebases. See DR-8 in the extraction proposal.

### 9. No BikeRack ↔ BikeShop protocol contract defined
- [x] **Resolved**
- **Severity:** Design — blocks implementation
- **Problem:** The PRD says "BikeRack's enrichment output is the integration surface" and flags span format richness as a risk. But neither document defines what enriched spans look like, what BikeShop expects, or how the catch-up delta protocol works. The BikeShop client module lives inside BikeRack but speaks an undefined protocol to an unbuilt server.
- **Resolution:** Single authenticated WebSocket connection with typed message envelope (DR-4). Telemetry payloads use OTEL span format (JSON OTLP). Control messages (notifications, catch-up, lifecycle, subscriptions) use purpose-built typed messages. Protocol types defined in `@pennyfarthing/core` and shared by both BikeRack client module and BikeShop server. Design process works backward from DataSource types (DR-1): DataSource defines what BikeShop must produce → SQLite schema stores it → protocol messages carry enough to populate it. Capture format is the timestamped message stream. Connection lifecycle: auth (DR-2), session:start, catchup, steady-state streaming, cache-and-flush on disconnect/reconnect. See DR-4 in the extraction proposal for full protocol shape and connection lifecycle.

### 10. Appendix ideas not revisited after architectural correction
- [x] **Resolved**
- **Severity:** Consistency — future planning affected
- **Problem:** Ideas A–N were written assuming BikeRack is a lightweight launcher and WheelHub is the server. The extraction proposal makes BikeRack the full server stack. Ideas like failover (F), capture/replay (D), and cross-BikeShop casting (C) were designed around redirecting a telemetry stream from a lightweight client. Now failover means failing over the entire server process. The ideas haven't been revisited through the new architecture's lens.
- **Resolution:** Three ideas need annotation, not redesign. The rest are unaffected. **(D) Capture/Replay:** works better under the new architecture — DR-4 defines the capture format (timestamped message stream), DR-1 defines the replay consumer (ReplayDataSource). No revision needed. **(F) Failover:** simpler than originally described — BikeRack is a local product that keeps running; only the BikeShop connection module fails over. Failover is connection-level, not process-level. The idea's mechanics (timers, caching, preference swap) all hold at smaller scope. **(C) Cross-BikeShop Casting:** relay is straightforward under DR-4 — forward the typed message stream. BikeShop-side features (routing topology, remote control) are unchanged. Ideas A, B, E, G–N are BikeShop-side or CLI-side features that interact through the DR-4 protocol or BikeShop's own UI — unaffected by the extraction. See DR-6 in the extraction proposal.
